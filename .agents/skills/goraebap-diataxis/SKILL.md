# Diátaxis 기반 문서 작성과 관리

이 저장소의 지침 문서는 [Diátaxis](https://diataxis.fr/) 프레임워크의 3개 분면(튜토리얼 제외)과 용어집으로 관리합니다.

## 1. 분면 구분과 폴더 구조

| 분면 | 사이트 메뉴 | 폴더 | 독자의 질문 | 담는 내용 | 담지 않는 내용 |
| --- | --- | --- | --- | --- | --- |
| How-to guides | **플레이북** | `playbooks/` | "이 작업을 어떤 순서로 하지?" | 목표를 이루는 실행 절차, 설정 스니펫, 확인 명령 | 긴 배경 설명(→ 아티클), 모든 규칙 나열(→ 레퍼런스) |
| Explanation | **아티클** | `articles/` | "왜 이렇게 설계했지?" | 설계 의도, 대안 비교, 트레이드오프, 판단 기준 | 단계별 실행 지시(→ 플레이북), 건조한 스펙 표(→ 레퍼런스) |
| Reference | **레퍼런스** | `reference/` | "규칙·구조·스펙이 뭐지?" | 정확한 사실, 구조, 허용/금지 표, 계약, 매핑 | 1인칭 경험이나 긴 논증(→ 아티클), 작업 순서(→ 플레이북) |
| Glossary | **용어집** | `content/glossary/` | "이 용어가 무슨 뜻이지?" | 영역별(`frontend.md`, `backend.md`, `design-system.md` 등) 보편 아키텍처·설계 용어의 정의, 혼동 구분, 메타데이터 | 특정 프로젝트 전용 기능 분류명, 산문 메모 |

분면끼리 내용을 중복하지 않고 **상대 경로 링크**로 연결합니다.
- 플레이북 → 기준표가 필요하면 레퍼런스로 링크
- 레퍼런스 → 설계 배경이 필요하면 아티클로 링크
- 아티클 → 구체적 규칙이 필요하면 레퍼런스로 링크

## 2. 톤앤매너

모든 문서는 담백한 **‘합니다’체**를 씁니다. 분면에 따라 글의 결을 분명히 나눕니다.

- **레퍼런스**: 건조하고 정확하게 사실·규칙·경계만 씁니다. 이유는 생략하거나 한 구절까지만 둡니다.
- **플레이북**: 번호가 매겨진 실행 단계와 바로 복사해 쓸 수 있는 설정·명령 위주로 씁니다. 마지막에 동작 확인 단계를 둡니다.
- **아티클**: **유연하고 겸손한 기술 블로그 톤**으로 씁니다.
  - 다른 선택지(예: 전통 레이어드, 멀티모듈, ORM 등)의 장점을 솔직히 인정합니다.
  - 어떤 전제와 트레이드오프를 거쳐 현재 기준을 택했는지 사고의 흐름을 풀어냅니다.
  - 확신에 찬 선언(“~해야 한다”, “~이 달라집니다”, “~가 자연스럽게 풀립니다”, “~가 답답해집니다”)을 피하고, 관찰과 경험에 기반한 어투(“~라고 느끼게 되었습니다”, “~쪽이 덜 불편했습니다”, “~에 가깝습니다”, “~으로 타협했습니다”)를 씁니다.
  - 일기체나 우유부단한 결론(“알아서 선택하세요”)으로 흐르지 않게 선택의 근거와 중심은 유지합니다.

### 공통 금지 표현

- AI 특유의 서론·결론 금지 (“이 문서에서는 ~에 대해 알아봅니다”, “이상으로 ~을 살펴보았습니다”).
- 근거 없는 평가 수식어 금지 (“강력한”, “손쉬운”, “효율적인”, “완벽한”).
- 문단마다 `**이름**: 설명` 패턴이나 형식적인 3항목 나열을 기계적으로 반복하지 않습니다.
- 특정 제품명·사내 업무명·프로젝트 전용 기능 분류명(예: `cowork`, `foundation`)을 일반 지침에 넣지 않습니다. 어떤 프로젝트에서나 통용되는 일반화된 개념과 예시만 씁니다.

## 3. 프레임워크 중립성과 상단 탭 분리

프레임워크가 바뀌어도 기준이 무너지지 않도록 **공통 기준**과 **스택 구현**을 파일로 분리합니다.

```text
content/backend/
  playbooks/
    <slug>/
      index.md          # 공통 절차 (프레임워크 이름 없음)
      springboot.md     # Spring Boot 구현 절차
      nestjs.md         # NestJS 구현 절차 (추가 시 자동 탭 생성)
  articles/
    <slug>.md           # 단일 공통 글 (스택 탭 없음)
  reference/
    <slug>/
      index.md          # 공통 규칙·명세 (프레임워크 이름 없음)
      springboot.md     # Spring Boot 매핑·예시

content/glossary/
  frontend.md           # 프론트엔드 영역 용어집
  backend.md            # 백엔드 영역 용어집
  design-system.md      # 디자인 시스템 영역 용어집 (새 영역 파일 추가 시 자동 반영)
```

- **공통 문서(`index.md`)**: 모든 스택에서 참인 문장만 쓰고, 프레임워크 고유 용어 대신 일반 개념어(진입 계층, 트랜잭션 경계, 영속성 포트 등)를 씁니다.
- **스택 문서(`<stack>.md`)**: `<Slot>`/`<Fill>` 같은 전용 태그 없이 독립된 순수 마크다운으로 작성합니다. 사이트에서는 문서 상단 탭(`[공통]` | `[Spring Boot]` | `[NestJS]`)으로 전환해 보여줍니다.
- **단일 공통 문서(`<slug>.md`)**: 아티클처럼 스택 구분이 필요 없는 글은 단일 파일로 둡니다.

### 머리말 (Frontmatter)

- 공통 문서(`index.md`, `<slug>.md`): `title`, `summary`, `order`, `icon`을 작성합니다. 본문에 H1(`# 제목`)을 중복해서 쓰지 않습니다.
- 스택 문서(`<stack>.md`): `title`, `summary`를 작성합니다. 본문에 H1(`# 제목`)을 중복해서 쓰지 않습니다.
- 아티클·블로그 글: 카드뷰에 노출할 `thumbnail: /thumbnails/<slug>.jpg`를 함께 둡니다. 썸네일은 단색 배경 중앙에 주제를 추상적으로 표현하는 한 손 미니멀 잉크 스케치(16:9, 텍스트·테두리 없음)로 통일해 `web/apps/blog/public/thumbnails/`에 저장합니다.

## 4. 통합 용어집(`content/glossary/*.md`) 스키마

용어집은 영역별 마크다운 파일(`content/glossary/<domain>.md`)로 한 폴더에서 관리합니다. 사이트의 통합 용어집 테이블(`/glossary`, 영역·분류 필터·검색)과 본문 용어 팝오버 인터랙션에 자동으로 파싱됩니다. 별도 산문 절이나 메모를 섞지 않고 모든 항목을 동일한 엔트리 구조로 작성합니다.

```markdown
---
domain: backend
label: 백엔드
order: 2
---

## <카테고리>

### <대표 용어> (<영문>)

- **id**: `<전역-고유-영문-슬러그>`
- **정의**: 팝오버에 단독으로 띄워도 완결되는 1~2문장입니다.
- **구분**: *(선택)* 혼동하기 쉬운 다른 용어와의 경계입니다.
- **스택 매핑**: *(선택)*
  - Spring Boot: 대응 표현
  - NestJS: 대응 표현
- **관련 컴포넌트**: *(선택)* `button`, `dialog`
- **자동 연결**: *(선택)* `없음` 또는 `별칭1, 별칭2` (생략 시 대표 용어로 본문 자동 연결)
```

- 어떤 프로젝트에서나 통용되는 보편 설계·아키텍처 개념만 수록합니다.
- 새 영역(예: `infra.md`, `ai.md`)이 필요하면 `content/glossary/` 아래에 파일만 추가합니다.
- 새 개념을 합의하면 해당 영역 용어집 파일에 먼저 추가하고, 본문 문서 전반에서 같은 이름으로 통일합니다.

## 5. 시각 표현용 코드 펜스 (순수 마크다운 유지)

문서 원본에는 JSX를 쓰지 않고 아래 3가지 코드 펜스로 폴더 구조·계층도·플로우차트를 표현합니다. GitHub과 AI 스킬에서는 일반 텍스트로 읽히고, 사이트에서는 디자인 시스템 톤의 전용 시각 컴포넌트로 렌더링됩니다.

- **`tree` (폴더 구조)**: 들여쓰기(2칸) + `# 설명` 주석으로 작성합니다. 첫 줄 `# title: 제목`을 넣으면 헤더 라벨로 쓰이고, 이름 앞 `!`를 붙이면 해당 줄을 강조합니다.
- **`layers` (수직 계층도)**: `# title:`, `# direction: down|up|none`, `# caption:` 메타 줄과 `이름 | 배지 | 설명` 행으로 작성합니다. 배지에 `선택` 또는 `optional`이 들어가면 점선 테두리로 구분합니다.
- **`mermaid` (플로우차트 · 시퀀스)**: 첫 줄에 `%% caption: 설명`을 적으면 다이어그램 하단 캡션으로 표시되며, 사이트에서 테마·다크모드 연동과 크게 보기 모달이 자동 적용됩니다.

## 6. 성숙도(Maturity) 메타데이터와 기준 점검

지침과 아티클에 실무에서 얼마나 오래 써 보고 검증했는지를 나타내는 성숙도 상태 코드와 근거를 기록합니다. 시간차 검증(승격·하향 추적), 근거 대비 감사, AI 스킬 적용 강도 구분에 활용하며, 아직 분류하지 않은 문서에는 생략합니다.

```yaml
---
title: ...
summary: ...
maturity: stable
maturityNote: "여러 업무 앱에서 오래 써 보며 검증됨. 소규모 단순 CRUD는 예외 가능"
reviewedAt: 2026-11-27
---
```

| 코드 | 라벨 | 의미 | AI 스킬(`goraebap-webapp`) 적용 강도 |
| --- | --- | --- | --- |
| `stable` | **안정** | 여러 프로젝트에서 오래 써 보며 실무 검증을 거친 기준 | 기본 기준 (프로젝트 예외 규칙이 없으면 그대로 따름) |
| `refining` | **다듬는 중** | 실무에 적용하며 계속 다듬고 있는 기준 — 경험에 따라 변경 가능 | 참고 기준 (상황에 맞게 유연하게 판단·확인) |

- **`maturityNote`**: 실무에서 얼마나 검증되었는지, 어떤 조건이면 바뀔 수 있는지를 1~2문장으로 적습니다.
- **`reviewedAt`**: 마지막으로 성숙도를 검토·갱신한 날짜(`YYYY-MM-DD`)를 적습니다.
- **점검·비교 명령**: 루트에서 `node scripts/maturity-audit.mjs` (`--unscored`, `--json`, `--stale=180`)로 분포, 근거 누락, 재검토 경과, Git 이력 기반 변화(`refining ↔ stable`)를 확인합니다.
