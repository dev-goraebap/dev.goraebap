# 계층과 명령

모듈은 단수 이름으로 두고 내부를 application·domain·infrastructure로 나눕니다. 모듈 루트의 Facade·Spi·Event가 공개 계약입니다. 다른 모듈의 내부 패키지를 직접 참조하거나 순환 호출하지 않습니다.

| 역할 | 책임 |
| --- | --- |
| Controller | 요청 형식 검증·HTTP 변환 |
| Service | 피처의 읽기·쓰기 유스케이스와 트랜잭션·도메인 조율 |
| Domain | 업무 불변식·의미 있는 상태 전이 |
| Infrastructure | jOOQ 영속성·조회·외부 연동 |

- 명령은 저장소에서 애그리거트를 복원하고 업무 메서드를 호출한 뒤 save합니다. 조회 DTO를 명령 판정의 원본으로 쓰지 않습니다. jOOQ에는 변경 감지가 없으므로 저장 호출을 생략하지 않습니다.
- Repository는 findById·findAllById·existsBy·save·saveAll처럼 의도를 드러냅니다. 반복문마다 조회·저장하지 않고 묶어 확인하고 일괄 처리합니다. 감사 주체는 명시적으로 전달합니다.
- 도메인은 프레임워크 비의존 순수 Java입니다. 엔티티의 변경은 업무 메서드로 제한하고, 모든 입력을 검증한 뒤 상태를 바꿉니다. Setter로 불변식을 우회하지 않습니다.
- 신규 create와 저장소의 fromPersistence를 구분합니다. 복원은 현재 생성 규칙을 과거 데이터에 다시 적용하지 않습니다. 불변 값·조회 모델은 record를 기본으로 합니다.
- 외부 전송을 확실히 보장해야 하면 커밋과 연결한 영속 outbox, 재시도와 멱등성을 설계합니다. 프로젝트에 이미 있는 신호·이벤트 기반을 먼저 확인합니다.

## 피처별 서비스

피처마다 `XxxService` 하나에 읽기·쓰기 메서드를 함께 둡니다. `XxxQueryService`와 명령 서비스로 나누지 않습니다. 읽기와 쓰기의 분리는 서비스 클래스 수가 아니라 처리 경로로 지킵니다.

| 메서드 | 처리 경로 |
| --- | --- |
| 읽기 | 같은 피처의 application 조회 포트 → jOOQ 구현 → 화면 DTO |
| 쓰기 | 도메인 저장소 → 업무 메서드와 불변식 검증 → 명시적 save |

공개 메서드는 리소스별로 묶고 목록 조회 → 단건 조회 → 생성 → 수정 → 삭제 → 그 밖의 상태 전환 순으로 둡니다. 복수 애그리거트를 다루는 유스케이스도 서비스가 조율합니다. 서비스와 애그리거트를 1:1로 맞추지 않습니다.

다른 피처의 완성된 조회는 소유 서비스의 읽기 메서드로 요청합니다. 다른 피처의 쓰기 메서드끼리 직접 호출하지 않고 실제 공유 대상의 소유권과 조율 경계를 정합니다. 쓰기 메서드에서 다른 피처의 화면 조회 결과를 가져와 핵심 상태 변경을 판정하지 않습니다.

## 트랜잭션

- 읽기만 있는 서비스는 클래스에 `@Transactional(readOnly = true)`를 선언합니다.
- 읽기·쓰기가 함께 있으면 클래스에 기본 트랜잭션을 달지 않고 public 메서드마다 선언합니다. 읽기는 `@Transactional(readOnly = true)`, 쓰기는 `@Transactional`입니다. 쓰기 메서드의 재정의를 빠뜨려 읽기 전용으로 실행되는 실수를 피합니다.
- 함께 성공해야 하는 변경은 같은 트랜잭션에서 처리합니다. 기존 전파·격리·롤백·잠금과 원자성을 유지합니다. 외부 호출·파일·메시지 전송을 DB 원자성으로 착각하지 않습니다.

기존 QueryService는 해당 피처를 고칠 때 같은 피처의 Service로 합칩니다. 표기 정리가 트랜잭션의 실제 범위를 바꾸지 않는지 공개 메서드 전체를 확인합니다. 관련 없는 피처를 일괄 변경하지 않습니다.
