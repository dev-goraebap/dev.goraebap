# 모듈 간 계약

모듈 루트에는 다른 모듈이 참조할 공개 계약과 공개 값 타입을 둡니다. 다른 모듈은 내부 application·domain·infrastructure 타입을 참조하지 않습니다.

## 피처별 Facade와 전달 타입

피처가 제공하는 계약은 `XxxFacade` 하나로 모읍니다. 같은 피처의 조회·쓰기·표시를 QueryFacade·CommandFacade·ViewFacade로 나누지 않습니다. 계약은 여러 소비자가 쓰는 업무 기능을 표현하고 내부 엔티티를 그대로 공개하지 않습니다.

전용 입력·결과는 Facade 안의 `Param`·`Result` 묶음이 소유합니다. 예를 들어 `ProductFacade.Param.Create`, `ProductFacade.Result.Detail`처럼 부릅니다. 전용 record는 해당 묶음에 중첩하며 묶음 클래스의 생성자는 감춥니다. Spi도 같은 방식으로 자기 전달 타입을 소유합니다.

- 단순 인자 하나를 억지로 Param으로 감싸지 않습니다.
- 여러 계약이 실제로 함께 쓰는 업무 enum·값 타입은 모듈 루트에 별도로 둘 수 있습니다.
- HTTP 요청·응답은 application의 해당 피처 Requests·Views에 둡니다. 모듈 계약과 HTTP DTO는 소유 경계가 다릅니다.
- Facade 구현은 그 계약을 선언한 모듈의 application에 둡니다. 소비 서비스는 상대 Facade를 직접 사용하고, 의미 없는 중계 포트·어댑터를 더하지 않습니다.
- Event는 업무 사건을 전달합니다. 동기 호출 결과가 필요한 유스케이스를 이벤트로 우회하지 않습니다.

## Spi 도입 조건

Spi는 소유 모듈이 외부 모듈에 구현을 요구하는 계약입니다. 다음 세 조건을 모두 충족할 때 도입합니다.

1. 소유 모듈이 자기 불변식을 검증하기 위해 그 정보가 필요합니다.
2. 소유 모듈의 데이터와 규칙만으로는 판정할 수 없습니다.
3. 호출 인자로 전달받아 해결할 수 없습니다.

소비자가 항상 값을 전달할 수 있으면 인자를 사용합니다. 편의 조회를 위해 Spi를 만들지 않습니다. 단순히 양방향 참조를 숨기려고 인터페이스를 늘리기 전에 모듈 경계가 실제 업무 경계인지 확인합니다.

Spi는 선언 모듈의 루트에 두고 선언 모듈 밖에서 구현합니다. 문서에 누가 구현하는지 명시합니다. 번역이 필요 없으면 소유 피처에서 직접 구현하고, 형태 변환이나 여러 피처의 조립이 필요할 때만 어댑터를 둡니다. 코드 의존 방향은 단방향으로 유지합니다.
