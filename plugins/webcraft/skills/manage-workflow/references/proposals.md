# 지침 제안

프로젝트 작업 중 요청이 기존 지침과 다를 때, 이 프로젝트만의 예외로 둘지 Webcraft 지침을 고칠지 정하고 Webcraft 원본 저장소(`dev-goraebap/dev.goraebap`)의 이슈로 받습니다. 제안자가 누구든 받아들일지는 플러그인 관리자가 정합니다. 프로젝트 세션에서 바로 PR을 올리는 안은 작업 중 다른 저장소 체크아웃·글쓰기 역할 위임·판 올리기가 끼어 무거워 쓰지 않고, 로컬 제안함은 다른 사용자의 제안을 받을 수 없어 쓰지 않습니다.

## 흐름

1. 프로젝트 작업 중 요청이 지침과 부딪히면 에이전트가 그때만 한 번 묻습니다. 선택지는 "이 프로젝트만 예외", "지침을 고치자(제안)", "지침대로 하기"입니다. 지침과 부딪히지 않으면 묻지 않습니다.
2. "이 프로젝트만 예외"를 고르면 프로젝트 AGENTS.md의 [프로젝트 규칙](project-rules.md) 표에 한 줄로 적습니다.
3. "지침을 고치자(제안)"을 고르면 프로젝트 작업은 멈추지 않습니다. 프로젝트에는 프로젝트 규칙 표에 지속 규칙 한 줄만 남기고 이슈 번호나 제안 표시는 붙이지 않습니다.
4. 이슈 본문은 일반화합니다. 제품명·고객·사내 주소·업무 데이터를 쓰지 않고, 제안한 프로젝트 이름 대신 프로젝트 종류(예: 사내 업무 앱)만 씁니다.
5. 공개 게시라 되돌리기 어려우므로 에이전트는 이슈 본문 초안을 사용자에게 보이고 승인을 받은 뒤 올립니다. 에이전트가 이슈를 올릴 수 있으면(`gh`가 있고 로그인됨) 승인받아 `gh issue create --repo dev-goraebap/dev.goraebap`로 올립니다. 올릴 수 없으면 같은 형식의 이슈 문서를 `~/.goraebap/issues/<YYYY-MM-DD>-<짧은 영문 이름>.md`로 만들고, 새 이슈 페이지 주소(`https://github.com/dev-goraebap/dev.goraebap/issues/new`)와 함께 "이 내용을 붙여 넣어 올려 주세요"라고 안내합니다.
6. 검토와 반영은 원본 저장소 세션에서 합니다. 열린 제안 이슈를 하나씩 보고 받아들이기·고쳐서 받기·버리기를 정한 뒤, 결과(반영한 판, 버린 이유)를 이슈에 남기고 닫습니다. 받아들인 것은 [글쓰기 맡기기](../../goraebap-mode/references/writer.md)로 스킬을 고치고 검사·판 올리기·배포를 합니다.
7. 프로젝트는 플러그인이 갱신되면 닫힌 이슈를 보고 프로젝트 규칙 표의 같은 줄을 지우거나 예외로 남깁니다.

기존 회수(프로젝트 규칙 중 공통으로 올릴 것 찾기)도 같은 절차로 이슈를 올립니다.

## 제안서 형식

| 항목 | 쓰는 것 |
| --- | --- |
| 고칠 지침 파일 | 대상 경로. 예: `design-system/references/theme.md` |
| 지금 규칙 | 현재 지침이 정한 기준 한 문장 |
| 바꿀 규칙 | 새로 바꿀 기준 한 문장 |
| 이유와 근거 | 프로젝트에서 일어난 일과 바꿀 이유 |
| 프로젝트 종류 | 제안을 만든 프로젝트의 종류(예: 사내 업무 앱) |
| 날짜 | 제안한 날짜(`YYYY-MM-DD`) |
