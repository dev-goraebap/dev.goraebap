# 코드 작성

파일 배치와 레이어·슬라이스·공개 API는 공식 `feature-sliced-design` 스킬을 따릅니다. 이 워크플로우에서 FSD 규칙과 검사기를 별도로 유지하지 않습니다.

- 컴포넌트는 PascalCase 파일 하나에 하나씩, 페이지에는 Page 접미사를 씁니다. 훅은 use로 시작하고 일반 유틸·설정 파일은 kebab-case입니다.
- 파생값을 state에 복사해 Effect로 맞추지 않습니다. 사용자 명령은 이벤트 핸들러·mutation이 처리하고, Effect는 외부 구독과 동기화에 쓰며 해제합니다.
- 값·함수의 메모이제이션은 측정된 비용 또는 참조 안정성이 필요한 경계에 씁니다. 개발 모드의 이중 실행 검사에서 드러난 수명주기 문제를 실행 방지 플래그로 숨기지 않습니다.
- 그룹·별칭·lint 설정은 프로젝트에서 확인합니다. 다른 프로젝트의 페이지 그룹이나 도우미 함수가 있다고 가정하지 않습니다.

## 화면 계층 묶기

- FSD 층은 `app` · `pages` · `features` · `entities` · `shared` 다섯이며 widgets 층은 두지 않습니다.
- `pages`는 주소입니다. 라우터의 파일 라우팅이 `pages` 폴더를 읽으며, 폴더 하나가 주소 하나이자 슬라이스 하나입니다. 폴더마다 그 아래 주소들의 부모 경로(레이아웃·가드·데이터 준비)를 맡는 파일과 그 주소의 화면을 맡는 파일을 나눠 둡니다. 주소에 나타나지 않는 묶음 폴더로 여러 주소에 같은 틀을 겁니다. 폴더 안의 슬라이스 세그먼트(`ui/`·`model/`·`api/`·`lib/`·`config/`)와 공개 진입점은 라우트로 읽지 않게 라우터를 설정합니다.
- `pages`의 파일은 자기 라우트 폴더와 조상 라우트 폴더의 것만 가져옵니다. 형제 주소의 코드는 가져오지 않으며, 두 주소가 함께 쓰는 것은 공통 조상 폴더로 올립니다. 프로젝트의 화면 규칙 검사로 확인합니다.
- 공간이 여럿인 앱은 공간마다 `pages` 아래 폴더를 두어 주소로 묶습니다. features·entities는 공간별로 묶지 않습니다.
- 슬라이스 안에서 컴포넌트는 파일 하나에 하나씩 둡니다. 여러 파일이 함께 쓰는 훅·로직은 `model/`에 두고, 한 파일에서만 쓰는 작은 조각은 그 파일 위쪽에 둡니다.
- `shared` 층 안에서 키트와 제품이 만든 공용 컴포넌트를 다른 폴더로 나눕니다. 업무를 모르는 레이아웃(앱 셸·페이지·분할 보기·칸 머리·휴대폰 도구)은 키트 안의 레이아웃 폴더에 모읍니다. 앱 셸처럼 업무를 아는 틀(공간·메뉴 항목·권한에 따른 관리 진입)은 `app` 층에 둡니다.
- 패턴의 공통 뼈대는 한 곳에 둡니다. 분할 화면의 진입부·목록 화면·줄, 위 단계 경로, 버릴지 묻는 창, 양식 바닥을 화면마다 다시 조립하지 않습니다. 화면은 줄·도구·칸 내용만 넘깁니다.
