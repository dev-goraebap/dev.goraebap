# 리팩터링

1. 유지할 동작(공개 계약·데이터·권한)과 바꿀 구조를 분리해 적고 호출자와 외부 계약을 확인합니다. 기능 추가나 버그 수정이 드러나면 같은 변경에 섞지 않고 따로 떼어 구조 변경을 먼저 마칩니다.
2. 코드를 옮기기 전에 지금 동작을 특성 테스트, 스냅숏, 비교 실행 같은 검증으로 고정합니다. 타입 검사와 린트만으로 동작이 고정되었다고 보지 않습니다. 테스트는 내부 구현이 아니라 사용자가 관찰하는 동작을 단언해, 내부를 바꿔도 통과하고 동작이 깨질 때만 실패하게 둡니다.
3. 지금 처음부터 만든다면 둘 목표 구조를 [프론트엔드 엔지니어링](../../frontend-engineering/SKILL.md)과 [백엔드 엔지니어링](../../backend-engineering/SKILL.md) 기준에 맞춰 먼저 정합니다.
4. 새 구조를 더하기 전에 죽은 코드, 한 번만 쓰는 감싸기, 중복 검증을 먼저 뺍니다.
5. 작은 단계로 옮기며 매 단계 검증을 통과시킵니다. 내부 API를 바꾸면 모든 호출자를 새 구조로 옮기고 예전 경로는 같은 변경에서 지웁니다. 호환용 다리나 옛길과 새길을 함께 두지 않으며, 이름을 바꾸면 문자열과 문서 속 참조까지 확인합니다.
6. 컴파일 통과로 끝내지 않고 고정한 검증과 [검증](../references/verification.md) 기준으로 실제 동작이 같음을 증명합니다. 읽는 사람의 부담이 줄지 않으면 되돌립니다.
7. 사용자가 허용한 범위에서 [Git 작업](../../webapp-project/references/git.md)에 따라 빼기 → 구조 변경 → 정리 순서의 작은 커밋으로 나눕니다.
