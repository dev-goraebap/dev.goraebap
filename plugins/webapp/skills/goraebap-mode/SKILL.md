# 웹 플랫폼 작업 방식

프로젝트가 채택한 개발 방식입니다. 현재 프로젝트의 AGENTS.md를 먼저 읽습니다. AGENTS.md의 "프로젝트 규칙"은 이 플러그인의 지침보다 우선합니다. 지침을 읽다가 프로젝트 규칙과 다른 곳을 만나면 프로젝트 규칙을 따릅니다. 작업 중 요청이 지침과 부딪히면 그때만 한 번 이 프로젝트만 예외로 둘지([프로젝트 규칙](../onboarding/references/project-rules.md)), 지침을 고칠지([지침 제안](../onboarding/references/proposals.md)), 지침대로 할지 사용자에게 묻고 처리합니다. 플러그인 원본과 다른 프로젝트는 자동으로 바꾸지 않습니다.

## 시작

시작할 때 프로젝트 AGENTS.md의 최소 버전과 설치된 플러그인 판을 비교합니다. 설치된 버전이 낮거나, 세션 중에 플러그인이 갱신돼 지침이 맞지 않거나, 필요한 지침을 읽을 수 없으면 추측으로 진행하지 않고 [이어받기 문서](references/handoff.md)를 따릅니다.

사용자가 원하는 결과를 짧게 설명하고 기존 변경·staging 상태를 확인합니다. 제품 동작이 달라지면 관련 요구사항과 설계를 읽습니다. 기록 위치와 이슈 도구는 프로젝트가 정합니다. 연결되지 않은 도구를 필수로 가정하거나 조회만 하는 질문에 업무를 만들지 않습니다.

프로젝트 AGENTS.md의 `Webapp 스택:` 줄을 확인합니다. 영역 지침은 구현을 담지 않으므로, 영역 지침을 읽을 때마다 같은 스킬의 `examples/`에서 프로젝트 스택과 이름이 같은 절을 함께 읽습니다([예시 읽기](references/examples.md)). 줄이 없으면 프로젝트의 실제 의존성에서 스택을 확인하고, AGENTS.md에 그 줄을 더할지 사용자에게 묻습니다([연결](../onboarding/SKILL.md#연결)). 맞는 스택 절이 없으면 지침만으로 진행하고 그 사실을 보고합니다.

작업에 맞는 플레이북 하나를 읽고, 계약·스키마 변경 같은 의존 단계만 함께 수행합니다. 작은 수정은 필요한 단계만 적용합니다.

| 작업 | 플레이북 |
| --- | --- |
| 문제 정의, 근거 조사, 선택지 결정 | [요구사항 토론](playbooks/requirements.md) |
| 저장소 구성, 지침 연결, 스택·배포 경로 설정 | [프로젝트 만들기](playbooks/project-setup.md) |

| 버그 재현·원인 추적·회귀 수정 | [버그 수정](playbooks/bug-fix.md) |

## 필요한 지침만 읽기

아래 링크에서 필요한 지침만 읽습니다. 관리 도구로 이름을 바꿔 설치하면 스킬 메타데이터와 지침 링크도 함께 바뀝니다.

| 바꾸는 것 | 읽을 스킬 |
| --- | --- |
| 시스템 경계·새 기술·형상관리·운영 | [webapp-project](../webapp-project/SKILL.md) |
| 화면 코드 구조·상태·라우트 | [frontend-engineering](../frontend-engineering/SKILL.md) |
| UI 컴포넌트·테마·레이아웃·화면 패턴 | [frontend-design-system](../frontend-design-system/SKILL.md) |
| 로딩·전환·상태 화면·상호작용 | [frontend-interaction](../frontend-interaction/SKILL.md) |
| 서버 모듈·도메인·API·스키마 | [backend-engineering](../backend-engineering/SKILL.md) |

스킬 이름은 지침 사이트(dev.goraebap.xyz)의 공간과 메뉴를 따릅니다. 프론트엔드 엔지니어링은 코드 구조와 상태, 디자인 시스템은 화면 표현, 인터랙션은 화면의 반응과 움직임을 다룹니다. 백엔드 엔지니어링은 도메인·서비스·트랜잭션과 함께 API 계약과 DB 마이그레이션을 참고 자료로 둡니다. 여러 영역을 바꾸면 관련 지침을 함께 읽습니다. 규칙 본문은 담당 지침 한 곳에서 고치고 다른 지침에서는 연결합니다. 지침의 규칙을 프로젝트의 스택으로 구현한 모양은 각 스킬의 `examples/`에서 읽습니다([예시 읽기](references/examples.md)).

스킬·참고 자료·문서를 작성하거나 고칠 때는 [글쓰기 기준](references/writing.md)을 읽습니다. 스킬 본문과 예시에도 같은 기준을 적용합니다. 글과 로고·이미지 같은 에셋은 맡길 역할을 정해 두었으면 [글쓰기 맡기기](references/writer.md)·[에셋 맡기기](references/assets.md)에 따라 맡기고, 정해 두지 않았으면 직접 만듭니다.

## 진행과 완료

- 관례와 코드로 확인할 수 있는 것은 확인하고 진행합니다. 제품 의미·팀 선택이 갈리는 부분만 질문합니다.
- 데이터 소유권·입출력·실패 상태를 정한 뒤 구현합니다. 추측한 재사용을 위해 계층을 늘리지 않습니다.
- 역할마다 기본값을 두되(글쓰기·에셋 역할), 도구와 모델은 사용자 설정과 실행 환경을 따르고 없으면 세션 모델을 씁니다. 다중 에이전트, 자동 커밋·병합을 전제하지 않습니다.
- [검증](references/verification.md)에 따라 바뀐 부분을 확인합니다. 수행한 검증과 남은 제한을 구분해 답합니다.
- 작업 보고에 읽은 지침과 예시 파일을 적습니다.
- 작업 중 MCP·플러그인 도구의 기능 부족이나 반복 호출을 실제 스키마로 확인하면 우회만 설명하고 끝내지 않고 [도구의 부족을 발견했을 때](references/tool-improvements.md)를 따릅니다.
- 브랜치·커밋·PR을 다룰 때는 [Git 작업](../webapp-project/references/git.md)을 따릅니다.
- 커밋·푸시·게시·배포는 사용자가 허용한 범위에서만 합니다.

스킬 자체가 틀렸으면 [지침 개선](playbooks/evolve.md)으로 원인을 고칩니다.
