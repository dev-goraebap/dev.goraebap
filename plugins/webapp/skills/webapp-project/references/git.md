# Git 작업

작업 브랜치를 어디서 따고 이름을 어떻게 붙이는지, 커밋과 PR을 어떤 기준으로 남기는지 정합니다. 브랜치 이름과 커밋만 보고 다른 사람이 무엇을 왜 바꿨는지 알 수 있어야 합니다. 브랜치 흐름은 [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow), 목적 접두사는 [Conventional Branch](https://conventionalbranch.org/)를 따릅니다.

프로젝트 AGENTS.md의 프로젝트 규칙이나 팀·회사 배포 지침이 다른 형식을 정했으면 그것을 따릅니다.

## 시작 전에 확인한다

작업 트리의 미커밋 변경과 지금 브랜치를 확인합니다. 다른 일의 변경과 섞이면 브랜치를 만들거나 커밋하기 전에 사용자에게 묻습니다. 커밋·푸시·PR 생성·병합은 사용자가 허용한 범위에서만 합니다.

## 기본 브랜치와 작업 흐름

기본 브랜치(대개 `main`)의 최신에서 새 브랜치를 땁니다. 한 브랜치에는 한 가지 일만 담고, `main`·`master`·`develop`에는 접두사를 붙이지 않습니다.

- 개인·단독 작업에서는 모든 변경에 PR을 강제하지 않습니다. 기본 브랜치에 직접 커밋하거나 작업 브랜치를 로컬에서 바로 합칠 수 있습니다.
- 팀 프로젝트나 협업 저장소에서는 작업 브랜치에서 PR을 거쳐 기본 브랜치에 합치는 것을 기본으로 둡니다.

## 브랜치 이름

이름은 `<목적>/<짧은 설명>`으로 붙입니다.

| 목적 | 쓰는 경우 |
| --- | --- |
| `feature` | 새 기능, 제품 동작 변경 |
| `fix` | 버그 수정 |
| `refactor` | 동작을 유지하는 구조 변경 |
| `docs` | 문서·지침만 바꿀 때 |
| `chore` | 빌드·도구·의존성·설정 |
| `hotfix` | 배포본의 긴급 수정. 프로젝트가 배포 브랜치를 쓸 때만 |
| `release` | 배포 준비. 프로젝트가 쓸 때만 |

`refactor`와 `docs`는 Conventional Branch에 없지만 이 스킬의 플레이북(기능·버그·리팩터링)과 맞추려고 둡니다.

설명은 영어 소문자·숫자·하이픈으로 두세 단어에서 다섯 단어 안에 씁니다. 대문자·밑줄·공백은 쓰지 않고, 하이픈과 점은 처음이나 끝에 두거나 잇달아 쓰지 않습니다. 점은 버전 번호(`release/v1.2.0`)에만 씁니다. 이슈 키가 있으면 설명 앞에 둡니다(`fix/hoho-123-session-expiry`).

에이전트·도구·사람 이름(`codex/`, `claude/`, 개인 이름)을 접두사로 쓰지 않습니다. 이름에는 목적이 보여야 하고, 누가 만들었는지는 커밋 작성자와 PR이 보여 줍니다. Conventional Branch가 정한 에이전트 출처 접두사(`ai/`, `claude/`, `codex/`, `copilot/`, `cursor/`)도 쓰지 않습니다. 최근 브랜치 이름을 보고 형식을 따라 하지 않고 이 문서의 형식을 따릅니다.

이미 푸시한 브랜치의 이름은 사용자 확인 없이 바꾸지 않습니다.

## 커밋

- 하나의 논리적 변경 단위로 커밋합니다. 기능·버그 수정과 무관한 포맷 변경이나 별개 리팩터링은 섞지 않습니다.
- 스키마·API 계약·생성 산출물처럼 원본과 함께 맞아야 하는 파일은 같은 커밋에 담아 중간 상태가 깨지지 않게 합니다.
- 커밋 메시지는 프로젝트에 정해진 형식과 언어를 우선 따릅니다. 별도 규칙이 없으면 변경의 핵심을 한 줄 제목으로 쓰고, 판단 배경이나 결정 경위(증상·원인·확인)가 필요할 때만 본문에 이유를 적습니다.

## PR과 병합

- PR을 열 때는 변경 목적, 핵심 변경점, 수행한 검증과 미확인 범위를 짧게 적습니다.
- 병합 방식(squash·merge·rebase)은 저장소 설정과 팀 규칙을 따르며, 병합이 끝난 작업 브랜치는 정리합니다.
