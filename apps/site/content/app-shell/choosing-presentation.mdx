사용자가 항목을 열거나 값을 바꾸고 새 대상을 만들 때, 그 화면을 팝오버·확인 창·대화상자·미리보기 패널·라우트 마스킹·페이지 중 무엇으로 열지 정하는 규칙입니다. 개발자와 에이전트가 새 기능의 화면 형태를 결정하거나 기존 화면을 검토할 때 위에서부터 질문 순서대로 대조해 판단합니다.

규칙마다 성격 표시를 붙입니다. **[관례]**는 여러 제품과 디자인 시스템 지침이 같은 방향으로 수렴한 기준이고, **[고래밥]**은 관례가 갈리거나 비어 있는 지점에서 이유를 두고 정한 우리 결정입니다. 표기 기준의 자세한 설명은 [읽는 법](/#규칙의-세-가지-표시)에서 다룹니다.

## 질문 순서로 표현 고르기

에이전트가 화면을 설계할 때 가장 자주 틀리는 판단이 오버레이와 페이지의 선택입니다. 조작이나 대상을 열 때는 아래 질문을 위에서부터 차례로 묻고, 처음 해당하는 표현을 고릅니다.

| 순서 | 질문 | 선택할 표현 | 데스크톱 | 휴대폰 | 주소(URL) | 구분 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 상태·담당자·날짜처럼 값 하나만 바꾸는가? | **그 자리에서 고르기** | 팝오버 | 바텀시트 | 없음 | [관례] |
| 2 | 삭제·폐기처럼 되돌릴 수 없는 결정을 확인하는가? | **확인 창** | 확인 대화상자 | 바텀시트 | 없음 | [관례] |
| 3 | 이름 바꾸기·초대처럼 몇 칸으로 끝나는 짧은 변경이고, 결과를 링크로 공유할 일이 없는가? | **짧은 양식 대화상자** | 모달 대화상자 | 바텀시트 | 없음 | [관례] |
| 4 | 목록을 보면서 여러 항목을 차례로 훑는가? | **미리보기 패널** | 목록 옆 비모달 패널 | 대상 페이지로 이동 | 목록 주소 + `?peek=대상ID` | [고래밥] |
| 5 | 만들기·수정처럼 짧게 끝내고 목록으로 돌아오지만, 내용이 길어질 수 있고 링크·새로고침이 의미 있는가? | **라우트 마스킹** | 목록 위 대화상자(크게 보기로 페이지 전환) | 처음부터 대상 페이지 | 주소창에 대상의 실제 주소 표시 | [고래밥] |
| 6 | 상세 본문, 활동·댓글, 대화, 여러 단계 작업처럼 읽고 오래 머무는가? | **자기 페이지** | 페이지 | 페이지 | 대상의 고유 주소 | [관례] |
| 7 | 외부에 링크로 공유하는 것이 주 목적인가? | **자기 페이지** | 페이지 | 페이지 | 대상의 고유 주소 | [관례] |

## 왜 이렇게 나누는가

오버레이(팝오버·대화상자·패널)와 별도 페이지를 가르는 기준은 **아래 화면의 맥락 유지**, **작업 길이와 복잡도**, **배경 참조 필요 여부**, **주소 공유 필요 여부** 네 가지입니다.

1. **[관례] 아래 화면의 상태를 유지해야 하면 오버레이, 길거나 복잡하면 페이지로 엽니다.**
   [Smashing Magazine의 모달·페이지 결정 트리(2026-03)](https://www.smashingmagazine.com/2026/03/modal-separate-page-ux-decision-tree/)는 목록의 스크롤·필터·선택 상태를 잃지 않고 잠깐 처리해야 할 때 오버레이를 쓰고, 작업이 길거나 단계가 많으면 별도 페이지로 분리하도록 안내합니다. [Atlassian Modal dialog 지침](https://atlassian.design/components/modal-dialog/usage)도 복잡한 상호작용, 큰 표, 여러 단계 작업에 모달을 쓰지 말라고 명시합니다.
2. **[관례] 배경 화면을 함께 봐야 하면 비모달로 엽니다.**
   모달 대화상자는 아래 화면을 가리고 조작을 막습니다. [NN/g(Modal vs Nonmodal)](https://www.nngroup.com/articles/modal-nonmodal-dialog/)는 모달을 치명적 경고, 진행에 꼭 필요한 정보 입력, 작업 노력을 줄이는 짧은 요청에만 쓰도록 제한합니다. 목록의 다른 항목과 비교하거나 연달아 훑어야 할 때는 Smashing Magazine 결정 트리의 기준대로 비모달인 [미리보기 패널](/app-shell/peek/)을 씁니다.
3. **[관례] 짧은 단일 컬럼 입력만 대화상자에 담고, 링크 공유 대상은 페이지로 둡니다.**
   [GitHub Primer Dialog 지침](https://primer.style/product/components/dialog/guidelines/)은 대화상자를 짧은 단일 컬럼 작업에만 쓰고, 링크로 공유해야 하는 내용은 페이지로 만들도록 정합니다.
4. **[고래밥] 짧게 끝나지만 주소도 필요한 만들기·수정은 라우트 마스킹으로 풉니다.**
   실무 도구에서는 이슈·문서 작성처럼 목록 맥락을 유지한 채 모달로 빨리 열고 싶지만, 작성 내용이 길어지거나 주소를 복사해 공유하고 새로고침해도 깨지지 않아야 하는 경우가 있습니다. 주소 없는 대화상자로만 열면 새로고침·공유·휴대폰 뒤로가기가 깨지고, 무조건 페이지로만 이동하면 목록의 조건과 스크롤 맥락이 끊깁니다. 그래서 앱 안에서 누르면 목록 위 대화상자로 열고 직접 진입·새로고침·휴대폰에서는 페이지로 여는 [라우트 마스킹](/app-shell/route-masking/)을 씁니다([Next.js Intercepting Routes](https://nextjs.org/docs/app/api-reference/file-conventions/intercepting-routes), [TanStack Router Route Masking](https://tanstack.com/router/latest/docs/framework/react/guide/route-masking)과 같은 원칙).

## 목록에서 행을 누를 때 무엇으로 여는가

목록의 행을 클릭했을 때 미리보기 패널을 열지 대상 페이지로 이동할지는 목록이 하는 일로 정합니다.

- **[고래밥] 한 목록 안에서는 행 클릭 동작을 하나로 통일합니다.**
  받은 항목·알림·승인 대기·검토 요청처럼 여러 항목을 연달아 확인하고 판단하는 **처리 목록**은 행을 누르면 미리보기(`?peek=ID`)를 엽니다. 반대로 업무·문서·자료처럼 하나를 골라 들어가 일하는 **작업 목록**은 행을 누르면 대상의 자기 페이지로 이동하고, 데스크톱에서 미리보기가 필요할 때는 `Space` 키나 행 끝의 미리보기 버튼을 씁니다. 판단이 애매할 때는 작업 목록(페이지가 기본, 미리보기는 보조 수단)으로 봅니다.
- **[관례] 어느 쪽이든 행은 실제 주소를 가진 링크로 둡니다.**
  새 탭으로 열기나 주소 복사를 했을 때 처리 목록은 `?peek=ID`가 붙은 주소를, 작업 목록은 대상의 고유 주소를 그대로 따라가야 합니다. 자세한 행 마크업 규칙은 [컬렉션](/app-shell/collections/)에서, 미리보기의 주소·히스토리 계약은 [미리보기 패널](/app-shell/peek/)에서 다룹니다.

## 대화상자와 시트의 경계 규칙

오버레이를 열 때는 중첩, 입력 보호, 휴대폰 전환의 세 가지 제약을 지킵니다.

1. **[관례] 모달 위에 모달을 쌓지 않습니다.**
   [Atlassian](https://atlassian.design/components/modal-dialog/usage), [Apple HIG(Modality·Sheets)](https://developer.apple.com/design/human-interface-guidelines/sheets), [NN/g](https://www.nngroup.com/articles/modal-nonmodal-dialog/) 모두 모달 대화상자나 시트 위에 다른 모달을 겹쳐 여는 것을 금지합니다(Primer는 예외적으로 최대 3단계까지 언급하나, 이 규칙집에서는 중첩 금지를 따릅니다). 대화상자 안에서 또 다른 선택이나 하위 양식이 필요해진다면 처음부터 페이지로 열어야 한다는 신호입니다.
2. **[고래밥] 확인 창만 열린 대화상자 위에 한 겹 허용합니다.**
   작성 중인 대화상자를 닫을 때 "작성 중인 내용을 버릴까요?"를 묻거나 삭제를 최종 확인하는 확인 창에 한해서만 현재 대화상자 위에 올릴 수 있습니다.
3. **[관례] 입력이 남아 있는 채로 닫을 때는 확인합니다.**
   사용자가 값을 입력한 상태에서 바깥 영역 클릭, `Esc`, 닫기 버튼으로 대화상자나 시트를 닫으려 하면 입력이 사라진다는 점을 알리고 닫을지 확인합니다([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/modality)).
4. **[관례] 데스크톱 팝오버와 짧은 양식·확인 대화상자는 휴대폰에서 바텀시트로, 긴 입력은 페이지로 바꿉니다.**
   - 그 자리 팝오버는 휴대폰에서 바텀시트로 엽니다. [NN/g Bottom sheets 지침](https://www.nngroup.com/articles/bottom-sheet/)에 따라 바텀시트에는 짧은 조작만 담고, 끌어서 닫기에만 의존하지 않도록 눈에 보이는 닫기 버튼을 두며, `Esc`와 바깥 누름으로도 닫히게 합니다. 시트 위에 시트를 쌓지 않고, 시트 안에서 다른 페이지로 이동하지 않습니다.
   - 이름 바꾸기·초대처럼 몇 칸으로 끝나는 짧은 양식과 확인 창은 휴대폰에서 바텀시트로 엽니다. 데스크톱은 대화상자, 휴대폰은 바텀시트로 그리는 반응형 대화상자는 [shadcn Drawer 문서의 Responsive 절](https://ui.shadcn.com/docs/components/base/drawer)이 권하는 방식이며, 그 예시도 프로필 고치기 양식입니다. 칸은 한 화면에 들어가는 만큼만 두고, 바닥에 취소·제출(버튼 44px, 짧은 실행 단추 88px 이상)을 두며, 시트 안 내용만 스크롤하고 아래 안전 영역을 피합니다. 가상 키보드가 올라오면 시트의 보이는 높이가 줄어 내용을 시트 안에서 스크롤해야 합니다.
   - 입력이 길어지거나 단계가 나뉘거나 제목·본문을 쓰는 양식은 바텀시트에 담지 않고 자기 주소를 가진 페이지로 엽니다. [Primer Dialog 지침](https://primer.style/product/components/dialog/guidelines/)도 대화상자를 짧은 단일 컬럼 작업에만 씁니다.
   - 휴대폰 전환 폭(1024px), 주소 없는 바텀시트를 닫는 방법과 뒤로가기 처리는 [적응형](/app-shell/adaptive/)에서 다룹니다.

## 확인하지 못한 것

- Linear 웹 앱의 모달·패널 실제 픽셀 크기 수치는 공개 자료에 없어 확인하지 못했습니다. 콘텐츠 영역과 읽기 열의 폭 기준은 [콘텐츠 폭](/app-shell/content-width/) 규칙을 따릅니다.
- Linear의 미리보기(peek)·모바일 상세 문서는 일부 원문을 확인하지 못해, 공개된 [Plane 미리보기 소스](https://github.com/makeplane/plane/blob/preview/apps/web/components/issues/peek-overview/view.tsx)와 디자인 시스템 지침을 함께 참고했습니다.
