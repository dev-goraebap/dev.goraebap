이 절은 1절의 품질 목표와 2절의 제약을 지키기 위해 Webcraft가 고른 근본 선택을 다룹니다. 서버는 필요한 경계를 가진 모듈형 모놀리스로 시작하고 모듈 사이는 공개 계약으로만 잇습니다. 서버가 HTTP 계약의 원본이며, 화면은 상태마다 소유자를 하나씩 정하고 캐시를 즉시 그려 가리는 막 없이 전환합니다. 변경이 맞는지는 말이 아니라 변경 종류별 점검으로 확인합니다.

## 4.1 핵심 선택

| 선택 | 내용 | 이유 |
| :--- | :--- | :--- |
| 모듈형 모놀리스 | 백엔드는 한 애플리케이션 안에 단수 이름의 모듈을 두고, 모듈 내부를 application·domain·infrastructure로 나눕니다. 별도 서비스·큐·캐시·복제·추상화는 구체적인 요구와 운영 비용이 확인될 때만 들입니다. | 경계는 코드로 지키면서 배포·운영 단위는 하나로 유지합니다. |
| 모듈 계약(Facade·Spi) | 모듈 루트의 Facade·Spi·Event만 공개 계약입니다. 피처마다 `XxxFacade` 하나에 조회·쓰기·표시를 모으고 전용 입력·결과는 `XxxFacade.Param`·`XxxFacade.Result`에 중첩합니다. Spi는 소유 모듈이 자기 불변식을 검증하는 데 필요하고, 자기 데이터로 판정할 수 없고, 호출 인자로 받을 수도 없을 때만 둡니다. | 다른 모듈의 내부 타입을 참조하거나 순환 호출하지 않고, 의존 방향을 단방향으로 유지합니다. |
| 피처별 서비스와 읽기·쓰기 경로 | 피처마다 `XxxService` 하나에 읽기·쓰기 메서드를 함께 둡니다. 읽기는 같은 피처의 조회 포트 `XxxQuery` → `JooqXxxQuery` → 화면 DTO, 쓰기는 도메인 저장소 → 업무 메서드와 불변식 검증 → 명시적 save 경로를 따릅니다. | 읽기와 쓰기의 분리를 서비스 클래스 수가 아니라 처리 경로로 지킵니다. 조회 DTO로 명령을 판정하지 않습니다. |
| 서버가 계약의 원본 | API를 바꾸면 OpenAPI 명세·생성 클라이언트 타입·실제 호출자를 같은 변경에서 맞춥니다. 오류는 `application/problem+json`과 안정된 오류 코드로 구별합니다. | 서버와 화면이 따로 타입을 맞추다 한쪽만 바뀌는 일을 막습니다. |
| 외부 작업 분리 | 외부 제공자 호출은 핵심 트랜잭션과 분리하고 타임아웃·실패·재시도·멱등성을 정합니다. 전송을 보장해야 하면 영속 outbox를 씁니다. | 핵심 트랜잭션의 성공과 외부 작업의 성공을 혼동하지 않습니다. |
| FSD 파일 구조 | 프론트엔드 파일 배치·레이어·슬라이스·공개 API는 공식 `feature-sliced-design` 스킬을 따릅니다. 조회를 소유한 슬라이스의 api에 요청·키·`queryOptions`를 함께 둡니다. | 코드 위치 규칙을 Webcraft가 따로 만들지 않고, 조회의 소유자가 코드 위치로 드러나게 합니다. |
| 상태 소유자 분리 | 서버 데이터·캐시는 TanStack Query, 경로·확정 필터·정렬·페이지·탭은 TanStack Router의 검증한 URL, 입력 초안·적용 전 필터·열림 상태는 로컬 state나 슬라이스 model이 소유합니다. | 같은 원본을 여러 곳에서 편집하고 맞추지 않습니다. 백그라운드 재조회가 입력을 덮지 않습니다. |
| 디자인 시스템 키트 | 지정이 없으면 shadcn/ui·Tailwind CSS v4·Solar와 레퍼런스 키트를 출발점으로 씁니다. 필요한 항목만 shadcn 레지스트리 `@webcraft`에서 받고 프로젝트가 소유합니다. | 셸·페이지·상태 화면을 화면마다 새로 그리지 않고, 공통 변경이 프로젝트에 자동으로 번지지 않게 합니다. |
| 가리는 막 없는 전환 | 첫 진입만 첫 방문 덮개로 덮습니다. 그 뒤에는 캐시를 즉시 그리고 뒤에서 갱신(stale-while-revalidate)하며, 캐시가 없으면 지금 화면을 유지하다 150ms가 지나면 카드 위쪽 2px 진행 표시만 띄웁니다. 링크에 포인터나 초점이 오면 그 화면을 미리 준비합니다. | 스켈레톤·영역별 덮개·불투명 막이 본문 높이와 맞지 않거나 재방문에서도 화면을 가려 읽던 자리를 잃게 합니다. |
| 라우트 마스킹 | 자기 주소가 있는 작성·수정 양식은 데스크톱에서 목록 위 대화상자로 열고 주소창에는 양식의 실제 주소를 보입니다. 직접 진입·새로고침·휴대폰에서는 대상 페이지로 엽니다. 읽는 대상의 상세는 자기 페이지로 엽니다. | 목록 맥락을 잃지 않으면서 모든 대상에 직접 접근할 주소를 둡니다. 초안은 라우터 위 저장소에 두어 크게 보기·분기점 전환에서도 남깁니다. |
| 점검으로 확인 | 변경 종류마다 확인할 것을 정합니다. 화면 전환·로딩·캐시를 바꾸면 실행 중인 앱에서 주요 이동을 누르는 Playwright 점검으로 `layout-shift`와 진행 표시를 잽니다. | 자동 검사 통과와 실제 동작 확인을 구분하고, 하지 않은 검증을 완료로 기록하지 않습니다. |

## 4.2 품질 목표와 전략의 연결

| 품질 목표 | 전략 | 자세히 |
| :--- | :--- | :--- |
| 화면 일관성 | 디자인 시스템 키트, 분기점 `64rem` 하나, 앱 셸과 페이지 슬롯을 공통으로 쓰기 | [8.5 화면 기초](/architecture/8-5/), [8.6 화면 배치와 탐색](/architecture/8-6/), [8.8 UI 부품 사용](/architecture/8-8/) |
| 밀림 없는 화면 전환 | 가리는 막 없는 전환, loader와 페이지가 같은 `queryOptions` 쓰기, 지연 로딩 부품을 전환 전에 준비하기 | [8.7 데이터 상태와 입력](/architecture/8-7/), [6. 실행 뷰](/architecture/6/) |
| 상태와 데이터의 소유 명확성 | 상태 소유자 분리, 라우트 마스킹의 초안 저장소, 모듈 계약과 피처별 조회 포트 | [8.4 프론트 코드와 상태](/architecture/8-4/), [8.2 백엔드 코드](/architecture/8-2/) |
| 계약 일치 | 서버가 계약의 원본, OpenAPI 생성 타입, problem+json 오류 | [8.1 API와 모듈 계약](/architecture/8-1/) |
| 단순한 구조 | 모듈형 모놀리스, Spi 도입 조건, 의미 없는 중계 포트·어댑터를 더하지 않기 | [5. 구성 요소 뷰](/architecture/5/), [8.1 API와 모듈 계약](/architecture/8-1/) |
| 확인 가능한 변경 | 변경 종류별 점검, Playwright 전환 점검, 수행한 검증과 남은 제한 구분 | [8.9 검증](/architecture/8-9/) |
