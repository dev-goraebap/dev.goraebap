이 절은 Webcraft 지침과 레퍼런스 키트를 만들고 고치며 내린 결정과 기각한 대안을 구조, 화면, 지침 운영으로 나누어 모읍니다. 규칙 절 본문에는 결정 날짜와 이력을 섞지 않습니다. 결정에 이른 경위(증상·원인·확인)는 그 변경의 커밋과 PR 본문에 남깁니다. 날짜나 판이 붙은 결정은 그 기록과 판 이력에서 확인한 것이고, 나머지는 지침 본문이 이유와 함께 밝힌 결정입니다.

개별 프로젝트가 내린 되돌리기 어려운 기술 선택은 그 프로젝트의 기록에, 지침과 다르게 정한 예외는 `AGENTS.md`의 프로젝트 규칙 표에 남깁니다. 프로젝트 정의서의 이 절은 그 기록에서 채웁니다.

## 9.1 구조

| 결정 | 내용 |
| :--- | :--- |
| 모듈형 모놀리스 출발 | 필요한 경계를 가진 모듈형 모놀리스에서 시작합니다. 서비스·큐·캐시·복제·추상화를 처음부터 두는 안은 구체적인 요구와 운영 비용이 확인되기 전에는 쓰지 않습니다. |
| 피처별 Facade 하나 | 피처가 제공하는 계약은 `XxxFacade` 하나로 모으고 전용 입력·결과는 `Param`·`Result`에 중첩합니다. 같은 피처를 QueryFacade·CommandFacade·ViewFacade로 나누는 안과, 소비 서비스와 Facade 사이에 의미 없는 중계 포트·어댑터를 두는 안은 기각했습니다. |
| 피처별 Service 하나 | 피처마다 `XxxService` 하나에 읽기·쓰기 메서드를 둡니다. `XxxQueryService`와 명령 서비스로 나누는 안은 기각하고, 읽기·쓰기 분리는 처리 경로로 지킵니다. 기존 QueryService는 그 피처를 고칠 때 합칩니다. |
| Spi 도입 조건 | Spi는 세 조건(소유 모듈의 불변식 검증에 필요, 자기 데이터로 판정 불가, 호출 인자로 전달 불가)을 모두 만족할 때만 둡니다. 편의 조회를 위한 Spi와 양방향 참조를 숨기려고 인터페이스를 늘리는 안은 기각했습니다. |
| 피처가 조회를 소유 | 화면 조회 포트 `XxxQuery`는 소유 서비스와 같은 피처에 1:1로 두고 구현은 package-private `JooqXxxQuery`에 둡니다. 여러 피처의 SQL을 공통 조회 저장소에 모으는 안과, 포트 전용 Row와 화면 DTO 사이에 값 복사만 하는 중간 타입은 기각했습니다. |
| 동기 결과는 Facade로 | Event는 업무 사건을 전달하는 데만 씁니다. 동기 호출 결과가 필요한 유스케이스를 이벤트로 우회하는 안은 기각했습니다. |
| 서버가 계약의 원본 | API를 바꾸면 OpenAPI·생성 클라이언트 타입·호출자를 같은 변경에서 맞춥니다. 전역 success/data 래퍼를 기본으로 두는 안은 기각하고 HTTP 상태 코드와 `application/problem+json`으로 표현합니다. |
| 서버는 프로젝트 하나, module과 shared (2026-11-17) | 백엔드는 `server/` 아래 Gradle 프로젝트 하나로 두고 빌드 파일도 하나, 실행 jar도 하나로 배포합니다. 기본 패키지는 `xyz.goraebap`이고, 조립(`ServerApplication`과 적용할 마이그레이션 묶음을 적는 `Migrations`)은 기본 패키지에 둡니다. 소스는 기술 기반만 두는 `xyz.goraebap.shared`와 컨텍스트를 두는 `xyz.goraebap.module`로 나눕니다. 모듈은 필요하면 모듈 그룹 폴더로 묶을 수 있으며, 이 저장소는 `module/foundation`(`user`, `file`, `notification`, `system`, `seed`, `realtime`, `search`, `mcp`)과 `module/workspace`(`project`, `issue`, `document`, `richbody`, `activity`) 둘로 묶습니다. 2026-11-16에는 Gradle 하위 프로젝트 셋(`foundation`, `workspace`, `app`)으로 나눴다가 하루 뒤 합쳤습니다. 하위 프로젝트 사이는 컴파일러가, 모듈 사이는 테스트가 지켜 경계를 지키는 장치가 둘이었는데, 모듈 사이의 규칙은 어차피 테스트로 지켜야 하므로 장치를 하나로 줄였습니다. 빌드 파일 셋과 테스트 지원 코드를 나눠 쓰는 설정도 사라졌습니다. 대신 참조 방향을 컴파일러가 아니라 테스트가 지키고, 다른 저장소가 받아 가는 단위가 폴더 둘에서 컨텍스트 맵의 그룹 목록으로 바뀝니다. 하위 프로젝트를 그대로 두는 안, 감싸지 않고 기본 패키지 바로 아래에 그룹과 `shared`를 나란히 두는 안(Spring Modulith의 기본 모양), `shared`를 다른 뿌리 패키지로 떼는 안(스캔 설정과 오류 기록기가 뿌리 둘을 알아야 하고 패키지 이름이 관례에서 벗어남)은 기각했습니다. 사용자가 결정했습니다. |
| 공통 모듈 그룹 이름은 foundation (2026-11-16) | 사용자·인증·알림·파일 같은 일반·지원 도메인을 담는 모듈 그룹의 이름을 `foundation`으로 합니다. `core`는 도메인 주도 설계에서 제품을 다르게 만드는 핵심 도메인(core domain)을 가리키므로 일반·지원 도메인에 붙이면 뜻이 거꾸로 읽혀 기각했습니다. `platform`은 뜻은 맞지만 사용자가 `foundation`을 골랐고, `common`과 `shared`는 유틸리티를 아무거나 넣는 자리처럼 읽혀 기각했습니다. |
| 기본 패키지는 xyz.goraebap (2026-11-16) | Java 기본 패키지를 도메인 goraebap.xyz를 뒤집은 Java 관례에 따라 `xyz.goraebap`으로 합니다. 그룹은 `xyz.goraebap.foundation`, `xyz.goraebap.workspace`, `xyz.goraebap.app`을 쓰며, 앞부분이 같아야 조립한 앱이 모든 그룹의 빈을 찾습니다. `dev.goraebap`은 goraebap.dev 도메인을 가진 것처럼 읽히고, `webcraft`는 지침 플러그인의 이름이라 제품 코드와 뜻이 섞여 기각했습니다. 사용자가 결정했습니다. |
| DB는 하나, 마이그레이션 기록은 묶음마다 (2026-11-17) | 모든 묶음이 업무 DB 하나(`app.db`)를 같이 쓰며 DB 연결과 트랜잭션 관리자도 하나입니다. 묶음은 지금 그룹(`foundation`, `workspace`)과 같으며 자기 마이그레이션 폴더와 자기 기록표를 가집니다. `foundation`은 `db/foundation`과 `flyway_history_foundation`, `workspace`는 `db/workspace`와 `flyway_history_workspace`를 쓰므로 묶음마다 `V1`부터 따로 세어도 부딪히지 않습니다. 조립의 `Migrations`가 적용할 묶음과 순서를 적으며, 서버가 뜰 때 기대는 순서대로 `foundation` 다음에 `workspace`를 적용합니다. 업무 DB의 jOOQ 생성물은 `xyz.goraebap.jooq` 한 패키지로 만들어 그룹 이름이 import에 들어가지 않습니다. 2026-11-16에는 하위 프로젝트마다 DB 파일을 따로 두기로 하고 그렇게 만들었다가 하루 뒤 되돌렸습니다. 트랜잭션 관리자가 둘이 되어 트랜잭션이 엉뚱한 DB에 걸리는 버그가 났고, 알림 하나를 보내려고 아웃박스가 필요해졌으며, 다른 DB를 함께 바꾸는 저장이 같이 되돌려지지 않고, 백업 시점이 다르면 파일 사이가 어긋났기 때문입니다. 모듈형 모놀리스를 다루는 자료들은 표를 모듈별로 나누는 것에서 시작하고 DB를 따로 두는 것은 부하가 다르거나 떼어 낼 계획이 있을 때 하라고 권합니다. 나중에 PostgreSQL로 옮기면 DB 하나 안의 스키마가 되므로 파일을 나눠서 생긴 복잡함은 가려는 곳에서는 필요 없는 것이었습니다. 하위 프로젝트마다 DB 파일을 따로 두는 안은 이 경위로 기각했고, 마이그레이션 기록표를 하나로 두는 안은 묶음을 다른 저장소가 받아 갈 때 버전 번호가 부딪혀 기각했습니다. 사용자가 결정했습니다. |
| 로그 DB는 따로 (2026-11-16) | `foundation`은 활동, 요청 수, 서버 오류 기록을 업무 DB와 다른 파일(`foundation-logs.db`)에 둡니다. 한 그룹 안에서도 생명주기가 다른 데이터는 파일을 나눕니다. 로그는 복제와 보관 기간이 업무 데이터와 다르고, 요청마다 쓰여 업무 저장과 쓰기 잠금을 다투며, 로그 파일을 쓰지 못해도 서버는 멈추지 않아야 하기 때문입니다. 로그를 `app.db`에 합치는 안은 기각했습니다. |
| 컨텍스트 사이에는 조인하지 않는다 (2026-11-17) | 다른 컨텍스트의 표는 SQL에서 언급하지 않습니다. 표시할 값과 판정은 Facade로 얻고, 걸러 내기·정렬·페이지 나누기처럼 한 쿼리 안에서 필요한 것은 주인이 내놓은 공개 뷰를 읽습니다. 공개 뷰는 주인의 마이그레이션에 정의하고 이름은 `_public`으로 끝나며, 지금 `project_public`, `project_key_public`, `activity_entry_public`, `user_public` 넷입니다. 문자열로 쓴 SQL로 표를 읽지 않으며 로그 DB를 통째로 백업하는 `VACUUM INTO` 하나만 예외입니다. `ContextMapTest`가 이 규칙을 지킵니다. 2026-11-16에는 하위 프로젝트 사이에만 이 규칙을 두었다가 같은 그룹 안의 컨텍스트 사이에도 똑같이 적용하도록 넓혔고, 다른 컨텍스트의 표를 조인하던 조회 다섯 파일(`issue`의 둘, `document`의 둘, `notification`의 하나)이 공개 뷰를 읽도록 바꿨습니다. 다른 컨텍스트의 표 구조에 묶이면 그쪽이 표를 바꿀 때 깨지지만, 공개 뷰는 주인이 표를 바꿔도 열을 지키는 계약이기 때문입니다. 같은 그룹 안에서는 조인을 허용하는 안은 그룹을 다시 나눌 때마다 조회를 고쳐야 해서 기각했고, 모두 Facade로만 읽는 안은 목록 조회에서 걸러 내기와 페이지 나누기를 한 쿼리로 할 수 없어 기각했습니다. 사용자가 결정했습니다. |
| foundation은 제품과 도메인을 모른다 (2026-11-16) | `foundation`은 제품 이름을 코드에 두지 않고 조립하는 앱이 설정 `app.product.name`으로 주며, 메일 제목, 푸시 제목, MCP 서버 이름, 에이전트 토큰의 접두사가 이 값을 씁니다. 역할은 `INSTANCE_ADMIN` 하나만 알고 다른 역할은 각 도메인이 `RoleSpi`로 내놓습니다. 에이전트에게 주는 MCP 안내문은 일반 규칙만 두고 제품의 안내문은 조립하는 앱이 `McpServerProfileSpi`로 넣습니다. 소속(부서, 팀)은 `AffiliationSpi`로 받으며 채우는 도메인이 조립에 없으면 비어 있습니다. 사용자 표에는 이름, 이메일, 상태만 두고 성별이나 퇴사일 같은 인사 정보는 그것을 다루는 도메인이 자기 표에 두며, 코드와 API에서 사람을 가리키는 말은 `user`와 `member`로 씁니다. `foundation`은 여러 제품이 받아 가는 코드이므로 한 제품의 이름이나 한 도메인의 개념이 들어 있으면 다른 제품이 받을 수 없기 때문입니다. 사용자가 결정했습니다. |
| 마이그레이션은 V1에서 새로 (2026-11-16) | `foundation`의 스키마는 `V1__schema.sql` 하나로 시작합니다. jOOQ의 DDL 파서가 다시 실행하지 못하는 색인과 일부 제약은 `[jooq ignore]` 표시 사이에 둡니다. 기존 제품의 마이그레이션 이력을 모듈별로 쪼개 순서대로 옮기는 안은 한 파일에 여러 모듈의 표가 섞인 마이그레이션을 손으로 나눠야 해서 오류가 나기 쉬워 기각했습니다. 이미 운영 중인 DB를 가진 제품이 `foundation`을 받을 때는 그 제품 쪽에서 "V1은 적용됨"으로 표시하는 이관이 따로 필요합니다. 사용자가 결정했습니다. |
| foundation 그룹은 자기 테스트로 혼자 돈다 (2026-11-17) | `foundation` 그룹의 통합 테스트는 `shared`와 `module/foundation`만 묶은 테스트용 서버에서 돌고, `workspace` 그룹의 테스트는 전체 서버에서 돕니다. 다른 그룹 없이 뜨는지 확인하기 위해서입니다. `foundation`만 받아 가는 저장소에서도 서버가 뜨는지 테스트로 확인하며, 컴파일 수준의 참조는 `ContextMapTest`가 보고 빈이 실제로 엮이는지는 이 테스트가 봅니다. |
| 그룹 사이 아웃박스는 두지 않는다 (2026-11-17) | DB를 따로 두던 하루 동안 DB마다 아웃박스를 만들었다가 DB를 합치면서 걷어 냈습니다. DB가 하나면 다른 그룹의 Facade 호출이 같은 트랜잭션에 묶이므로 알림 보내기 같은 일을 미뤄서 처리할 이유가 없습니다. 쓰는 곳이 없는 장치는 두지 않으며, 외부 서비스 호출처럼 커밋 뒤에 반드시 처리해야 하는 일이 생기면 그때 다시 만듭니다. 푸시 발송은 원래부터 자기 발송 기록(`PushOutbox`)을 갖고 있고 그대로 둡니다. 사용자가 결정했습니다. |
| shared는 하나 (2026-11-17) | 프로젝트가 하나가 되어 `shared`도 `xyz.goraebap.shared` 하나입니다. 기술 기반만 두며, 컨텍스트를 참조하지 않고 표를 읽지 않습니다(`ContextMapTest`). `realtime`, `search`, `mcp`는 컨트롤러와 확장점을 갖기 때문에 `shared`가 아니라 `foundation` 그룹의 컨텍스트로 둡니다. 같은 날 낮에는 하위 프로젝트마다 자기 `shared`를 두기로 했다가 하위 프로젝트를 없애면서 하나로 합쳤습니다. 사용자가 결정했습니다. |
| 모듈 그룹은 필요하면 묶는다 (2026-11-17) | 모듈은 필요하면 모듈 그룹 폴더로 묶을 수 있으며, 이 저장소는 `module/foundation`(`user`, `file`, `notification`, `system`, `seed`, `realtime`, `search`, `mcp`)과 `module/workspace`(`project`, `issue`, `document`, `richbody`, `activity`) 둘로 묶습니다. 그룹 폴더가 있다고 규칙이 생기지는 않으며, 그룹은 다른 저장소가 받아 갈 목록과 그림에 쓰입니다. 사용자가 결정했습니다. |
| 컨텍스트 맵을 파일로 두고 테스트가 지킨다 (2026-11-17) | 컨텍스트 구성은 `server/contexts.json`에 적으며, 13개 컨텍스트마다 패키지(`package`), 그룹(`group`), 하위 도메인 종류(`subdomain`: `generic`, `supporting`, `core`), 가진 표(`tables`), 내놓은 공개 뷰(`views`), 참조하는 컨텍스트(`uses`)를 적습니다. `ContextMapTest`가 이 파일을 읽어 모든 클래스가 컨텍스트나 `shared`에 속하는지, 코드의 참조와 `uses`가 같은지(코드에 있는데 적지 않았거나 적었는데 코드에 없으면 실패), 다른 컨텍스트가 패키지 바로 아래의 공개 계약만 쓰고 `application`·`domain`·`infrastructure` 안은 쓰지 않는지, `generic`·`supporting`·`core` 순서에서 자기보다 뒤의 것을 참조하지 않는지 지킵니다. 또한 표와 뷰마다 주인이 하나이고 맵의 표와 스키마의 표가 같은지, 컨텍스트가 남의 표를 읽지 않고 공개 뷰만 읽는지, `shared`가 컨텍스트를 모르고 표를 읽지 않는지, 문자열로 쓴 SQL로 표를 읽지 않는지(로그 DB를 통째로 백업하는 `VACUUM INTO` 하나만 예외)도 함께 검사합니다. 하위 도메인 종류와 그룹은 판단이므로 사람이나 에이전트가 보기에 틀렸거나 억지스러우면 고칩니다. 테스트는 경계만 지키고 분류가 옳은지는 판단하지 않으므로 분류를 고치기 비싼 곳에 넣지 않아, 표 이름·API 주소·jOOQ 생성 패키지에는 그룹 이름이 없고 마이그레이션 폴더(`db/foundation`, `db/workspace`)와 기록표 이름(`flyway_history_foundation`, `flyway_history_workspace`)에만 그룹 이름이 있습니다. Spring Modulith 라이브러리를 쓰는 안은 하위 도메인 종류와 표의 주인을 다루지 않고 `module`과 `shared`로 감싸는 구조가 기본값이 아니라 기각했습니다. 사용자가 결정했습니다. |
| 도메인이 정하는 이름은 foundation이 열어 둔다 (2026-11-17) | 알림이 가리키는 대상의 종류(`Subject`의 `type`)는 열거형이 아니라 도메인이 주는 이름으로 두며 `foundation`은 그 이름에 뜻을 두지 않습니다. 문서를 공유할 수 있는 묶음(부서, 팀)은 `workspace`가 확장점(`DocumentGroupSpi`)을 열고 그것을 다루는 도메인이 채우며, 채우는 도메인이 조립에 없으면 문서는 프로젝트와 사람에게만 공유됩니다. 어떤 역할을 가진 사람을 묻는 일은 표를 읽지 않고 `UserFacade`로 합니다. `foundation`과 `workspace`는 어떤 도메인이 함께 조립될지 모르기 때문입니다. |
