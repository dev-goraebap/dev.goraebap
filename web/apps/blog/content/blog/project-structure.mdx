프로젝트가 작을 때는 폴더 구조가 거의 문제가 되지 않습니다. 파일이 늘어나고 기능이 서로 얽히기 시작하면 그때부터 매번 같은 질문을 하게 됩니다. 이 파일은 어디에 둬야 하지? 이 패키지가 저 패키지를 불러도 되나? 저는 이 질문에 그때그때 답하지 않으려고 여러 해 동안 구조를 바꿔 보았습니다. 이 글은 그 과정에서 남은 원칙과, 지금 프론트엔드에 FSD(Feature-Sliced Design)를 쓰고 백엔드를 기능 모듈로 나누는 이유를 정리한 것입니다. 2025년 10월에 옛 블로그에 쓴 세 편의 글을 지금의 생각으로 다시 묶었습니다.

## 타입 기준과 기능 기준

처음 배운 구조는 controllers, services, repositories처럼 역할(타입)로 폴더를 나누는 방식이었습니다. 이 방식에는 분명한 장점이 있습니다. 폴더만 봐도 요청이 어떤 계층을 거치는지 보이고, 컨트롤러 → 서비스 → 저장소라는 한 방향 흐름이 폴더 구조 자체로 드러납니다.

문제는 프로젝트가 커질 때 생깁니다. services 폴더 안은 결국 UserService, PostService, OrderService처럼 기능별 파일로 채워지고, 그 서비스들끼리도 서로 부릅니다. 어떤 서비스는 핵심 규칙을 맡고 어떤 서비스는 여러 서비스를 엮는데, 이 차이가 폴더 어디에도 드러나지 않습니다. 투두 리스트가 아닌 이상 실무 프로젝트를 담기에는 너무 평평한 구조였습니다.

반대쪽은 user, post, order처럼 기능(도메인)으로 폴더를 나누는 방식입니다. 한 기능을 고칠 때 관련 파일이 한곳에 모여 있어 응집도가 높고, 공개할 것만 드러내는 캡슐화도 쉽습니다. 대신 규칙이 저절로 생기지 않습니다. 기능 폴더끼리는 결국 서로를 참조하게 되고, 완전히 떼어 내려면 코드를 중복해야 합니다. 폴더 안에서 계층도 보이지 않습니다.

두 방식의 단점을 다 겪어 본 뒤에도 저는 기능 기준이 더 좋았습니다. 단점이 더 구체적으로 보였던 것은 그만큼 오래 쓰면서 부딪혔기 때문입니다. 그래서 고민은 "어느 쪽이 맞나"에서 "기능 기준을 쓰면서 규칙을 어떻게 세우나"로 옮겨 갔습니다.

## 같은 줄에 다른 기준을 섞지 않는다

기능 기준으로 시작한 프로젝트는 대개 이런 모양이 됩니다. 처음에는 user, post, order 같은 기능 폴더만 있다가, 요구사항을 처리하다 보면 common, database, utils 같은 폴더가 같은 줄에 생깁니다. 이때부터 구조가 말을 하지 않습니다. 같은 높이의 폴더가 어떤 것은 업무 기준이고 어떤 것은 기술 기준이라, 새 파일을 어디에 둘지 폴더만 보고는 알 수 없습니다.

그래서 첫 번째 원칙은 **같은 높이의 폴더는 같은 기준으로 나눈다**입니다. 업무 기능은 한 묶음으로, 업무를 모르는 기술 코드(설정, 유틸, 데이터베이스 연결)는 shared 같은 다른 묶음으로 올립니다. 이렇게 묶어 두면 "여기는 업무를 모르는 영역"이라는 경계가 한 줄로 생깁니다. 나중에 여러 개발자와 이 주제로 토론하면서도, 계층을 먼저 나누든 도메인을 먼저 나누든 **루트에서 업무 관심사와 업무 밖 관심사를 가르는 것**만은 양보할 수 없다는 생각이 오히려 굳어졌습니다.

## 참조는 한 방향으로

두 번째 원칙은 묶음 사이의 참조 방향입니다. 묶음에 높낮이를 두고, 높은 묶음은 낮은 묶음을 부를 수 있지만 반대는 안 됩니다. 같은 묶음 안의 참조는 높이에 따라 다르게 봅니다. 낮은 묶음(shared)은 더 내려갈 곳이 없으니 안에서 서로 부르는 것이 자연스럽습니다. 반대로 업무가 몰리는 높은 묶음에서 폴더끼리 서로 부르기 시작하면 복잡도가 빠르게 올라갑니다.

이 문제가 까다로운 이유는 클래스 수준과 패키지 수준이 다르게 보이기 때문입니다. UserService가 PostService를 부르고 그 반대는 없다면 클래스로는 한 방향입니다. 하지만 엔티티 관계, DTO, 다른 서비스가 user 폴더의 저장소를 쓰는 일이 겹치면 패키지로는 user ↔ order처럼 양쪽으로 엮입니다. 저는 높은 묶음 안에서 이런 양방향이 보이면 구조를 바꿀 신호로 봤습니다.

옛 프로젝트에서는 이 신호가 올 때마다 묶음을 하나씩 늘렸습니다. 여러 곳이 함께 쓰는 엔티티와 저장소를 domain으로 내리고, 두 진입점이 같이 쓰는 유스케이스를 features로 빼고, 데이터베이스 구현을 infra로 떼어 냈습니다. 처음부터 다 갖추지 않고 필요할 때 늘렸다는 점은 지금도 맞다고 생각합니다. 다만 이 방식은 묶음이 늘수록 한 기능의 흐름이 여러 묶음에 흩어집니다.

## 물리적 의존성을 먼저 본다

그 흩어짐이 토론에서 가장 먼저 나온 비판이었습니다. "한 도메인의 기능이 여러 레이어에 나뉘어 있어서 흐름을 보려면 여러 폴더를 오가야 한다." 또 하나는 "API 요청·응답 DTO는 프레젠테이션 한곳에 모아야 하지 않나"였습니다.

두 비판 모두 맞는 말이었고, 결국 무엇을 먼저 보느냐의 차이라는 결론에 이르렀습니다. 저는 **패키지가 실제로 무엇을 import하는지(물리적 의존성)**를 먼저 봅니다. 그래서 낮은 묶음이 높은 묶음의 DTO를 가져다 쓰는 구조는 받아들이지 않고, 각 묶음이 자기에게 필요한 입출력 타입을 스스로 가집니다. 반대편은 아키텍처 개념상의 자리(개념적 의존성)를 먼저 보고, 그래서 DTO를 API 계약이라는 안정된 자리에 모읍니다. 둘 다 맞지만, 개념을 먼저 보는 쪽은 사람마다 해석이 달라지기 쉽습니다. 저는 팀원이나 AI가 해석 없이 따를 수 있는 쪽, 즉 import 방향처럼 검사로 확인할 수 있는 규칙을 고릅니다.

이 기준은 조회에서 특히 쓸모가 있습니다. 생성·수정·삭제는 대개 도메인 하나의 경계 안에서 끝나지만, 화면 하나를 그리는 조회는 여러 도메인의 데이터를 섞습니다. "A는 B를 불러도 된다" 같은 가로 규칙을 늘리면 예외가 끝없이 생기니, 위에서 아래로만 부른다는 세로 규칙 하나로 단순하게 두는 편이 오래갑니다.

## 지금의 답: 프론트엔드는 FSD

프론트엔드에서는 이 고민의 상당 부분을 FSD가 먼저 풀어 두었습니다. FSD는 높낮이가 있는 층(layer), 층 안의 기능 단위(slice), 기술 역할(segment)을 나누고, 위층은 아래층만 부르며 같은 층의 slice끼리는 부르지 않는다는 규칙을 둡니다. 제가 기능 기준을 쓰면서 세우려던 두 원칙이 이미 방법론으로 정리되어 있었던 셈입니다. 업무를 모르는 shared가 맨 아래에 있는 것도 같습니다. FSD를 처음 익힌 뒤로는 코드를 보는 방식 자체가 바뀌었고, 백엔드 구조를 고민할 때도 이 용어를 빌려 썼습니다.

여기에 실무 기준을 두 가지 더했습니다. pages 폴더를 주소와 1:1로 맞춰 폴더만 보고 앱의 주소를 알 수 있게 하고, widgets·features·entities는 처음부터 만들지 않고 재사용이 확인될 때만 선택적으로 꺼내 씁니다. 실제 규칙은 [프론트엔드 디렉토리 구조](../frontend/reference/directory-structure/index.md)에 있습니다.

## 지금의 답: 백엔드는 기능 모듈

백엔드는 Spring으로 시작해 프론트엔드와 언어를 맞추려고 NestJS로 옮겼다가, 다시 Spring으로 돌아왔습니다. 그동안 위에서 말한 묶음(app·features·domain·infra·shared)을 먼저 나누는 구조를 써 왔지만, 지금은 토론에서 받은 첫 번째 비판을 받아들였습니다. **기능(모듈)을 먼저 나누고, 그 안에서 계층을 나눕니다.** 한 기능의 흐름이 한 폴더 안에 모이고, 모듈 안은 application·domain·infrastructure로 나뉩니다.

그래도 두 원칙은 그대로입니다. 루트에서는 업무를 모르는 shared와 업무 모듈을 가르고, 모듈 사이는 한 방향으로만 부릅니다. 이걸 지키려고 모듈이 밖에 내놓는 계약을 피처마다 Facade 하나로 모으고, 피처마다 Service도 하나만 둡니다. 다른 모듈의 내부 패키지는 직접 부르지 않고, 역방향 확장이 꼭 필요할 때만 조건을 따져 Spi를 둡니다. 물리적 의존성을 먼저 본다는 생각도 남아서, 모듈 경계는 사람의 기억이 아니라 테스트가 지킵니다. 규칙은 [디렉토리·패키지 구조](../backend/reference/directory-structure/index.md), [구성 요소와 실행 흐름](../backend/reference/components-and-flow/index.md), [데이터 접근](../backend/reference/data-access/index.md)에 있습니다.

## 고르지 않은 것들

클린 아키텍처와 헥사고날 아키텍처의 이론적인 깔끔함에 끌려 데모 프로젝트를 여러 번 만들어 봤습니다. 하지만 그 완성도를 실제 프로젝트에 그대로 옮기려 할 때마다 복잡도와 실용성 사이의 틈에 부딪혔습니다. 제가 처음부터 완벽한 구조를 강요하지 않고 필요할 때 경계를 늘리는 쪽을 고르는 이유입니다. 반대로 타입 기준 구조는 작은 프로젝트라면 지금도 충분히 좋은 선택이라고 생각합니다. 다만 커질 것이 보이는 프로젝트라면 처음부터 기능 기준으로 시작하는 편이 나중의 이사를 줄입니다.

AI가 코드를 대신 써 주는 지금은 이 원칙이 오히려 더 중요해졌습니다. 코드는 빠르게 쌓이지만, 어디에 두고 어디를 부를지는 여전히 누군가 정해 줘야 합니다. 폴더 기준과 참조 방향을 규칙으로 적어 두면 사람도 AI도 같은 자리에 같은 코드를 둡니다.
