프론트엔드 프로젝트를 새로 열 때마다 `src/` 아래를 어떻게 나눌지는 늘 비슷한 고민으로 돌아옵니다. 처음 몇 주 동안은 어떤 구조든 크게 불편하지 않지만, 화면과 상태가 쌓이기 시작하면 “이 파일은 어디에 두어야 하지?”, “저 폴더의 컴포넌트를 여기서 가져다 써도 되나?” 같은 질문이 반복됩니다.

돌아보면 지금의 FSD(Feature-Sliced Design) 기반 구조에 닿기까지 꽤 여러 번 폴더를 뒤집어 보았습니다. 역할별 폴더에서 출발해 아토믹 디자인을 거쳤고, FSD를 만나면서야 그동안 막연하게 불편했던 지점들을 비로소 말로 정리할 수 있었습니다.

## 역할별 폴더로 시작했을 때의 불편함

프론트엔드를 처음 시작할 때 가장 자연스럽게 만들게 되는 구조는 `src/components`, `src/store`, `src/hooks`, `src/utils`처럼 **파일의 기술적 역할**로 폴더를 나누는 방식입니다.

```text
src/
  components/
  pages/
  store/
  hooks/
  api/
  utils/
```

프로젝트가 작을 때는 이만큼 단순하고 빠른 구조도 드뭅니다. 훅은 `hooks/`, 전역 상태는 `store/`, 컴포넌트는 `components/`에 넣으면 되니 처음에 고민할 일이 거의 없습니다.

다만 기능이 늘어나면서 구조 자체에 **참조 방향에 대한 책임이 없다**는 점이 조금씩 부담으로 다가왔습니다. `components/` 안의 어떤 파일이 `store/`를 직접 부르고, `hooks/` 안의 파일이 다른 도메인의 `api/`와 `components/`를 끌어다 써도 폴더 구조만 봐서는 무엇이 어색한 의존성인지 잘 드러나지 않았습니다. 화면 하나를 고치려고 하면 `pages`, `components`, `hooks`, `store`, `api`를 계속 오가야 했고, 시간이 지날수록 “어디서 어디를 부르면 안 되는지”는 결국 사람의 기억에만 의존하게 되었습니다.

## 아토믹 디자인을 써 보며 배운 것과 부딪힌 벽

그다음으로 한동안 적용해 본 방식이 **아토믹 디자인(Atomic Design)**이었습니다. 브래드 프로스트(Brad Frost)가 화학의 원소 조합에 빗대어 제안한 방법론으로, UI를 다섯 단계의 시각적 단위로 나누어 작은 조각부터 화면까지 조립해 나가는 접근입니다.

```text
atoms (원자)       → 버튼, 입력창, 레이블처럼 더 쪼갤 수 없는 기본 요소
molecules (분자)   → 검색창 + 검색 버튼처럼 원자를 묶은 단순 조합
organisms (유기체) → 헤더, 카드 목록처럼 독립된 UI 구역
templates (템플릿) → 실제 데이터 없이 화면 뼈대만 잡은 레이아웃
pages (페이지)     → 템플릿에 실제 데이터를 채운 완성 화면
```

아토믹 디자인을 써 보며 분명히 얻은 점이 있었습니다. UI 컴포넌트를 무작정 한 폴더에 쌓지 않고 “작은 부품이 큰 부품으로 조립된다”는 계층 의식이 생겼고, 덕분에 버튼이나 입력창 같은 기본 UI를 디자인 시스템 단위로 분리해 바라보는 눈이 트였습니다.

하지만 실무 웹 애플리케이션 전체의 폴더 구조로 끌고 가다 보니 두 가지 벽에 자주 부딪혔습니다.

첫 번째는 **분류 기준의 모호함**이었습니다. 버튼이 `atoms`라는 데는 누구나 동의하지만, 툴팁이 붙은 아이콘 버튼이나 검색 필터 바가 `molecules`인지 `organisms`인지는 사람마다, 심지어 어제의 나와 오늘의 내가 다르게 판단하기 일쑤였습니다. 코드를 짜기 전에 “이걸 분자에 넣을까, 유기체에 넣을까”를 고민하는 시간이 생각보다 자주 쌓였습니다.

두 번째가 더 근본적인 한계였습니다. 아토믹 디자인은 **UI 컴포넌트의 조립 단위**를 다루는 모델이지, 앱 전체의 **상태·API·비즈니스 로직**을 배치하는 모델이 아니었습니다. 컴포넌트 폴더는 다섯 단계로 나뉘어 있는데, 정작 서버 통신, 인증 상태, 도메인 계산 로직은 여전히 예전처럼 `store/`나 `hooks/`에 따로 떠돌거나 `organisms/` 안쪽에 뒤섞이기 쉬웠습니다.

## FSD를 만나고 비로소 언어화된 불편함

아토믹 디자인의 한계를 느끼던 시점에 접한 것이 **Feature-Sliced Design(FSD)**이었습니다.

FSD를 읽으면서 가장 크게 와닿았던 지점은, 그동안 접해 본 프론트엔드 구조론 가운데 **처음으로 패키지의 우선순위를 ‘기능(비즈니스) 관점’에서 바라보고 있었다**는 점이었습니다. 역할별 폴더는 파일의 문법적 종류(`components`, `hooks`, `store`)를 우선했고, 아토믹 디자인은 화면에 보이는 UI의 크기와 조립 단계를 우선했습니다. 반면 FSD는 `app → pages → widgets → features → entities → shared`라는 수직 레이어 아래에서, 먼저 **비즈니스 책임과 기능 단위(슬라이스)**로 코드를 묶고, 그 안에서야 `ui`, `model`, `api` 같은 기술적 역할(세그먼트)을 나눕니다.

이 관점을 접하고 나서야 예전 구조들에서 막연하게 느끼던 불편함이 무엇이었는지 하나씩 정의를 내릴 수 있게 되었습니다.

- 역할별 폴더가 답답했던 이유는 단순히 파일이 많아서가 아니라, **누가 누구를 참조해도 되는지 경계가 없었고 함께 바뀌는 기능 코드가 여러 폴더에 찢어져 있었기 때문**이었습니다.
- 아토믹 디자인이 앱 전체 구조로 버거웠던 이유는 방법론이 나빠서가 아니라, **UI의 시각적 계층과 비즈니스 의존성 계층을 같은 폴더 트리에 억지로 겹쳐 놓으려 했기 때문**이었습니다.

FSD가 제시하는 단방향 레이어 규칙, 같은 층 슬라이스 간의 격리, 그리고 `index.ts`(공개 API)를 통한 캡슐화는 이 두 문제를 한꺼번에 짚어 주었습니다. 새로운 기법을 하나 더 외웠다기보다, 그동안 손에 잡히지 않던 구조적 문제들을 설명할 어휘를 얻은 기분에 가까웠습니다.

## FSD v2.1이 보여 준 방향 전환

FSD를 계속 따라가며 한 번 더 고개를 끄덕이게 된 지점은 **v2.0에서 v2.1로 넘어오며 달라진 강조점**이었습니다.

예전 v2.0 시절의 FSD는 앱을 처음부터 잘게 쪼개 대부분의 코드를 `features`와 `entities`에 배치하고, `pages`는 이를 조립만 하는 얇은 껍데기로 두는 분위기가 강했습니다. 막상 그렇게 따라 해 보면 한 화면에서만 쓰이는 기능까지 억지로 `features`에 떼어 놓게 되고, 코드 흐름을 따라가려다 폴더만 여럿 오가는 피로가 쌓이기 쉬웠습니다.

v2.1에서는 이 지점을 정면으로 손봅니다. 여러 페이지에 걸친 흐름을 담던 `processes` 레이어는 경계만 흐린다는 이유로 공식 폐기되었고, 사고방식 자체가 **Pages-First**로 옮겨 갔습니다. 화면에 종속된 UI·폼·데이터 로직은 우선 해당 `pages` 슬라이스 안에 두고, 실제로 여러 곳에서 재사용되는 시점에만 `features`나 `entities`로 내리라는 쪽으로 방향을 잡은 것입니다. 공개 API에서도 `export *` 같은 와일드카드 재내보내기나 `shared/` 전체를 한 파일에 몰아 넣는 거대 배럴 파일을 피하고, `shared`에 비즈니스 로직을 섞지 말라는 현실적인 경계들이 훨씬 분명해졌습니다.

이 변화가 좋았던 이유는, FSD가 이론의 완결성에 집착하기보다 실제 프로젝트에서 생기는 과도한 분리와 탐색 피로를 스스로 인정하고 덜어내는 쪽으로 진화하고 있었기 때문입니다.

## 백엔드 설계에까지 번진 예상 밖의 영감

흥미로웠던 점은, FSD에서 얻은 시선이 프론트엔드에만 머물지 않고 **간접적으로 백엔드 패키지 설계를 바라보는 눈까지 바꾸어 놓았다**는 것입니다.

당시 백엔드 쪽에서는 클린 아키텍처의 개념을 코드로 옮기려고 헥사고날 아키텍처 스타일의 폴더 구조를 적용해 보며 꽤 진땀을 빼고 있었습니다. 이론상으로는 깔끔해 보이는데, 실제 코드에 옮겨 보면 클린 아키텍처가 말하려는 의존성 방향과 폴더 구조가 자연스럽게 맞물리지 않는 구간이 자주 생겼습니다.

물론 백엔드에 FSD의 레이어 구조를 그대로 옮겨 쓰는 것은 성격상 크게 맞지 않습니다. 서버는 화면 조립보다 바운디드 컨텍스트와 트랜잭션 경계가 중심이기 때문입니다. 그럼에도 FSD 문서를 읽으며 두 가지 면에서 적지 않은 영감을 받았습니다.

하나는 **폴더 구조의 배치 자체로 의존성 방향을 표현하려는 태도**였습니다. 머릿속의 아키텍처 다이어그램에만 의존 규칙을 두지 않고, 디렉토리의 높낮이와 공개 진입점만 봐도 “여기는 어디까지 참조할 수 있는 곳인지”가 물리적으로 드러나게 설계하려는 접근이 인상 깊었습니다.

다른 하나는 **규칙의 예외를 다루는 방식**이었습니다. FSD 역시 “같은 레이어의 슬라이스끼리는 서로 참조하지 않는다”는 강한 원칙을 세우지만, 실무에서 `entities` 사이의 도메인 관계처럼 원칙만으로 풀기 어려운 지점이 생긴다는 사실을 숨기지 않습니다. 공식 문서에서 크로스 임포트 예외를 다루기 위해 `@x` 표기법 같은 장치를 제안하고 토론하는 글을 읽으며 생각이 많이 바뀌었습니다. 어떤 아키텍처 규칙이든 100% 완벽할 수는 없으며, 중요한 것은 예외가 없는 척하는 규칙을 만드는 것이 아니라 **예외가 불가피할 때 그것을 어떤 경계와 약속으로 통제할 것인가**를 고민하는 쪽에 가깝다는 걸 배웠습니다.

## 지금의 기준으로 남긴 것

돌아보면 역할별 폴더는 작은 앱에서 여전히 가볍고 빠른 출발점이고, 아토믹 디자인 역시 디자인 시스템이나 순수 UI 컴포넌트를 바라볼 때는 유효한 시선입니다. 다만 제품 기능이 계속 붙는 웹 앱을 관리할 때는, **기능 중심으로 패키지를 묶고 폴더 배치로 의존성을 드러내는 FSD의 기본 원칙**이 지금까지 써 본 기준 가운데 가장 설득력이 높았습니다.

지금 이 사이트에서 정리하는 프론트엔드 구조 역시 공식 FSD v2.1의 레이어 기준을 그대로 바탕으로 삼되, `pages`를 URL 트리와 맞추는 습관만 더해 쓰고 있습니다. 구체적인 레이어 규칙과 React·Angular별 적용 방식은 [디렉토리 구조](../reference/directory-structure/index.md)에, 실제 작업 순서는 [화면·슬라이스 추가](../playbooks/new-page-and-slice/index.md)에 정리해 두었습니다.
