목록에서 항목을 눌러 상세를 보거나 새 글을 작성하는 흐름을 설계할 때, 데스크톱과 웹의 기본 특성 사이에서 자주 고민에 빠지게 됩니다.

항목을 누를 때마다 아예 새 페이지로 이동해 버리면 구현은 단순하고 주소도 깔끔합니다. 새로고침을 해도, URL을 복사해 동료에게 보내도 그대로 열립니다. 그런데 데스크톱에서 필터를 여러 개 걸고 수십 줄짜리 목록을 훑어보는 상황에서는 페이지 전체가 바뀔 때마다 맥락이 끊기는 느낌이 듭니다. 항목을 잠깐 확인하고 닫았을 뿐인데 목록이 다시 그려지거나 보던 스크롤 위치를 잃어버리는 일도 흔합니다.

반대로 목록 위에 모달이나 사이드 패널을 띄워 해결하려 하면 데스크톱 체감은 한결 가벼워집니다. 하지만 모달 상태를 컴포넌트의 `selectedId` 같은 로컬 상태로만 들고 있으면 곧 다른 불편함이 따라옵니다.

## 로컬 모달만 썼을 때 놓치게 되는 것들

모달에 고유한 URL이 없을 때 가장 먼저 아쉬워지는 것은 **공유와 새로고침**입니다. 모달을 열어 둔 채로 주소를 복사해 전달하면 상대방에게는 여전히 빈 목록 화면만 열립니다. 작업 중에 실수로 새로고침을 누르면 보고 있던 상세나 검색 결과가 흔적도 없이 닫혀 버립니다.

브라우저의 **뒤로가기 동작**도 어색해지기 쉽습니다. 사용자는 모달을 닫으려고 뒤로가기를 눌렀는데 모달이 닫히는 대신 이전 페이지로 튕겨 나가 버립니다. 그렇다고 데스크톱 모달을 모바일 화면에 그대로 우겨 넣으면 좁은 화면 위에 바텀시트나 작은 대화상자가 겹치면서 스크롤과 키보드 포커스가 꼬이기 시작합니다.

결국 한쪽은 “목록 맥락 유지”를 얻고 “웹의 주소 계약”을 잃었고, 다른 한쪽은 “주소 계약”을 얻고 “목록을 훑는 리듬”을 잃고 있었습니다.

## 주소는 대상으로, 표현은 환경에 따라

이 둘을 함께 풀기 위해 정착한 방식이 **라우팅 마스크(Route Masking)**를 결합한 Routed Modal 패턴입니다. 출발점은 단순합니다. **상세·작성·수정·전역 검색처럼 독립된 의미를 가진 화면은 무조건 자기만의 실제 URL과 페이지를 원본으로 둔다**는 원칙입니다.

그 위에 화면을 여는 방식만 환경에 따라 나눕니다.

- **데스크톱 목록에서 클릭할 때**는 목록 화면을 그대로 둔 채 위에 대화상자를 띄우되, 브라우저 주소창에는 대상의 실제 주소(`/items/42`)를 마스킹해 보여 줍니다. 내부적으로는 목록 주소에 패널 쿼리(`?panel=/items/42`)를 붙여 목록 상태를 유지합니다.
- **링크를 직접 열어 들어오거나 새로고침을 누를 때**는 마스크를 풀고 대상의 독립 페이지로 곧바로 엽니다. 주소를 복사해 보내도 받는 사람 화면에서 깨지지 않습니다.
- **휴대폰 폭에서 열 때**는 처음부터 마스킹을 끄고 일반 페이지 이동으로 대상 화면 전체를 엽니다. 덕분에 모바일에서는 브라우저 뒤로가기만으로 자연스럽게 목록으로 돌아옵니다.

이렇게 나누고 나니 데스크톱의 빠른 탐색감과 웹의 고유 주소 원칙을 따로따로 구현하지 않고 같은 화면 컴포넌트 하나로 엮을 수 있게 되었습니다.

## 막상 구현해 보며 다듬은 세 가지 경계

아이디어 자체는 명쾌해 보였지만, 실제 앱에 올려 써 보면서 예상치 못한 경계 사례를 꽤 만났습니다.

첫 번째는 **대화상자 안에서의 이동과 닫기 의미**였습니다. 목록 위 모달에서 상세를 열었다가 수정 화면으로 넘어가고, 다시 다른 관련 항목을 눌렀을 때 닫기 버튼이나 `Esc`를 누르면 어디로 가야 할까요. 처음에는 일반 히스토리 `push`로 쌓았더니, 닫기 버튼을 눌러도 모달이 안 닫히고 직전 상세로만 한 걸음씩 되돌아가 답답했습니다. 이후로는 대화상자 안에서 다른 대상으로 바꿀 때는 같은 마스킹 이력을 `replace`하고, 닫기·배경 클릭·`Esc`는 내부 이동 횟수와 상관없이 대화상자 전체를 닫아 처음 열었던 목록 조건과 스크롤로 돌아가게 정리했습니다.

두 번째는 **크게 보기 전환과 입력 초안 보존**이었습니다. 작성 모달에서 본문을 한참 적다가 화면이 좁게 느껴져 “페이지로 열기”를 눌렀을 때, 모달 컴포넌트가 언마운트되면서 입력해 둔 초안이 같이 날아가 버리는 문제가 있었습니다. 그래서 초안은 개별 모달이나 페이지 컴포넌트보다 수명이 긴 **라우터 상위 초안 저장소**에 두기로 했습니다. 그렇게 경계를 한 단계 올리고 나서야 크게 보기 전환이나 창 폭이 모바일로 줄어드는 순간에도 제목과 본문이 끊기지 않고 이어졌습니다.

세 번째는 **어디까지 마스킹을 쓸 것인가**였습니다. 이름 바꾸기나 폴더 생성처럼 굳이 독립된 URL을 공유할 일이 없는 짧은 확인 양식까지 억지로 라우팅 마스크에 넣으면 오히려 라우트 표만 복잡해졌습니다. 반대로 리소스의 상세·생성·수정이나 전역 검색처럼 주소를 공유하거나 새로고침할 수 있어야 하는 화면에만 마스킹을 적용하는 쪽이 관리 부담이 적당했습니다.

## 지금의 기준으로 남긴 것

모든 리소스를 Routed Modal로 열 필요는 없습니다. 목록과 상세를 나란히 보며 빠르게 오가는 화면은 List-Detail 중첩 라우트가 더 잘 어울리고, 흐름이 길고 독립적인 화면은 처음부터 Drill-down 페이지 이동이 더 자연스럽습니다.

다만 목록 위 대화상자를 쓰기로 선택한 화면이라면, 로컬 상태만으로 모달을 띄우기보다 **실제 페이지 주소를 원본으로 두고 데스크톱에서만 목록 위에 마스킹해 얹는 방식**이 지금까지 써 본 가운데 가장 덜 불편했습니다. 세부적인 리소스 패턴별 주소 규칙과 React·Angular 구현 방식은 [라우팅과 화면 전환](../reference/routing/index.md)에 정리해 두었습니다.
