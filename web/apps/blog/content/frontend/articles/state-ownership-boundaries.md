프론트엔드 앱의 규모가 커지기 시작하면 자연스럽게 “상태 관리를 어떤 도구로 통일할까”라는 질문에 닿게 됩니다. 예전에는 전역 스토어 라이브러리 하나를 정하고 로그인 사용자 정보, 서버에서 받아 온 목록, 현재 선택된 필터, 심지어 모달이 열려 있는지 여부까지 모두 한 저장소에 넣어 관리하던 시기가 있었습니다.

모든 상태를 한곳에 모아 두는 방식에도 분명한 장점이 있습니다. 어떤 화면에서든 필요한 값을 바로 꺼내 쓸 수 있고, 개발자 도구 한 창에서 앱 전체의 스냅샷을 시간 순서대로 훑어볼 수 있습니다. 초반에는 규칙도 단순해서 “전역으로 쓸 것 같으면 일단 스토어에 넣자”는 판단이 꽤 빠르게 먹히곤 했습니다.

## 한 저장소에 섞였을 때 반복되던 불편함

기능이 쌓이면서 불편함이 드러난 지점은 도구 자체의 성능보다 **서로 성격이 다른 데이터의 수명을 한 곳에 억지로 맞출 때**였습니다.

가장 먼저 부딪힌 문제는 **서버 데이터와 화면 초안의 충돌**이었습니다. 상세 화면에 들어왔을 때 서버에서 받아 온 제목과 본문을 폼 상태나 스토어에 복사해 두고 편집을 시작하는 패턴은 흔합니다. 그런데 사용자가 제목을 고치는 도중에 탭을 전환했다 돌아오거나 백그라운드 재조회가 돌면, 새로 도착한 서버 응답이 작성 중이던 입력을 조용히 덮어쓰는 일이 생겼습니다. 반대로 저장 요청을 보낸 뒤 응답이 오기 전에 한 글자를 더 입력했는데, 늦게 도착한 이전 저장 응답이 폼을 초기화해 버리는 경우도 겪었습니다.

비슷한 피로는 **목록 필터와 뒤로가기**에서도 반복되었습니다. 검색어와 정렬 조건을 전역 스토어나 컴포넌트 로컬 상태에만 두면, 상세 화면에 들어갔다 뒤로 돌아왔을 때 조건이 날아가거나 새로고침 한 번에 첫 페이지로 되돌아갑니다. 주소를 동료에게 공유해도 상대방 화면에는 필터가 전혀 걸려 있지 않은 목록이 열립니다.

여기에 **계정이나 워크스페이스 전환**까지 겹치면 관리 비용이 급격히 올라갔습니다. 로그아웃할 때 어떤 스토어 슬라이스를 비워야 하는지 매번 목록을 챙겨야 했고, 하나라도 빠뜨리면 이전 계정의 캐시가 잠깐 화면에 비치는 아찔한 버그로 이어지곤 했습니다.

## “어디에 저장할까”보다 “누가 원본을 소유할까”

이 문제들을 하나씩 뜯어보면서, 상태 관리에서 중요한 질문은 “어떤 라이브러리를 쓸까”보다 **“이 값의 원본(Source of Truth)은 누구인가”**에 가깝다고 느끼게 되었습니다. 성격이 다른 값을 같은 바구니에 넣지 않고 소유자를 셋으로 나누고 나서야 많은 동기화 코드가 자연스럽게 줄어들었습니다.

- **서버가 원본인 값**은 클라이언트 스토어에 복제하지 않고 서버 상태 캐시 계층에만 둡니다. 목록·상세·세션 정보는 캐시가 수명과 재조회, 계정 전환 시 전체 초기화를 일괄로 맡는 쪽이 훨씬 안전했습니다.
- **탐색과 조건을 표현하는 값**은 라우터가 검증하는 URL에 맡깁니다. 확정된 필터, 정렬, 페이지 번호, 선택 탭을 URL이 소유하면 새로고침과 뒤로가기, 링크 공유를 따로 구현할 일이 거의 사라집니다.
- **아직 확정되지 않은 임시 값**만 컴포넌트나 슬라이스의 로컬 UI 상태에 둡니다. 저장 전 입력 초안, 적용 버튼을 누르기 전의 필터 선택, 드로어 열림 상태처럼 화면이 닫히면 함께 사라져도 좋은 값들입니다.

전역 클라이언트 스토어 자체가 완전히 필요 없어지는 것은 아닙니다. 테마나 사이드바 접힘처럼 서버에도 저장하지 않고 URL에 담기도 어색한 UI 환경 설정은 여전히 전역 프로바이더나 서비스가 맡는 편이 깔끔합니다. 다만 예전처럼 앱 상태의 80%를 전역 스토어가 짊어지지 않게 되었을 뿐입니다.

## 경계에서 남는 현실적인 타협들

소유자를 나눈다고 해서 모든 경계가 칼같이 깔끔해지지는 않습니다. 실무에서 특히 신경을 쓰게 된 경계는 두 곳이었습니다.

하나는 **서버 데이터와 입력 초안이 만나는 자리**입니다. 읽기 화면에서는 서버 캐시 값을 그대로 그리되, 사용자가 입력을 시작한 순간부터는 별도의 `draft` 상태가 화면을 소유하도록 분리했습니다. 저장 요청이 날아가는 동안에도 계속 타이핑할 수 있어야 하는 화면에서는 초안에 판본 번호를 매겨 두고, 요청을 보냈던 판본과 응답 시점의 판본이 같을 때만 초안을 비우는 쪽으로 타협했습니다. 코드가 몇 줄 늘어나지만, 사용자가 방금 친 문장이 사라지는 사고를 막는 비용으로는 충분히 감당할 만했습니다.

다른 하나는 **검색 입력과 URL 사이**입니다. 검색어를 한 글자 칠 때마다 곧바로 URL과 API를 바꾸면 화면이 흔들리고 브라우저 히스토리도 어지러워집니다. 그래서 입력 중인 문자열은 로컬 상태에 두되 `200~300ms` 디바운스 뒤에 `replace`로 확정하고, 새 요청을 보내기 전에 이전 요청을 취소하는 규칙을 함께 묶었습니다. 입력을 지우거나 `Enter`를 누를 때만 기다리지 않고 즉시 반영하는 쪽이 체감상 덜 답답했습니다.

## 지금의 기준으로 남긴 것

전역 스토어 하나로 상태를 통합하는 접근은 클라이언트 안에서 복잡한 그래픽이나 오프라인 편집기 상태를 다루는 앱에서는 여전히 좋은 선택입니다. 하지만 대부분의 웹 업무 앱은 서버에서 읽어 온 데이터를 탐색하고 수정하는 비중이 압도적으로 큽니다.

그래서 지금은 “상태를 한곳에 모으자” 대신 **“서버 상태는 캐시, 확정 조건은 URL, 입력 초안은 로컬”**이라는 소유 경계를 먼저 긋는 쪽을 기본으로 삼고 있습니다. 구체적인 조회 옵션 공유, 준비 함수, 캐시 무효화와 검색 요청 취소 규칙은 [상태 관리와 데이터 흐름](../reference/state-and-data-flow/index.md)에 정리해 두었습니다.
