백엔드 프로젝트에서 코드를 어떤 기준으로 폴더와 패키지에 나눌지는 규모와 상관없이 늘 고민이 되는 지점입니다. 이 글은 흔히 비교하는 **타입 기준(Type-Based)**과 **기능 기준(Feature-Based)** 패키지 구조가 각각 어떤 강점과 한계를 갖는지 짚어 보고, 어떤 고민을 거쳐 지금의 **기능(컨텍스트) 중심 구조** 쪽으로 기울게 되었는지 정리합니다. 이어지는 구체적인 구성은 [컨텍스트와 레이어 설계](./context-and-layers.md)에서 다룹니다.

## 타입 기준 패키지 구조 (Type-Based)

레이어드 아키텍처를 코드로 옮길 때 가장 자연스럽게 떠올리는 방식이 `controllers`, `services`, `repositories`처럼 **기술적 역할(타입)**별로 폴더를 나누는 구조입니다.

```text
src/
  controllers/
    UserController
    PostController
    OrderController
  services/
    UserService
    PostService
    OrderService
  repositories/
    UserRepository
    PostRepository
    OrderRepository
```

이 구조는 계층이 곧 폴더 이름이라서 REST API가 어떤 흐름을 거쳐 처리되는지 한눈에 읽힙니다. 별도로 복잡한 규칙을 문서화하지 않아도 `controllers → services → repositories`라는 단방향 의존성이 구조 자체에 드러나기 때문에, 규모가 작거나 계층 규칙을 단순하게 유지하고 싶을 때는 꽤 쾌적하게 동작합니다.

다만 프로젝트가 자라면서 조금씩 답답한 지점이 생깁니다. 횡단 관심사로 나눈 폴더 안은 결국 반대 축인 업무 기능들로 채워지는데, `services/` 안에 수십 개의 서비스가 평면적으로 쌓이다 보면 어떤 서비스가 핵심 규칙을 다루고 어떤 서비스가 여러 업무를 조율하는지 폴더 구조만으로는 잘 보이지 않습니다. 기능 하나를 고칠 때도 `controllers`, `services`, `repositories`를 매번 오가야 하고, 서로 다른 패키지에 걸쳐 참조해야 하므로 대부분의 클래스를 `public`으로 열어 두게 됩니다.

## 기능 기준 패키지 구조 (Feature-Based)

반대로 **기능 기준(Feature-Based)**은 해결하려는 업무 영역별로 폴더를 묶는 방식입니다.

```text
src/
  user/
    UserController
    UserService
    UserRepository
  post/
    PostController
    PostService
    PostRepository
```

기능 기준으로 묶으면 한 기능을 만들거나 고칠 때 관련된 파일이 한 폴더에 모여 있어 코드 탐색이 한결 수월해집니다. 타입 기준에서는 모든 클래스를 열어 두어야 했던 것과 달리, 외부에 필요한 계약만 공개하고 내부 구현을 감추는 캡슐화도 시도해 볼 수 있습니다. 이미 업무 단위로 코드가 모여 있으니 나중에 특정 영역만 별도 모듈이나 서비스로 떼어낼 때도 출발점이 비교적 또렷합니다.

물론 기능 기준을 택했다고 고민이 사라지지는 않습니다. 오히려 실무에서 오래 써 볼수록 구체적인 문제들이 눈에 들어옵니다.

먼저 **패키지 레벨의 양방향 참조**가 생각보다 쉽게 생깁니다. 클래스 단위에서는 `OrderService → UserService`, `UserService → OrderRepository`처럼 각각 단방향 호출로 보이지만, 패키지 단위로 올려다보면 `user ↔ order`가 서로 참조하는 모양이 됩니다. ORM 엔티티의 양방향 연관관계나 공유 DTO가 얽히면 이 경계는 더 쉽게 흐려집니다.

여기에 한 폴더 안에 Controller, Service, Repository가 평평하게 함께 놓이다 보니 **내부 계층의 경계가 눈에 잘 띄지 않는 문제**도 따릅니다. 같은 기능 안에서 계층 간 의존 방향을 지키려면 별도의 기준과 주의가 필요해집니다.

## 먼저 정리해 두면 편한 경계: 업무 영역과 기술 기반

기능 기준으로 시작한 프로젝트에서 종종 마주치는 또 다른 고민은 공통 코드가 늘어나기 시작할 때입니다.

```text
src/
  user/         # 기능 기준 (업무)
  post/         # 기능 기준 (업무)
  database/     # 타입 기준 (기술)
  utils/        # 타입 기준 (기술)
  config/       # 타입 기준 (기술)
```

이 상태가 어색해지는 이유는 **같은 레벨의 폴더가 서로 다른 분류 기준을 따르고 있기 때문**입니다. `user`와 `post`는 비즈니스 업무를 기준으로 나눈 폴더인데, 바로 옆의 `database`와 `utils`는 기술적 역할로 나눈 폴더입니다. 외부 연동이나 공통 기능이 하나둘 붙을수록 어디까지가 업무 영역이고 어디부터가 기술 기반인지 구분이 흐려지고, 새 파일을 어디에 둘지 매번 망설이게 됩니다.

그래서 계층 우선으로 가든 기능 우선으로 가든, 최상위에서 **업무 영역과 기술 기반(비업무 영역)을 먼저 갈라 두는 편**이 프로젝트가 커져도 구조가 덜 흔들린다고 봅니다. 폴더 이름을 `shared`로 부르든 `common`이나 `core`로 부르든 이름 자체는 크게 중요하지 않습니다. 그보다 그 폴더 안에 비즈니스 지식이 없는 코드만 두고, 어떤 업무 패키지도 역으로 참조하지 않게 선을 긋는 쪽이 더 중요하다고 생각합니다.

```text
src/
  <context>/    # 업무 영역 (비즈니스 기능)
  shared/       # 기술 기반 예시 (DB 설정, 공통 에러, 유틸, 웹 필터 등)
```

이 경계만 먼저 잡아 두어도 “우리가 푸는 업무”와 “그 업무를 받쳐 주는 기술 기반”의 구분이 한결 쉬워집니다.

## 물리적 참조 규칙과 업무 응집도 사이의 선택

결국 패키지 설계에서 의견이 갈리는 지점은 **“무엇을 더 우선시하는가”**에 가깝습니다.

프론트엔드의 FSD(Feature-Sliced Design)처럼 최상위를 엄격한 수직 레이어(`app`, `features`, `domain`, `infra`, `shared`)로 나누고 물리적인 참조 방향을 단방향으로 통제하는 접근도 충분히 설득력이 있습니다. 레이어 간 의존성 그래프가 깔끔하게 유지되고, 고수준 형제 패키지 간의 결합을 구조적으로 막아 주기 때문입니다. 다만 한 업무 기능이 여러 최상위 레이어에 흩어져 있어 기능 전체의 흐름을 따라갈 때 폴더를 여럿 오가야 한다는 아쉬움이 남습니다.

반대로 바깥 축을 업무 단위로 묶는 기능 기준 구조는 응집도와 탐색 경험이 좋은 대신, 내부 계층과 형제 패키지 간의 참조 규칙을 따로 세우지 않으면 금세 엉키기 쉽습니다.

어느 한쪽이 절대적인 정답이라고 보기는 어렵습니다. 다만 실제로 코드를 읽고 수정하는 시간의 대부분은 특정 업무 기능을 손볼 때 쓰이다 보니, 여기서는 **바깥 축은 기능(컨텍스트)으로 묶어 응집도를 챙기고, 기능 기준의 약점이었던 양방향 참조와 계층 모호함은 내부 구조와 공개 계약 규칙으로 보완하는 쪽**으로 방향을 잡았습니다.

컨텍스트 바깥의 경계와 내부 3계층(`application`, `domain`, `infrastructure`)을 구체적으로 어떻게 구성해 이 균형을 맞추려 했는지는 다음 글인 [컨텍스트와 레이어 설계](./context-and-layers.md)에 이어서 정리해 두었습니다.
