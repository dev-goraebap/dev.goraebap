아키텍처 구조에는 프로젝트 규모와 팀 상황에 따라 맞는 답이 달라집니다. 이 글은 백엔드 코드를 컨텍스트 패키지와 3개 내부 계층(`application`, `domain`, `infrastructure`)으로 나누기까지 어떤 선택지들을 비교하고 어디에서 타협했는지 정리한 배경입니다. 구체적인 규칙은 [디렉토리·패키지 구조](../reference/directory-structure/index.md)와 [구성 요소와 실행 흐름](../reference/components-and-flow/index.md)에 있습니다.

## 패키지로 컨텍스트를 나누는 선택

현실의 하위 도메인을 소프트웨어 경계로 옮긴 것이 컨텍스트입니다. 이 경계를 코드에서 물리적으로 표현하는 방법은 격리 강도에 따라 보통 세 단계로 나뉩니다.

1. 같은 프로젝트 안에서 패키지·폴더로 분리 (모듈러 모놀리스)
2. 빌드 도구 단위의 멀티모듈로 분리
3. 별도 서버와 DB를 갖는 서비스로 분리 (MSA)

멀티모듈은 같은 프로세스로 묶어 배포하므로 네트워크나 분산 트랜잭션 비용은 없지만, 초기부터 빌드 설정과 의존성 관리, 모듈 간 리팩터링 복잡도가 따라옵니다. MSA는 여기에 더해 네트워크 호출, 분산 트랜잭션, 독립 배포·운영 비용까지 감당해야 합니다. 규모가 크고 팀이 여럿으로 나뉜 조직이라면 2단계나 3단계가 더 잘 맞을 수 있습니다.

반면 단일 팀이 빠르게 제품을 만들고 키워 가는 환경에서는, 처음부터 무거운 경계 비용을 치르기보다 패키지로 컨텍스트를 나누는 편이 현실적이라고 느꼈습니다. 빌드와 배포, 트랜잭션을 단순하게 유지하면서도 자동화된 경계 검사(`ArchitectureTest`, 린트, 모듈 export 제어)를 붙여 두면 내부 결합은 어느 정도 통제할 수 있습니다. 나중에 특정 컨텍스트만 독립 모듈이나 별도 서버로 떼어내야 할 시점이 오더라도, 이미 공개 계약(`*Facade`)이 경계로 서 있으므로 분리 부담을 덜 수 있습니다.

## 단순한 컨텍스트에도 내부 패키지를 두는 이유

당장 CRUD 수준인 단순한 컨텍스트를 떠올려 보면, 컨텍스트 폴더 바로 아래에 Controller, Service, Repository를 평평하게 두는 구조도 꽤 합리적입니다. 단순할 때는 파일 탐색도 빠르고 구조도 가볍습니다.

그럼에도 단순한 컨텍스트라도 최소한 `application/` 같은 내부 패키지를 두는 쪽으로 기울게 된 배경에는 두 가지 생각이 있었습니다.

하나는 **외부에 공개할 코드와 내부에 숨길 코드를 시각적으로 빠르게 구분하고 싶었기 때문**입니다. 컨텍스트 루트에 놓인 파일은 다른 컨텍스트가 써도 되는 공개 계약이고, 하위 패키지 안에 들어간 파일은 모두 내부 구현이라는 규칙을 두면 폴더 구조만 훑어도 경계가 비교적 쉽게 보입니다.

다른 하나는 **기능은 언젠가 확장되기 쉽다는 전제**입니다. 처음에는 단순한 조회·저장으로 시작한 기능도 시간이 지나면서 예외 조건이나 정책, 외부 연동이 하나둘 붙는 경우가 많았습니다. 처음부터 내부 패키지 경계를 잡아 두면 기능이 커질 때 폴더를 통째로 갈아엎지 않고 `domain/`과 `infrastructure/`를 필요한 시점에 덧붙여 나갈 수 있습니다. 당장의 간결함과 나중의 일관성 사이에서, 후자에 조금 더 무게를 둔 선택에 가깝습니다.

## 한 컨텍스트 안에 여러 애그리거트가 함께 있을 때

컨텍스트를 나누다 보면 어디까지를 하나로 묶고 어디서부터 쪼갤지가 늘 애매합니다. 예를 들어 게시물 기능을 만들 때 `post`, `category`, `tag`를 각각 별도 컨텍스트로 나눌 수도 있고, 하나의 컨텍스트 안에 함께 둘 수도 있습니다. 어느 한쪽이 무조건 틀렸다고 보기는 어렵습니다.

다만 너무 잘게 나누다 보면 실제로는 하나의 업무 문맥인 것들이 그저 테이블이나 기능 단위로만 쪼개지는 경우가 종종 있었습니다. 그렇게 되면 글 하나를 저장하거나 목록을 조회할 때마다 여러 컨텍스트의 공개 계약을 가로질러 호출해야 하고, 오히려 경계를 지키기 위한 억지 Facade만 늘어나는 느낌이 들었습니다.

그래서 서로 밀접하게 협력하는 요소들은 하나의 컨텍스트 안에 함께 두고, 대신 `domain/` 아래에서 생명주기와 일관성 경계가 다른 단위들(`post`, `category`, `tag`)을 각각 **애그리거트**로 나누는 쪽을 선호합니다. 컨텍스트는 비즈니스 문맥의 경계로, 애그리거트는 트랜잭션 일관성의 경계로 역할을 나눠서 보는 편이 개인적으로는 경계 설계가 덜 흔들렸습니다.

## Controller를 `application`에 함께 두는 타협

전통적인 레이어드 아키텍처나 헥사고날 아키텍처 관점에서 보면, Controller가 `application` 패키지 안에 들어가 있는 모습이 조금 어색해 보일 수 있습니다. 웹 진입점을 별도의 `presentation` 계층이나 Inbound Port/Adapter로 분리하는 쪽이 이론적으로는 더 깔끔한 것도 맞습니다.

다만 웹 백엔드 실무를 돌아보면, HTTP를 CLI나 다른 프로토콜로 통째로 갈아끼우는 일보다 API 스펙과 유스케이스가 함께 바뀌는 일이 훨씬 잦았습니다. 웹 진입점까지 포트로 감싸 멀리 떼어 놓으면 API 하나를 수정할 때마다 오가야 하는 파일과 보일러플레이트만 늘어나는 부담이 컸습니다.

반면 DB 접근이나 외부 API 연동(`infrastructure`) 쪽은 분리해 두었을 때 얻는 이점이 더 크게 느껴졌습니다. 도메인 계층이 프레임워크와 DB 라이브러리에 묶이지 않아야 핵심 규칙을 가볍게 테스트하고 기술 변경에도 버틸 수 있기 때문입니다. 그래서 웹 진입점(Controller)은 변경 주기가 비슷한 Service 옆에 함께 두고, 바깥쪽 기술 구현만 `infrastructure`로 분리하는 비대칭 3계층으로 타협했습니다.

## Service끼리 참조하지 않고 애그리거트를 조합하는 흐름

한 컨텍스트 안에 생명주기가 다른 여러 애그리거트가 함께 살다 보면, `application`에도 `PostService`, `CategoryService`, `TagService`처럼 여러 서비스가 자연스럽게 생깁니다. 이때 서비스가 다른 서비스를 호출하기 시작하면 처음에는 편해 보여도 곧 호출 그래프가 꼬이고 순환 참조가 생기기 쉽습니다.

그래서 같은 컨텍스트 안에서는 Service끼리 직접 기대기보다, 각 Service가 자기 유스케이스에 필요한 `domain`의 애그리거트와 포트를 직접 조합해 쓰는 방식을 쓰고 있습니다. 만약 여러 유스케이스에서 같은 도메인 계산이나 판단이 반복된다면 Service끼리 호출해 풀기보다 그 규칙을 `domain` 계층으로 내려 공유하는 쪽이 덜 꼬였습니다. 이렇게 두면 `application`은 비교적 얇은 조율자로 남고, 재사용되는 규칙은 순수한 `domain`에 모이게 됩니다.

## 계층 내부가 커질 때: 피처와 애그리거트, 그리고 루트 공통 규칙

컨텍스트 하나에 기능이 하나뿐이라면 `application/`이나 `domain/` 아래에 굳이 하위 패키지를 더 만들지 않고 평평하게 두는 편이 편합니다. 하지만 기능이 쌓여 Controller와 Service 조합이 여러 개(`post`, `category`, `tag` 또는 `auth`, `avatar`, `role` 등)로 늘어나면 한 폴더 안에 파일이 섞이기 시작합니다.

이 시점에서는 두 계층을 각자의 관점에 맞게 한 단계 더 나눕니다.

- **`application/`은 기능 관점(피처)**: 한 기능을 이루는 Controller · Service · Query · DTO를 세트로 묶어 하위 패키지로 나눕니다. 여기서 쓰는 ‘피처(Feature)’라는 이름은 업계의 엄밀한 표준 용어라기보다 이 문서에서 편의를 위해 부르는 말입니다. Vertical Slice Architecture의 슬라이스나 프론트엔드 FSD(Feature-Sliced Design)의 슬라이스처럼, 한 기능의 흐름을 세로로 묶은 단위와 비슷한 개념으로 이해하면 됩니다.
- **`domain/`은 애그리거트 관점**: 생명주기와 일관성 경계가 다른 모델 단위로 하위 패키지를 나눕니다.

여기서도 컨텍스트 루트에서 썼던 것과 비슷한 배치 원리가 한 번 더 반복됩니다. 컨텍스트 루트에 외부 공개 계약을 두고 내부를 하위 패키지로 숨겼듯, `application/`에서는 하위 피처들이 공통으로 참조하는 요소(공통 에러 코드, 설정, 쿠키·발송 포트 등)를 `application/` 루트에 둡니다. `domain/`에서도 여러 애그리거트가 함께 쓰는 값 객체나 공통 규칙은 `domain/` 루트에 둡니다. 같은 원리가 단계마다 반복되다 보니, 프로젝트가 커져도 “공통은 한 단계 위 루트에, 개별 관심사는 하위 폴더에”라는 감각으로 파일 위치를 찾기 쉬워졌습니다.
