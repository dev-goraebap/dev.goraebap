관계형 데이터베이스를 다루는 백엔드에서 JPA나 TypeORM처럼 엔티티와 객체 그래프를 중심에 두는 ORM은 오랫동안 자연스러운 선택지였습니다. 객체 중심으로 사고할 수 있고, 반복적인 매핑과 CRUD 코드를 크게 줄여 준다는 장점은 지금도 크다고 생각합니다. 그럼에도 최근 프로젝트들에서는 jOOQ(Java)나 Drizzle(TypeScript)처럼 **SQL에 좀 더 가까운 데이터 접근 방식**을 기본으로 두고 있습니다. 거창한 정답이라기보다, 작업을 이어 오며 느꼈던 몇 가지 고민에서 비롯된 선택입니다. 구체적인 사용 규칙은 [데이터 접근](../reference/data-access/index.md)에 정리해 두었습니다.

## 객체 중심 ORM을 쓰며 느꼈던 두 가지 고민

ORM을 오래 쓰다 보니 프로젝트가 조금만 복잡해져도 늘 비슷한 지점에서 망설이게 되었습니다.

하나는 **도메인 모델의 순수성과 실용성 사이의 타협**이었습니다. 매핑 코드를 줄이려고 `domain` 계층의 모델에 `@Entity`나 `@ManyToOne` 같은 어노테이션을 직접 붙이면 편하긴 하지만, 어느 순간 도메인 클래스가 기본 생성자나 프록시, 지연 로딩 같은 영속성 프레임워크의 제약에 맞춰져 가는 느낌이 들었습니다. 그렇다고 순수성을 지키자고 도메인 모델과 ORM 엔티티를 두 벌로 나누면, ORM을 쓰면서 매핑 코드까지 따로 관리해야 하는 부담이 생겼습니다.

다른 하나는 **조회 쿼리의 투명성**이었습니다. 단순한 저장이나 단건 조회에서는 큰 문제가 없었지만, 조건이 여러 개 붙는 목록 검색이나 커서 페이징, 집계 쿼리를 작성할 때는 ORM 쿼리빌더가 조금 답답하게 느껴질 때가 많았습니다. 지연 로딩이나 예상치 못한 N+1 쿼리처럼, 코드만 읽어서는 실제로 어떤 SQL이 몇 번 실행되는지 바로 가늠하기 어려운 경우도 종종 겪었습니다.

## 코드 작성 환경이 바뀌며 달라진 생각

사실 이런 고민들은 ORM을 쓰는 개발자라면 예전부터 알고 있던 트레이드오프에 가깝습니다. 그럼에도 전통 ORM의 추상화를 기꺼이 받아들였던 가장 큰 이유는, 결국 **사람이 직접 반복적인 영속성·매핑 코드를 덜 치고 싶었기 때문**이었던 것 같습니다. 약간의 불편함이 있더라도 직접 작성해야 할 인프라 코드 양을 줄여 주는 효용이 더 컸으니까요.

그런데 AI 에이전트가 구현 보일러플레이트의 상당 부분을 대신 작성해 주는 환경이 되면서, 이 기준이 조금 다르게 보이기 시작했습니다. “내가 덜 타이핑하기 위해” 두꺼운 추상화를 얹을 필요성은 예전보다 줄어든 반면, **에이전트가 작성한 코드를 사람이 읽고 검증할 때 동작이 얼마나 투명하게 보이는지**, 그리고 **계층 경계가 얼마나 단순하게 유지되는지**가 더 중요하게 느껴졌습니다.

## SQL 중심 도구를 써 보며 느낀 균형

jOOQ나 Drizzle처럼 SQL을 감추기보다 타입 안전한 코드로 드러내는 도구로 옮겨 보니, 적어도 앞서 겪었던 두 가지 고민은 꽤 덜어낼 수 있었습니다.

- **도메인 계층을 가볍게 둘 수 있었습니다**: `domain`에는 영속성 어노테이션 없는 순수한 언어 클래스만 남기고, 테이블과의 매핑은 `infrastructure` 안으로 몰아 둘 수 있었습니다.
- **조회 코드가 한결 솔직해졌습니다**: [명령과 조회의 분리](./command-and-query.md)에서 다룬 읽기 전용 `*Query` 구현체에서 조인·집계·윈도우 함수·커서 조건을 SQL에 가까운 형태로 적고, 결과를 화면용 뷰 DTO로 바로 매핑할 수 있었습니다. 코드만 보아도 어떤 쿼리가 날아갈지 대략 짐작이 되니 리뷰할 때도 마음이 편했습니다.

## 여전히 남아 있는 트레이드오프

물론 SQL 중심 도구가 모든 면에서 편한 것은 아닙니다. `infrastructure` 계층의 매핑 코드가 눈으로 보기에 분명 더 길고 수다스러워지고, ORM이 알아서 챙겨 주던 변경 감지(Dirty Checking)나 복잡한 객체 그래프의 일괄 저장 같은 편의는 포기해야 합니다.

팀이 JPA나 TypeORM에 깊이 익숙하고 객체 그래프 중심의 쓰기 패턴이 잘 맞는 프로젝트라면, 전통 ORM이 여전히 훨씬 생산적인 선택일 수 있습니다. 여기서는 단지 **도메인 계층을 프레임워크에서 떼어 두는 것, 조회 SQL을 눈으로 바로 확인하는 것, 그리고 경량 CQRS 흐름과의 궁합**에 조금 더 무게를 두고 SQL 중심 도구를 택해 보고 있는 쪽에 가깝습니다.
