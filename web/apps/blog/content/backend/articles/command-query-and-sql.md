이 글은 백엔드에서 명령(쓰기)과 조회(읽기)의 데이터 접근 경로를 왜 나누는지, 그리고 JPA·TypeORM 같은 전통적인 ORM 대신 jOOQ·Drizzle 같은 SQL 중심 도구를 택하게 된 배경을 정리합니다. 구체적인 규칙은 [데이터 접근](../reference/data-access/index.md)에 있습니다.

## 명령과 조회는 출발점이 다릅니다

백엔드 서버가 제공하는 기능은 크게 **상태를 바꾸는 명령(Command)**과 **데이터를 읽어 보여주는 조회(Query)**로 나뉩니다. 요청이 HTTP API로 들어오든, AI 에이전트의 MCP 도구 호출로 들어오든, 여러 진입점이 하나의 비즈니스 기능을 일관되게 바라보려면 `Service`가 공통 관문 역할을 맡게 됩니다.

그런데 `Service` 안에서 명령과 조회를 같은 방식으로 다루기 시작하면 두 가지 불편함이 생깁니다.

먼저 **명령**은 데이터를 저장·수정·삭제하기 전에 지켜야 할 업무 규칙과 불변식이 핵심입니다. 만약 명령도 조회처럼 SQL로 바로 처리해 버리면 검증과 상태 전이 규칙이 모두 `Service` 메서드 안에 쌓이고, 비슷한 유스케이스가 늘어날수록 같은 규칙이 여기저기 중복됩니다. 그래서 명령에서는 관련 상태와 규칙을 `domain` 계층의 엔티티와 값 객체로 캡슐화하고, `Repository` 포트를 통해 애그리거트 단위로 다루는 쪽이 책임을 깔끔하게 유지해 줍니다.

반면 **조회**는 상태를 바꾸지 않습니다. 필터링, 정렬, 페이징, 여러 테이블의 조합처럼 조회에서 자주 바뀌는 요구사항은 애플리케이션 메모리에서 객체 그래프를 조립하는 것보다 SQL의 기능을 그대로 활용하는 편이 훨씬 간결하고 예측 가능합니다.

## 엔티티 하나로 읽기와 쓰기를 함께 쓰려다 생기는 간극

예전에 ORM을 중심으로 개발할 때는 `PostEntity` 같은 클래스 하나를 만들어 두고 쓰기와 읽기에 모두 사용하는 것이 당연해 보였습니다. 하지만 화면이 조금만 복잡해져도 어색한 지점이 드러납니다.

조회 화면에서 작성자 이름이나 댓글 수, 태그 목록 같은 추가 정보가 필요해지면 쓰기에는 전혀 필요 없는 연관관계를 엔티티에 걸게 됩니다. 반대로 읽기 전용으로 불러온 엔티티에는 조회에는 쓸 일 없는 상태 변경 메서드들이 그대로 딸려 옵니다. 결국 엔티티만으로 화면 요구사항을 못 채워서 다시 별도의 DTO로 가공하고 형변환하는 코드가 쌓이게 됩니다.

이 간극이 생기는 이유는 단순합니다. **쓰기 모델은 업무 규칙이 바뀔 때 변하고, 읽기 모델은 화면이 바뀔 때 변하기 때문입니다.** 처음에는 둘이 똑같은 모양처럼 보여도, 서비스가 자라면서 자연스럽게 다른 모양으로 갈라집니다. 그래서 처음부터 도메인 모델은 **명령을 위해 존재하는 클래스**로 두고, 조회는 화면에 필요한 형태를 그대로 뽑아오는 쪽이 불필요한 변환과 억지 연관관계를 줄여 줍니다.

## 같은 DB 안에서 코드 경로만 나누는 경량 CQRS

CQRS라고 하면 흔히 쓰기 DB와 읽기 DB를 물리적으로 분리하고 메시지 브로커로 동기화하는 무거운 구조를 떠올리기 쉽습니다. 여기서 쓰는 방식은 그보다 훨씬 단순합니다. **같은 데이터베이스를 공유하면서 코드의 접근 경로만 둘로 나누는 경량 CQRS**입니다.

```text
명령(쓰기): Controller / MCP ─▶ Service ─▶ Repository 포트 & Domain 모델 ◀── Infrastructure 구현체
조회(읽기): Controller / MCP ─▶ Service ─▶ Query 포트 & View DTO        ◀── Infrastructure 구현체
```

조회에서는 `application` 계층이 화면에 필요한 뷰 DTO와 `*Query` 인터페이스를 직접 정의하고, `infrastructure` 계층이 SQL 쿼리로 그 DTO를 바로 채워 돌려줍니다. 뷰 DTO를 `infrastructure`가 아니라 `application`에 두는 이유는 의존 방향 때문입니다. 어차피 Controller와 Service가 `application`에 함께 있으므로 응답에 필요한 DTO를 `application`이 소유해야 `application`이 `infrastructure`를 역참조하지 않고 경계를 유지할 수 있습니다.

## 전통 ORM 대신 SQL 중심 도구를 택한 이유

JPA나 TypeORM 같은 전통적인 ORM은 분명 장점이 큽니다. 객체 그래프의 변경 감지(Dirty Checking)가 잘 맞아떨어지고 팀이 ORM의 동작 방식에 익숙하다면 지금도 충분히 좋은 선택입니다.

그럼에도 SQL에 비중을 둔 jOOQ(Java)나 Drizzle(TypeScript) 같은 도구로 옮겨 온 데에는 세 가지 현실적인 이유가 있습니다.

첫째, **도메인 계층의 순수성**입니다. 전통적인 ORM을 쓰면 클린 아키텍처와 실용주의 사이에서 늘 타협하게 됩니다. 매핑 코드를 줄이려고 `domain` 엔티티에 ORM 어노테이션을 직접 붙이자니 도메인이 영속성 프레임워크에 묶이고, 그렇다고 도메인 모델과 ORM 엔티티 클래스를 두 벌로 나누자니 유지보수할 변환 코드가 배로 늘어납니다. SQL 중심 도구를 쓰면 `domain`은 순수한 언어 클래스로 남겨두고 `infrastructure`에서만 테이블과 매핑할 수 있습니다.

둘째, **조회 쿼리의 완성도와 예측 가능성**입니다. 복잡한 조건 검색, 키셋 페이징, 조인과 집계로 갈수록 ORM 쿼리빌더의 한계나 예상치 못한 N+1·지연 로딩 문제가 발목을 잡습니다. SQL을 1급 시민으로 다루는 타입 안전 쿼리 빌더에서는 실행될 SQL이 코드에 그대로 드러납니다.

셋째, **코드를 작성하는 환경의 변화**입니다. 과거에 ORM의 두꺼운 추상화를 감수했던 큰 이유 중 하나는 사람이 직접 반복적인 영속성·매핑 코드를 덜 치기 위해서였습니다. AI 에이전트가 구현 보일러플레이트를 대신 작성해 주는 환경에서는 “직접 타이핑하는 수고를 덜기 위해” 무거운 ORM 추상화를 얹을 실익이 크게 줄어듭니다. 인프라 코드가 눈으로 보기에 조금 더 명시적으로 늘어날 수는 있어도, 대신 도메인 계층이 깔끔하게 유지되고 실제 실행되는 SQL을 한눈에 통제할 수 있다는 이점이 더 크다고 봅니다.

## 컨텍스트 경계와 조회의 타협: 언제 직접 JOIN을 허용하는가

컨텍스트마다 자기 모델과 테이블을 독립적으로 소유한다는 원칙을 지키다 보면, 쓰기 쪽은 깔끔하게 떨어집니다. 다른 컨텍스트의 상태를 바꾸거나 검증할 때는 예외 없이 공개 계약(`*Facade`)을 통하면 되므로, 다른 컨텍스트의 테이블을 직접 건드릴 이유가 없습니다.

문제는 **조회**입니다. 단일 데이터베이스를 공유하는 모듈러 모놀리스에서 다른 컨텍스트의 데이터가 함께 필요한 조회를 만나면, 모든 경우를 `*Facade` 조합으로만 풀려고 할 때 벽에 부딪힙니다. 이 지점은 외부 컨텍스트 데이터가 **“결과 보강용”**인지 **“집합 결정용”**인지로 나누어 보면 선명해집니다.

- **결과 보강(Enrichment)**: 자기 컨텍스트에서 필터·정렬·페이징을 모두 마친 20건의 목록에 작성자 이름이나 요약 정보만 덧붙이는 상황입니다. 이때는 20건의 ID를 모아 상대 `*Facade`를 한 번 배치 호출해 메모리에서 조합하면 N+1 문제도 없고 컨텍스트 경계도 온전히 지켜집니다.
- **집합 결정(Cross-Context Query)**: 반대로 외부 테이블의 상태나 이름으로 필터링(`WHERE`)하거나, 외부 컬럼 기준으로 정렬(`ORDER BY`)·페이징(`LIMIT` / `cursor`)하거나, 두 테이블을 가로질러 집계(`COUNT` / `GROUP BY`)하거나, 내 테이블에 행 자체가 없는 대상(`LEFT JOIN`)을 찾아야 하는 상황입니다. 이 경우에는 내 테이블만 먼저 잘라 오면 정렬과 페이지 크기가 망가지고, 외부 테이블 전체를 메모리에 끌어올릴 수도 없습니다.

DB가 물리적으로 분리된 MSA라면 이 문제를 풀기 위해 이벤트를 발행해 읽기용 복제 테이블(Projection)을 따로 유지해야 합니다. 하지만 단일 DB 모듈러 모놀리스에서 조회 몇 군데 때문에 이벤트 동기화와 최종 일관성 복잡도를 먼저 끌어들이는 것은 배보다 배꼽이 커지기 쉽습니다.

그래서 여기서는 **쓰기와 결과 보강은 `*Facade` 원칙을 지키되, 집합 자체를 결정해야 하는 읽기 전용 `*Query`에 한해 다른 컨텍스트 테이블의 직접 `JOIN`을 제한적으로 허용**하는 타협을 택합니다. 대신 집합을 결정하는 최소 컬럼만 읽고, 왜 직접 조인을 택했는지 주석으로 흔적을 남겨 둡니다. 그렇게 해 두면 당장은 단일 DB의 장점을 살리면서도, 나중에 특정 컨텍스트를 별도 DB나 서버로 떼어낼 시점이 왔을 때 어떤 쿼리만 읽기 모델 복제로 전환하면 되는지 경계가 분명하게 남습니다.
