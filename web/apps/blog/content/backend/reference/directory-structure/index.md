## 최상위 분리

소스 루트 아래는 **업무 영역(컨텍스트)**과 **업무와 무관한 기술 기반**으로 1차 분리합니다. 아래의 `shared/`는 기술 기반 폴더의 기본 예시이며, 프로젝트에서 업무 영역과 기술 기반을 구분하는 기준만 일관되게 지킨다면 폴더 이름(`shared`, `common`, `core` 등)은 자유롭게 정할 수 있습니다.

```tree
<source-root>/
  shared/               # 업무 지식이 없는 순수 기술 기반 (이름은 프로젝트별 선택)
    config/             # 전역 설정 (시간, 시크릿 등)
    domain/             # 공통 도메인 기반 타입·마커
    error/              # 공통 예외, 에러 코드 인터페이스
    persistence/        # DB 연결, 트랜잭션, 예외 변환
    storage/            # 오브젝트 스토리지 추상화 및 구현
    web/                # 전역 예외 처리, 공통 응답, 헬스체크, 페이징·필터
  <context>/            # 독립된 바운디드 컨텍스트 (프로젝트 기능에 따라 구성)
```

- 진입 파일이 소스 루트에 함께 놓이는 언어·프레임워크에서는 컨텍스트들을 `contexts/`나 `modules/` 같은 상위 폴더로 한 번 묶어 기술 기반 폴더와 나란히 둘 수 있습니다.
- 프로젝트 규모가 커져 공통 업무 묶음과 개별 제품 업무 묶음의 의존 방향을 분리해야 할 때만 컨텍스트 위에 상위 그룹 폴더를 한 단계 추가합니다.

## 컨텍스트 내부 구조

각 컨텍스트는 **루트의 공개 계약**과 **내부 3개 계층**으로 구성합니다.

```tree
<context>/
  <PublicContract>      # 다른 컨텍스트에 여는 진입 인터페이스(*Facade)와 공개 타입
  application/          # 진입점(Controller), 유스케이스·트랜잭션(Service), 조회 포트(Query), 요청·응답 DTO, 전용 에러 코드
  domain/               # 순수 비즈니스 모델(Entity, Value Object, 정책)과 영속성 포트 인터페이스(*Repository)
  infrastructure/       # domain·application 포트의 기술 구현체와 외부 연동 설정
```

- 조회 전용 로직만 있고 도메인 규칙이 없는 단순 컨텍스트는 `domain/`이나 `infrastructure/`를 생략할 수 있습니다.
- `application/`에 기능이 하나뿐이면 하위 폴더 없이 평평하게 두고, 여러 기능으로 늘어나면 **피처(`<feature>/`)** 단위로 나눕니다. 하위 피처들이 공통으로 참조하는 요소는 `application/` 루트에 둡니다.
- `domain/`도 애그리거트가 하나뿐이면 평평하게 두고, 여럿으로 늘어나면 **애그리거트(`<aggregate>/`)** 단위로 나눕니다. 하위 애그리거트들이 공통으로 참조하는 요소는 `domain/` 루트에 둡니다.

## 의존성 경계 규칙

| 출발 영역 | 허용 대상 | 금지 대상 |
| --- | --- | --- |
| `shared` | `shared`, 표준·외부 기술 라이브러리 | 모든 컨텍스트 |
| 컨텍스트 A | `shared`, 컨텍스트 B의 **공개 계약(루트)** | 컨텍스트 B의 `application`, `domain`, `infrastructure` |
| `domain` 계층 | 자기 컨텍스트 `domain`, `shared`의 도메인·에러 기반 타입, 언어 표준 | `application`, `infrastructure`, 웹·DB·DI 프레임워크 |

- 다른 컨텍스트의 기능이 필요하면 해당 컨텍스트의 공개 계약만 참조합니다.
- `domain` 계층은 특정 프레임워크나 DB 라이브러리에 의존하지 않는 순수 코드로 유지합니다.
- 경계 규칙은 코드 리뷰에만 맡기지 않고 자동화된 테스트 또는 린트 검사로 강제합니다.
