## HDA를 거쳐 다시 프론트엔드와 백엔드를 나누게 된 이유

웹 애플리케이션을 만들 때 어느덧 프론트엔드와 백엔드를 분리해 개발하는 방식이 기본값이 되었습니다. 저 역시 한때는 개발 비용을 줄여 보려고 UI/UX 경험을 일부 양보하면서 HTMX나 Hotwired 같은 HDA(Hypermedia-Driven Application) 방식을 시도했습니다.

경험 자체는 나쁘지 않았습니다. 서버가 HTML 조각을 바로 내려 주는 단순함은 분명 매력적이었고, 가벼운 화면을 빠르게 뽑아내는 데는 충분했습니다. 하지만 제품이 조금만 복잡해져도 불편한 지점이 반복해서 드러났습니다.

- 작성 중인 폼 초안을 유지하면서 목록과 상세를 오가거나, 모달·드로어·팝오버가 겹치는 상호작용을 다루기가 까다로워집니다.
- 리치 텍스트 에디터, 드래그 정렬, 캘린더, 복잡한 데이터 테이블처럼 프론트엔드 진영에 이미 완성도 높게 쌓여 있는 라이브러리를 그대로 쓰지 못하는 상황이 잦아집니다.
- 결국 클라이언트 스크립트를 조금씩 덧붙이다 보면 서버 템플릿과 클라이언트 상태가 어중간하게 섞입니다.

게다가 지금은 AI를 활용한 바이브 코딩 시대입니다. 예전에는 프론트엔드 분리로 늘어나는 보일러플레이트와 타입 연결 비용이 부담이었지만, 이제는 프론트엔드에도 힘을 주면서 개발 속도를 함께 끌어올릴 수 있게 되었습니다. 그래서 지금은 **프론트엔드 프레임워크와 백엔드 프레임워크를 명확히 나누어 개발하는 것**을 1차 규칙으로 둡니다.

## React와 Vite 기반의 구동과 API 계약

프론트엔드는 React, TypeScript, Vite를 기본으로 삼고, 상태의 소유권을 역할에 따라 분명히 나눕니다.

- **URL과 탐색 상태**: 라우터(TanStack Router)가 소유합니다. 검색 조건·필터·페이지 상태는 URL에서 검증합니다.
- **서버 데이터 캐시**: 조회 도구(TanStack Query)가 소유합니다. 라우트 loader에서 필요한 데이터를 미리 채우고, 파생값을 `useState`와 `useEffect`로 복사하지 않습니다.
- **HTTP 계약의 원본은 서버**: 백엔드의 OpenAPI 명세에서 클라이언트 타입을 자동 생성해 호출합니다. API가 바뀌면 타입 검사가 호출부의 어긋남을 바로 잡아 줍니다.

응답에는 전역 `success`/`data` 래퍼를 씌우지 않고 HTTP 상태 코드와 `application/problem+json`을 그대로 씁니다. 버튼 노출이나 편집 가능 여부도 화면이 권한 규칙을 다시 계산하지 않고, 서버 응답에 실려 온 `can` 같은 판정 값만 보고 그립니다.

## 개발은 분리하되, 배포는 제품 성격에 맞춰 고릅니다

프론트엔드와 백엔드를 나누어 개발한다고 해서 배포까지 항상 둘로 쪼개야 하는 것은 아닙니다. SPA 빌드 결과물(`dist/`)은 결국 정적 HTML·JS·CSS 파일이기 때문에 제품 성격에 따라 두 가지 배포 방식을 자연스럽게 선택할 수 있습니다.

| 배포 방식                              | 어울리는 제품                              | 구성과 특징                                                                                                                           |
| -------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| **별도 배포** (정적 호스팅 + API 서버) | 블로그, 공개 서비스, 프론트 갱신이 잦은 웹 | Vite 빌드 결과물을 정적 서버나 CDN에 올리고, 리버스 프록시나 별도 도메인으로 백엔드 API를 호출합니다.                                 |
| **함께 배포** (단일 컨테이너 이미지)   | 설치형 업무 앱, 내부 도구                  | 빌드 단계에서 프론트를 먼저 빌드해 백엔드 정적 리소스 경로에 담고, 서버가 `/api/**` 외의 경로를 `index.html`로 넘겨 SPA를 서빙합니다. |

개발할 때는 각 프레임워크의 개발 서버(Vite HMR + 백엔드 서버)를 따로 띄워 빠른 피드백을 얻고, 운영할 때는 블로그처럼 가볍게 정적으로 내보낼지 업무 앱처럼 컨테이너 하나로 묶을지만 고르면 됩니다.

## 파일 라우팅을 곁들여 내 입맛대로 다듬은 FSD 구조

프론트엔드 폴더 구조는 FSD(Feature-Sliced Design)의 단방향 의존 철학을 따르되, 실무에서 거추장스러웠던 부분을 제 작업 방식에 맞게 다듬어 씁니다.

```text
src/
├── app/         # 진입점, 프로바이더, 라우터 설정, 업무를 아는 앱 셸
├── pages/       # 곧 URL 주소 (파일 라우팅이 이 폴더를 읽음)
│   └── _app/    # 주소에 드러나지 않는 레이아웃 묶음
│       ├── route.tsx
│       └── projects/
│           ├── route.tsx   # 하위 주소 공통 틀·권한·데이터 준비
│           ├── page.tsx    # 현재 주소 화면
│           └── ui/         # 이 주소 전용 세그먼트 (라우트 제외)
├── features/    # 사용자 행위 단위 기능
├── entities/    # 업무 개체 단위 모델·표시
└── shared/      # 도메인 무관 유틸, API 클라이언트, UI 키트
```

표준 FSD에서 제가 의도적으로 바꾼 지점은 세 가지입니다.

1. **`widgets` 층을 두지 않습니다.** `pages`·`features`·`shared` 사이에 `widgets`를 두면 "이 컴포넌트가 feature인가 widget인가"를 고민하는 데 시간을 쓰게 됩니다. 업무를 모르는 화면 조합은 `shared`에, 업무와 메뉴를 아는 앱 셸은 `app`에 두고 층을 다섯(`app` · `pages` · `features` · `entities` · `shared`)으로 단순화합니다.
2. **파일 라우팅을 `pages` 층에 직접 연결합니다.** 파일 라우팅은 폴더와 파일 이름 규칙만으로 라우트 트리를 자동 생성해 주는 기능입니다. TanStack Router 플러그인이 `src/pages`를 직접 읽도록 설정하면, **폴더 하나가 곧 URL 주소 하나이자 FSD 슬라이스 하나**가 됩니다. `route.tsx`(부모 틀과 데이터 준비)와 `page.tsx`(실제 화면)만 라우트로 인식하고, 슬라이스 안의 `ui/`·`model/`·`api/`·`lib/` 폴더는 라우트에서 제외합니다.
3. **`pages` 안에서는 형제 주소를 가져오지 않습니다.** 각 주소 폴더는 자기 폴더와 조상 폴더의 코드만 참조합니다. 두 주소가 함께 써야 할 코드가 생기면 형제 폴더를 참조하는 대신 공통 조상이나 `features`/`shared`로 올립니다.

`shared` 안에서도 범용 UI 키트(또는 모노레포의 `packages/ui`)와 제품 고유 공용 컴포넌트를 분리해 둡니다. 이렇게 계층과 참조 방향을 단순하게 잡아 두면, 화면 수가 수십 개로 늘어나도 새 기능을 어디에 놓아야 할지 헤매지 않고 에이전트에게 작업을 맡길 때도 일관된 위치에 코드가 자리 잡습니다.
