데이터를 불러오는 중이거나 목록이 비어 있을 때, 오류가 나거나 양식을 저장·제출할 때 화면이 어떻게 반응할지 정합니다. 사용자가 지금 무슨 일이 일어나는지 알고 다음 행동을 고를 수 있게 하되, 불필요한 깜빡임이나 알림으로 흐름을 끊지 않습니다.

규칙 앞에는 성격을 표시합니다(`[관례]`, `[고래밥]`, `[선호]`). 구분 기준은 [읽는 법](/#규칙의-세-가지-표시)에 있습니다.

## 대기와 불러오기

대기 표시는 걸리는 시간과 바뀌는 범위에 맞춰 고릅니다([NN/g: Response times](https://www.nngroup.com/articles/response-times-3-important-limits/), [NN/g: Skeleton screens](https://www.nngroup.com/articles/skeleton-screens/), [Primer: Loading](https://primer.style/product/ui-patterns/loading/)). 사람의 응답 시간 감각은 0.1초(즉각 반응), 1초(생각의 흐름이 끊기지 않는 한계), 10초(주의를 붙잡아 둘 수 있는 한계)에서 갈립니다.

| 예상 시간 | 범위와 상황 | 표시 방법 |
| --- | --- | --- |
| 1초 미만 | 모든 동작 | `[관례]` 아무 대기 표시도 하지 않습니다 |
| 1~10초 | 화면의 한 구역만 갱신할 때 | `[관례]` 무엇을 불러오는지 이름이 붙은 스피너를 둡니다(1~3초는 비확정 표시, 3~10초는 가능하면 진행 정도를 알 수 있는 확정 표시) |
| 2~10초 | 페이지 전체를 처음 그릴 때 | `[관례]` 실제 화면 배치와 같은 모양의 스켈레톤을 보입니다 |
| 10초 초과 | 긴 작업 | `[관례]` 진행률을 표시합니다 |

- `[관례]` 스켈레톤은 실제 데이터 화면의 배치와 같을 때만 씁니다([Primer: Loading](https://primer.style/product/ui-patterns/loading/)). 실제 배치와 다른 스켈레톤은 내용이 나타날 때 화면이 다시 튀게 만듭니다.
- `[고래밥]` 앱 첫 진입만 스플래시로 덮고, 그 뒤의 화면 이동에는 본문을 가리는 막을 두지 않습니다. 캐시가 있으면 오래됐어도 바로 그리고 뒤에서 조용히 갱신하며, 링크에 포인터나 초점이 오면 그 화면을 미리 준비합니다. 캐시가 없을 때는 이전 화면을 그대로 두고 150ms 뒤에 콘텐츠 카드 위 테두리에 흐르는 진행 표시만 띄우며, 준비된 화면끼리는 콘텐츠 영역만 200ms 교차 페이드합니다. 막은 상세 안 사이드바까지 덮고 다시 방문할 때도 떠서 답답했고, 바꾼 뒤 다시 방문의 대기가 사라지고 레이아웃 이동이 0이었습니다.

## 빈 상태

`[관례]` 목록이나 영역에 보일 항목이 없을 때는 왜 비어 있는지에 따라 세 가지로 나누고, 각 상태에서 사용자가 바로 할 수 있는 다음 행동을 하나만 둡니다([Carbon: Empty states](https://carbondesignsystem.com/patterns/empty-states-pattern/), [NN/g: Empty states](https://www.nngroup.com/articles/empty-state-interface-design/), [Atlassian: Empty state](https://atlassian.design/components/empty-state/usage), Primer Blankslate).

| 상태 | 언제 나타나나 | 설명할 내용 | 다음 행동 (하나만) |
| --- | --- | --- | --- |
| 처음 | 아직 만든 항목이 하나도 없을 때 | 이곳에 무엇이 생기는지 안내합니다 | 만들기 |
| 결과 없음 | 검색어나 필터 조건에 맞는 항목이 없을 때 | 조건을 바꾸면 결과를 찾을 수 있다고 안내합니다 | 조건 지우기(초기화) |
| 오류 | 데이터를 불러오지 못했을 때 | 무엇을 불러오지 못했는지 알립니다 | 다시 시도 |

- `[선호]` 빈 상태 그림을 넣을 때는 테마 색으로 칠한 펜 선 풍경 그림을 씁니다([선호 화면](/app-shell/preferred-screens/)).

## 알림과 토스트

`[관례]` 알림과 오류는 원인이 생긴 자리에서 가장 가까운 곳에 둡니다. 화면에 결과가 바로 보이면 별도 알림을 띄우지 않으며, 자동으로 사라지는 알림에는 중요한 내용을 담지 않습니다([Primer: Notification messaging](https://primer.style/product/ui-patterns/notification-messaging/), Atlassian).

| 상황 | 알림을 두는 자리 |
| --- | --- |
| 입력 칸 하나의 값 오류 | `[관례]` 해당 입력 칸 바로 곁 |
| 양식 전체의 저장 실패 | `[관례]` 양식 안 |
| 페이지 전체의 상태·오류 안내 | `[고래밥]` 머리 줄 아래, 툴바 위의 배너 자리(안내가 없으면 자리도 비워 둠, [머리 줄과 툴바](/app-shell/header-and-toolbar/)) |

### 토스트 사용 기준

`[고래밥, 2026-11-07 결정]` 토스트는 화면의 변화만으로는 완료 여부를 알 수 없는 짧은 동작에만 씁니다. Primer는 토스트 자체를 권하지 않고 Atlassian도 자동으로 닫히는 알림에 중요한 내용을 금합니다. 화면 변화가 없는 짧은 완료까지 인라인이나 배너로 알리면 화면 자리만 차지하므로 그 경우에만 토스트를 허용하고, 오류와 중요 안내는 원위치에 고정해 놓치지 않게 합니다.

- 주소 복사, 항목 보관, 백그라운드로 넘긴 작업의 시작처럼 완료 결과가 현재 화면에 바로 드러나지 않는 짧은 완료에만 토스트를 띄웁니다.
- 항목 추가처럼 결과가 화면에 바로 보이면 아래의 바로 저장되는 속성 변경을 빼고는 토스트를 띄우지 않습니다.
- `[고래밥, 2026-11-09 결정]` 상세에서 저장 버튼 없이 바로 저장되는 속성 변경(상태·담당·날짜·라벨 등)은 결과가 화면에 보여도 5초 "되돌리기" 토스트를 띄우고, 남은 시간을 줄어드는 막대로 보이며 포인터가 올라가면 멈춥니다. 확인 단계가 없어 잘못 누르면 되돌릴 길이 필요하기 때문입니다.
- 오류, 경고, 되돌릴 수 없는 결과, 사용자가 읽고 다음 행동을 해야 하는 내용은 토스트에 두지 않습니다.
- 보관이나 삭제 취소처럼 되돌릴 수 있는 완료 알림에는 토스트 안에 `되돌리기` 동작 하나를 둘 수 있습니다. 이때는 사용자가 읽고 누를 수 있도록 충분히 오래 남깁니다.

## 저장과 제출

### 명시 저장과 입력 보존

- `[관례]` 양식 저장은 사용자가 저장·제출 버튼을 눌러 확정하는 명시 저장을 기본으로 합니다([Primer: Saving](https://primer.style/product/ui-patterns/saving/)).
- `[관례]` 한 양식 안에서 자동 저장과 명시 저장을 섞지 않습니다. 어떤 값은 바로 반영되고 어떤 값은 저장 버튼을 눌러야 반영되면 사용자가 현재 반영 상태를 예측할 수 없습니다.
- `[관례]` 저장 요청이 실패해도 사용자가 입력한 내용은 그대로 남깁니다. 입력한 채로 창이나 화면을 닫으려 할 때는 버릴지 먼저 묻습니다([라우트 마스킹](/app-shell/route-masking/)).

### 필수 값 검증과 제출 버튼

`[관례, 2026-11-07 결정]` 필수 항목이 비어 있어도 제출 버튼은 비활성화(`disabled`)하지 않고 늘 누를 수 있게 둡니다([Primer: Saving](https://primer.style/product/ui-patterns/saving/)).

1. 양식을 열었을 때 필수 항목에는 필수 표시(`*`, 보조기기가 읽을 수 있는 접근 가능한 이름 "필수")를 미리 보입니다. 아직 제출하지 않은 상태에서는 오류 문구를 미리 띄우지 않습니다.
2. 필수 값이 빠진 채로 제출 버튼을 누르면, 빠진 항목마다 그 칸 곁에 무엇이 필요한지 오류를 표시하고 첫 번째 빠진 항목으로 초점을 옮깁니다.
3. 사용자가 값을 채우면 해당 항목의 오류 표시는 그 자리에서 바로 사라집니다.
4. 저장 요청을 보내고 응답을 기다리는 동안에만 버튼을 처리 중 상태로 막아 중복 제출을 방지합니다.

비활성화된 버튼은 키보드 초점이 닿지 않고, 왜 누를 수 없는지(어느 칸이 빠졌는지) 알려 주지 못합니다. 버튼을 열어 두고 누른 시점에 빠진 칸으로 안내하는 편이 키보드·보조기기 사용자와 긴 양식을 작성하는 사용자 모두에게 원인을 분명히 전달합니다.
