앱 셸의 본문 영역 폭을 화면 성격에 따라 정하는 규칙입니다. 화면을 만들거나 검토할 때 본문을 영역 끝까지 채울지, 가운데 열로 모을지, 오른쪽에 속성 열을 둘지 이 기준으로 판단합니다.

규칙마다 성격을 함께 표시합니다. `[관례]`는 여러 제품과 공개 지침이 수렴한 기준이고, `[고래밥]`은 관례가 없거나 다르게 정한 결정이며, `[선호]`는 취향으로 고른 모양입니다. 표기 기준은 [이 문서를 읽는 법](/#규칙의-세-가지-표시)을 따릅니다.

## 화면 성격에 따라 본문 폭을 고른다

본문 영역에 담기는 내용과 주된 작업에 맞춰 네 가지 폭 가운데 하나를 고릅니다.

| 화면 | 본문 폭 | 이유와 성격 |
| --- | --- | --- |
| 컬렉션(목록·표·보드) | 본문 전체 폭. 행 바탕과 구분선은 영역 양 끝까지 채우고, 글자는 페이지 정렬선(`16px`)에 맞춥니다 | 한 행에 많은 속성을 나란히 보이고 위아래로 훑기 위해 `[관례]` |
| 읽고 쓰는 화면(상세 본문, 작성 양식, 문서) | 최대 약 `720px` 읽기 열 | 줄 길이를 제한해 시선 이동을 줄이기 위해 `[관례]` |
| 값과 정책(설정) | 최대 약 `720px` 가운데 열. 묶음은 카드 안의 행 목록으로 둡니다 | 항목 수가 적고 이름-값 쌍이 멀어지지 않게 하기 위해 `[관례]` |
| 상세 + 속성 | 읽기 열(최대 약 `720px`) + 오른쪽 속성 열(약 `256px`). 영역이 좁으면 속성을 제목 아래 알약 줄로 옮깁니다 | Linear·Plane 상세 화면과 Android 보조 패널 구성 `[관례]` |

### 컬렉션은 본문 전체 폭을 쓴다 `[관례]`

목록·표·보드 같은 [컬렉션](/app-shell/collections/)은 본문 영역 전체 폭을 씁니다. 행의 배경 면과 아래 구분선은 본문 영역의 왼쪽 끝부터 오른쪽 끝까지 채우고, 행 안의 글자와 요소는 페이지 양쪽 정렬선(`16px`)에 맞춥니다. 식별자·상태·제목·담당자·날짜 같은 여러 속성을 한 줄에 배치하고 열 위치를 맞춰 훑어보려면 가로 폭을 넓게 확보해야 합니다.

### 읽고 쓰는 화면과 설정은 최대 약 720px 열로 제한한다 `[관례]`

상세 본문, 작성 양식, 문서처럼 긴 글을 읽거나 입력하는 화면은 본문을 최대 약 `720px` 폭의 읽기 열로 둡니다. 줄이 지나치게 길어지면 다음 줄의 시작점을 찾기 어려워 읽는 흐름이 끊깁니다.

설정 화면처럼 값과 정책을 다루는 화면도 최대 약 `720px` 가운데 열에 둡니다. 설정은 한 화면에 들어가는 항목이 적고 왼쪽의 항목 이름과 오른쪽의 값이나 조작 도구가 짝을 이룹니다. 전체 폭으로 벌리면 이름과 값 사이가 멀어져 한눈에 이어 보기 어렵습니다.

### 상세와 속성이 함께 있으면 두 열로 나누고 좁을 때 접는다 `[관례]`

본문 글과 상태·담당자·마감일 같은 속성을 함께 다루는 상세 화면은 최대 약 `720px` 읽기 열 오른쪽에 약 `256px` 폭의 속성 열을 나란히 둡니다. 본문 영역이 좁아져 두 열을 나란히 놓기 어려우면 오른쪽 속성 열을 없애고, 같은 속성들을 본문 제목 아래의 알약 줄로 옮깁니다(이 배치 모양은 [선호 화면](/app-shell/preferred-screens/)의 기준이기도 합니다 `[선호]`).

`[고래밥, 2026-11-09 결정]` 본문이 있는 상세 화면의 속성 열은 본문에 제목이 있으면 맨 위에 "목차", 그 아래 대상별 속성, 맨 끝에 "정보"(작성자·작성일·수정일·버전 수) 순서로 둡니다. 목차와 버전도 다른 속성과 같은 속성 행으로 그려 아이콘과 글자 자리를 맞추고, 휴대폰은 목차를 오른쪽 아래 둥근 버튼과 바텀시트로 둡니다. 편집기 가장자리에는 목차 표시를 붙이지 않습니다. 가장자리의 짧은 선 목차는 무엇인지 알기 어려웠고, 화면마다 작성 정보 자리가 제각각이었기 때문입니다.

Linear와 Plane의 상세 화면이 본문 오른쪽에 속성 패널을 두는 구성을 씁니다. 다만 Linear 화면의 실제 픽셀 수치는 공개 자료에 없어 확인하지 못했습니다. [Android 권장 레이아웃(Canonical layouts)](https://developer.android.com/develop/ui/compose/layouts/adaptive/canonical-layouts)의 보조 패널(Supporting pane) 지침은 넓은 화면(`expanded`)에서 본문과 보조 패널을 70:30 비율로 나누고, 중간 화면(`medium`)에서는 반반으로 나누도록 안내합니다.

### 외부 지침에서 확인한 것과 확인하지 못한 것

[GitHub Primer: PageLayout](https://primer.style/components/page-layout)은 본문 컨테이너 폭(`containerWidth`)을 `medium`·`large`·`xlarge`·`full` 네 단계로 정의하고 콘텐츠 영역의 기본값을 `full`로 둡니다. 다만 어떤 성격의 화면에서 `full`을 유지하고 언제 폭을 제한하는지 정한 1차 지침 문서는 찾지 못했습니다. 컬렉션은 전체 폭으로 두고 읽고 쓰는 화면과 설정은 가운데 열로 좁히는 구분은 실제 제품들의 관행을 바탕으로 정리한 기준입니다.

## 목록 항목은 카드로 감싸지 않는다 `[관례]`

컬렉션의 개별 목록 항목은 카드로 감싸지 않습니다. 촘촘하게 나열하는 데이터는 여백과 구분선으로 나눈 행으로 그립니다.

카드는 설정 화면에서 관련된 항목 묶음을 하나의 상자로 묶을 때처럼, 서로 독립된 묶음을 구분할 때만 씁니다. 상자와 구분선을 줄이는 원칙은 [시각 위계](/common/visual-hierarchy/)에서 함께 다룹니다.

## 창 폭이 아니라 영역의 실제 폭으로 판단한다 `[고래밥]`

본문을 한 열로 둘지, 읽기 열 옆에 속성 열을 나란히 둘지 결정할 때는 브라우저 창 전체 폭(뷰포트)이 아니라 본문이 실제로 놓인 영역(컨테이너)의 폭을 기준으로 삼습니다.

같은 상세 화면이라도 열리는 자리에 따라 쓸 수 있는 가로 폭이 다릅니다.
- 전체 페이지로 열렸더라도 [사이드바](/app-shell/shell-and-sidebar/)를 넓히면 본문 영역이 줄어듭니다.
- 목록 옆에 여는 [미리보기 패널](/app-shell/peek/)은 본문 영역의 약 40~50%만 차지합니다.
- [라우트 마스킹](/app-shell/route-masking/)으로 목록 위에 여는 대화상자는 전체 페이지보다 좁습니다.

창 폭으로만 분기하면 창은 넓지만 미리보기 패널이나 대화상자 안은 좁을 때 두 열이 비좁게 구겨집니다. 영역의 실제 폭을 기준으로 삼아야 같은 상세 화면 부품이 페이지, 미리보기 패널, 대화상자 어디에 놓이든 그 자리의 폭에 맞춰 오른쪽 속성 열과 제목 아래 알약 줄 사이를 일관되게 오갑니다.
