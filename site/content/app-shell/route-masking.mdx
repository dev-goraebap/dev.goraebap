라우트 마스킹은 하나의 주소에 대화상자와 페이지 두 모습을 두는 규칙입니다. 데스크톱 앱 안에서 클릭해 열면 목록 위에 대화상자로 띄우고, 같은 주소로 직접 진입하거나 새로고침하면 독립된 페이지로 엽니다. 새 자료 만들기나 자료 수정처럼 짧게 끝내고 목록으로 돌아오지만, 내용이 길어질 수 있고 주소 공유와 새로고침이 의미 있는 작업에 적용합니다.

규칙의 성격은 세 가지로 표시합니다. `[관례]`는 여러 제품과 외부 지침이 같은 방향으로 수렴한 규칙이고, `[고래밥]`은 관례가 없거나 관례와 다르게 정한 자체 결정이며, `[선호]`는 기능 규칙이 아닌 모양 취향입니다. 전체 표시 기준과 결정 배경은 [문서 읽는 법](/start/how-to-read/)과 [결정 기록](/start/decisions/)을 참고합니다.

## 라우트 마스킹을 쓰는 이유

`[고래밥]` 작성 양식을 목록 위 대화상자로 열면서 동시에 고유한 페이지 주소를 갖게 합니다.

목록을 탐색하다가 새 항목을 만들거나 기존 항목을 고칠 때는 목록의 맥락(검색어, 필터, 스크롤 위치, 선택 상태)을 잃지 않고 작업을 마치는 편이 유리합니다. 이 점만 보면 목록 위에 뜨는 대화상자가 알맞습니다.

그러나 주소가 없는 대화상자만 쓰면 한계가 생깁니다. 브라우저를 새로고침할 때 열려 있던 작업 화면이 사라지고, 주소를 복사해 다른 사람에게 공유할 수 없으며, 휴대폰에서 뒤로가기 동작이 기대와 어긋납니다. 입력할 내용이 길어지면 좁은 대화상자 안에 갇히기도 합니다. [GitHub Primer: Dialog guidelines](https://primer.style/product/components/dialog/guidelines/)에서도 대화상자는 짧은 단일 열 작업에만 쓰고, 링크로 공유할 대상은 별도 페이지로 만들라고 안내합니다.

라우트 마스킹은 두 요구를 함께 만족시킵니다. 하나의 주소에 두 가지 모습을 두어, 앱 안에서 클릭해 진입할 때는 목록 위에 대화상자를 그리고 주소창에는 대상의 실제 페이지 주소를 표시합니다. 그 주소로 직접 찾아오거나 새로고침하면 대화상자가 아니라 원래 페이지로 엽니다.

이 동작은 라우터 라이브러리의 기존 패턴과 같은 원리를 따릅니다.

- [TanStack Router: Route masking](https://tanstack.com/router/latest/docs/framework/react/guide/route-masking): 실제 렌더링하는 라우트와 다른 주소를 브라우저 주소창에 표시합니다. 마스크 정보는 브라우저 히스토리 state에 저장하며, `unmaskOnReload` 옵션으로 새로고침 시 마스크를 해제합니다. 주소창의 URL을 복사해 새 탭에서 열면 히스토리 state가 없으므로 마스크 없이 실제 페이지가 열립니다.
- [Next.js: Intercepting routes](https://nextjs.org/docs/app/api-reference/file-conventions/intercepting-routes)와 [Parallel routes](https://nextjs.org/docs/app/api-reference/file-conventions/parallel-routes): 사진 모달 패턴에서 앱 안 클릭(soft navigation)은 모달로 가로채서 열고, 새로고침이나 링크 공유를 통한 진입(hard navigation)은 전체 페이지로 엽니다. 브라우저 뒤로가기가 모달을 닫고 앞으로가기가 다시 엽니다.

제품과 외부 지침의 전체 비교는 [비교 조사](/references/comparison/)와 [읽기 목록](/references/reading-list/)에서 다룹니다.

## 언제 라우트 마스킹을 선택하는가

`[고래밥]` 라우트 마스킹 적용 여부는 **작업이 끝나는 시간**과 **주소의 필요성** 두 가지로 판단합니다. 주소가 필요 없는 짧은 작업은 일반 대화상자로 열고, 오래 머무는 화면은 처음부터 페이지로 엽니다.

화면 전체에서 표현 방식을 고르는 순서와 기준은 [표현 고르기](/app-shell/choosing-presentation/)에 정리되어 있습니다. 라우트 마스킹과 인접한 표현을 구분하는 기준은 아래와 같습니다.

| 표현 방식 | 적용 조건 | 주소 | 대표 사례 |
| --- | --- | --- | --- |
| 라우트 마스킹 `[고래밥]` | 짧게 끝내고 목록으로 돌아오지만, 내용이 길어질 수 있고 링크 공유·새로고침이 의미 있는 작업 | 대상의 실제 주소 (목록 위에서는 `?panel=대상`을 마스크) | 새 자료 만들기, 자료 수정 |
| 짧은 양식 대화상자 `[관례]` | 몇 칸으로 끝나는 짧은 변경이고 결과를 링크로 공유할 일이 없는 작업 (휴대폰은 전체 화면) | 없음 | 이름 바꾸기, 초대 |
| 미리보기 패널 `[고래밥]` | 목록을 보면서 여러 항목을 차례로 훑는 작업 (데스크톱만 목록 옆, 휴대폰은 페이지) | 목록 주소 + `?peek=대상ID` | 처리 목록의 항목 연속 확인 ([미리보기 패널](/app-shell/peek/) 참고) |
| 자기 페이지 `[관례]` | 읽고 오래 머무르거나 외부 공유가 주 목적인 화면 | 대상의 실제 주소 | 상세 읽기, 활동·댓글, 여러 단계 작업 |

## 마스킹 계약

`[고래밥]` 라우트 마스킹으로 여는 화면은 아래 7가지 계약을 지킵니다.

1. **진짜 주소와 직접 진입 (`[고래밥]`)**: 마스킹 대상에는 고유한 실제 주소가 있습니다. 주소창에 그 주소를 입력하거나 외부 링크로 직접 진입하면 처음부터 독립된 페이지로 엽니다.
2. **목록 쿼리와 마스크 표시, 새로고침 해제 (`[고래밥]`, `[관례]`)**: 데스크톱 목록에서 대상을 열면 내부 라우팅은 목록 주소에 `?panel=대상`을 더하고, 브라우저 주소창에는 대상의 실제 주소를 마스크로 보입니다. 그 상태에서 새로고침하면 마스크를 풀어 대상 페이지로 엽니다([TanStack Router: Route masking](https://tanstack.com/router/latest/docs/framework/react/guide/route-masking)의 `unmaskOnReload` 동작).
3. **진입 경로에 따른 닫기 동작 (`[고래밥]`, `[관례]`)**: 현재 세션에서 목록을 거쳐 대화상자를 열었으면 닫을 때 브라우저 히스토리 뒤로가기(`router.back()` 등)를 실행해 목록의 검색·필터 조건과 스크롤 위치를 그대로 유지합니다([Next.js: Intercepting routes](https://nextjs.org/docs/app/api-reference/file-conventions/intercepting-routes)의 모달 닫기 원칙). 이 세션에서 쌓인 이전 기록이 없으면 목록 주소로 바꿉니다(replace).
4. **크게 보기와 초안 유지 (`[고래밥]`)**: 대화상자에서 작성하다가 내용이 길어져 '크게 보기'를 실행하면 작성 중이던 같은 초안을 그대로 페이지로 옮깁니다. 대화상자가 닫히고 페이지가 마운트되는 동안 입력이 사라지지 않도록, 초안 저장소는 대화상자와 페이지 부품보다 오래 사는 상위 영역에 둡니다. 대화상자에서 페이지로 전환할 때 초안을 보존하는 이 규칙은 외부 1차 출처를 찾지 못했으며 자체 설계로 정한 것입니다.
5. **휴대폰은 처음부터 페이지로 이동 (`[고래밥]`, `[관례]`)**: 휴대폰 폭(1024px 미만)에서는 라우트 마스킹을 쓰지 않고 처음부터 대상의 실제 페이지로 이동합니다([GitHub Primer: Dialog guidelines](https://primer.style/product/components/dialog/guidelines/)도 휴대폰의 입력 대화상자는 전체 화면으로 열도록 안내합니다). 휴대폰 분기점과 전체 화면 전환 규칙은 [적응형](/app-shell/adaptive/)을 참고합니다.
6. **저장 성공 시 결과 페이지로 교체 (`[고래밥]`)**: 작성이나 수정을 저장해 성공하면 현재 기록을 결과 페이지 주소로 바꿉니다(replace). 결과 페이지에서 브라우저 뒤로가기를 눌렀을 때 다시 작성 화면으로 가지 않고 원래 목록으로 돌아가게 하기 위해서입니다.
7. **입력이 남아 있을 때 닫기 확인 (`[관례]`)**: 입력한 값이 있는 채로 대화상자를 닫으려 하면 변경 내용을 버릴지 먼저 묻습니다([Apple HIG: Modality](https://developer.apple.com/design/human-interface-guidelines/modality)는 사용자 입력이 유실될 수 있을 때 닫기 전 확인을 요구합니다). 명시적 저장과 입력 보호 규칙은 [상태와 피드백](/app-shell/states-and-feedback/)을 참고합니다.
