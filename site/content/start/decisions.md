화면을 설계하거나 고칠 때 관례와 다르게 정한 규칙, 여러 지침이 갈릴 때 택한 기준, 기각한 대안을 확인한다. 새 화면을 만드는 개발자와 에이전트는 각 규칙의 이유와 전제를 보고 그대로 적용하고, 나중에 전제나 환경이 바뀌면 이 기록을 근거로 규칙을 재검토한다.

## 규칙의 성격과 바꿀 때의 기준

이 규칙집의 모든 항목은 성격에 따라 세 가지로 구분한다. 자세한 읽는 법은 [규칙 읽는 법](/start/how-to-read/)에서 다루고, 외부 제품·지침과의 대조는 [비교 조사](/references/comparison/)와 [참고 자료](/references/reading-list/)에 정리해 두었다.

| 표시 | 뜻 | 바꿀 때 |
| --- | --- | --- |
| `[관례]` | 여러 제품과 디자인 시스템 지침이 같은 쪽으로 수렴한 규칙이다. 근거 자료가 있다. | 참조한 근거 지침이나 웹 표준이 바뀌었을 때 |
| `[고래밥]` | 확립된 관례가 없거나, 관례와 다른 쪽을 택한 우리 결정이다. 선택 이유와 대가를 함께 적는다. | 결정 당시의 이유나 전제가 더 이상 맞지 않을 때 |
| `[선호]` | 기능 규칙이 아니라 작업자가 고른 시각적 취향이다([선호 화면](/app-shell/preferred-screens/), [시각 위계](/common/visual-hierarchy/), [아이콘](/common/icons/)). | 취향이 바뀌면 자유롭게 |

아래에는 지침 간 충돌이 있었거나 관례와 다르게 결정한 핵심 항목을 모았다.

## 표현과 주소

### 미리보기 패널을 두고 주소(`?peek=`)에 남긴다

- 분류: `[고래밥]` (2026-11-07 결정)
- 관련 규칙: [미리보기 패널](/app-shell/peek/), [표현 고르기](/app-shell/choosing-presentation/)

데스크톱에서 목록을 보면서 여러 항목을 차례로 훑을 때는 목록 옆에 비모달 미리보기 패널을 열고, 목록 주소에 `?peek=대상ID` 쿼리를 남긴다. 패널을 처음 열 때는 방문 기록을 추가하고(`push`), 패널이 열린 채 다른 행을 누르거나 위·아래 키로 항목을 옮길 때는 기록을 쌓지 않고 주소만 바꾼다(`replace`). 휴대폰 폭에서 `?peek=` 주소로 진입하면 패널을 그리지 않고 대상의 자기 페이지로 바꿔 이동한다(`replace`).

- 이유: Linear와 Plane처럼 목록의 검색·필터·스크롤 맥락을 유지한 채 항목을 확인하는 패널이 필요하다. 그런데 Plane은 미리보기 열림 상태를 내부 스토어에만 두고 주소에 남기지 않아 브라우저 뒤로가기로 패널을 닫거나 새로고침·링크 공유로 같은 화면을 다시 열 수 없다. 주소에 상태를 남겨야 뒤로가기 한 번으로 목록으로 돌아오고 링크를 공유할 수 있다.
- 기각한 안:
  - 미리보기 패널을 두지 않고 항상 페이지로 이동하기: 여러 항목을 연달아 확인하는 처리 목록에서 목록과 상세를 오가는 비용이 크다.
  - 주소 없이 상태로만 미리보기 열기(Plane 방식): 뒤로가기·새로고침·공유가 깨진다.

### 행 클릭 동작은 목록의 성격에 따라 나눈다

- 분류: `[고래밥]` (2026-11-07 결정)
- 관련 규칙: [미리보기 패널](/app-shell/peek/), [컬렉션](/app-shell/collections/)

목록 행을 눌렀을 때 열리는 대상은 그 목록에서 주로 하는 일에 따라 정한다. 한 목록 안에서는 한 가지 방식으로 통일한다.

| 목록 구분 | 대상 예 | 데스크톱 행 클릭 | 데스크톱에서 다른 열기 수단 | 휴대폰 행 클릭 |
| --- | --- | --- | --- | --- |
| 처리 목록 (여러 항목을 연달아 확인·판단) | 받은 항목, 알림, 승인 대기, 검토 요청 | 미리보기 패널 (`?peek=ID`) | 패널 안의 '페이지로 열기', 위·아래 키로 항목 이동 | 대상 페이지 |
| 작업 목록 (하나를 골라 들어가 작업) | 업무, 문서, 자료 | 대상의 자기 페이지 | `Space` 키, 행 끝의 미리보기 버튼(포인터를 올리면 보이고 키보드 초점이 닿음) | 대상 페이지 |

어느 목록으로 볼지 애매할 때는 작업 목록으로 판단해 페이지 이동을 기본으로 삼는다.

- 이유: Linear는 행을 누르면 페이지로 이동하고 `Space` 키로 미리보기를 여는 반면, Plane은 행을 누르면 미리보기를 연다. 받은 항목처럼 빠르게 훑고 넘기는 목록과 문서처럼 본문에 들어가 오래 머무는 목록은 주된 동선이 다르므로 두 방식을 목록 성격에 맞춰 분리했다.
- 기각한 안:
  - 모든 목록에서 행 클릭을 항상 페이지 이동으로 통일하기: 받은 항목이나 승인 대기 목록에서 항목을 하나씩 확인하고 돌아오는 동선이 길어진다.

### 작성·수정은 라우트 마스킹으로 대화상자와 페이지를 겸한다

- 분류: `[고래밥]`
- 관련 규칙: [라우트 마스킹](/app-shell/route-masking/), [표현 고르기](/app-shell/choosing-presentation/)

만들기·수정처럼 짧게 끝내고 목록으로 돌아오지만 내용이 길어질 수 있고 새로고침이나 링크 공유가 의미 있는 화면은 라우트 마스킹을 쓴다. 데스크톱 목록에서 열면 목록 주소에 `?panel=대상`을 더해 목록 위 대화상자로 띄우되, 브라우저 주소창에는 대상의 실제 페이지 주소를 보여 준다. 그 주소로 직접 진입하거나 새로고침할 때, 대화상자에서 '크게 보기'를 누를 때, 휴대폰에서 열 때는 마스크 없이 실제 페이지로 연다.

- 이유: Linear와 Plane은 작성 화면을 모달로 열어 목록의 조건과 스크롤을 지킨다. 반면 GitHub Primer 대화상자 지침은 링크로 공유할 대상을 모달이 아닌 페이지에 두라고 권한다. 주소 없는 모달만 쓰면 새로고침·공유·휴대폰 뒤로가기가 깨지고 글이 길어질 때 좁은 창에 갇힌다. Next.js 인터셉트 라우트나 TanStack Router의 라우트 마스킹처럼 한 주소에 두 가지 표현을 두어 두 요구를 함께 해결한다.
- 기각한 안:
  - 주소 없는 대화상자만 쓰기: 새로고침이나 주소 공유 시 작성 화면으로 바로 진입할 수 없고 휴대폰 입력 화면이 좁아진다.
  - 데스크톱에서도 항상 페이지로 이동하기: 짧은 항목을 하나 만든 뒤 기존 목록의 스크롤과 필터 맥락으로 즉시 돌아오기 어렵다.

## 셸과 적응형 전환

### 사이드바 기본 폭은 340px로 유지한다

- 분류: `[고래밥]` (2026-11-07 결정)
- 관련 규칙: [셸과 사이드바](/app-shell/shell-and-sidebar/)

데스크톱 사이드바의 기본 폭은 340px로 두고, 사용자가 220~380px 범위에서 끌어서 조절할 수 있게 한다.

- 이유: 조사한 제품과 지침의 사이드바 기본 폭은 250~340px, 최소 폭은 220~256px 범위다(Plane 기본 250px, Atlassian 기본 320px·범위 240px~화면의 50%, Primer 최소 256px. Linear 화면의 실제 픽셀 수치는 공개 자료에 없어 확인하지 못했다). 한글 메뉴 이름과 2단계 하위 항목을 말줄임표 없이 한눈에 읽을 수 있도록 관례 상한인 340px을 기본값으로 유지한다.
- 대가와 보완: 좁은 노트북 화면에서 미리보기 패널을 함께 열면 가운데 목록 폭이 좁아진다. 이 상황은 사용자가 사이드바를 220px까지 줄이거나 아이콘 모드로 접어서 해결한다.
- 기각한 안:
  - 기본 폭을 280px(Plane 250px과 Atlassian 320px의 중간)로 줄이기: 하위 메뉴와 작업 공간 이름이 자주 잘린다.

### 데스크톱과 휴대폰 전환 분기점은 1024px 하나로 통일한다

- 분류: `[고래밥]`
- 관련 규칙: [적응형](/app-shell/adaptive/)

사이드바↔하단 탭, 팝오버↔바텀시트, 마스킹 대화상자↔페이지, 표↔행 목록 전환은 모두 1024px(`64rem`) 한 지점에서 동시에 바꾼다.

- 이유: 제품과 지침마다 전환 폭이 다르다(Atlassian 1024px, Primer 768px, Plane 768px, Android 창 크기 구분 600px·840px, Linear는 웹 모바일 설계 없음). 부품마다 분기점을 다르게 두면 중간 폭에서 데스크톱 부품과 모바일 부품이 섞여 레이아웃이 깨진다. 분기점을 하나로 통일하되, 1024px보다 작게 잡으면 태블릿 세로 화면에서 고정 사이드바와 터치 영역이 좁게 맞물리므로 Atlassian과 같은 1024px을 택했다.
- 기각한 안:
  - 768px을 분기점으로 쓰거나 600px·840px 다단계 분기점 두기: 768~1024px 구간에서 사이드바(340px)를 펼치면 본문 열이 지나치게 좁아진다.

### 휴대폰 하단 탭은 '앞 네 곳 + 더보기'로 구성한다

- 분류: `[고래밥]`
- 관련 규칙: [적응형](/app-shell/adaptive/)

휴대폰 주 탐색인 하단 탭은 현재 메뉴 공간의 앞 네 항목과 '더보기' 탭을 합쳐 다섯 칸으로 두고, '더보기'를 누르면 나머지 목적지를 바텀시트로 연다.

- 이유: Android 적응형 탐색 지침과 NN/g 모바일 탐색 지침은 하단 탭을 4~5개로 두고 항상 보이게 하라고 권한다. 반면 Apple HIG는 '더보기(More)' 탭 같은 오버플로를 피하라고 안내한다. 그러나 업무 도구는 주 탐색 목적지가 다섯 곳을 넘는 경우가 많고, 상단 햄버거 메뉴로 탐색을 숨기면 발견성이 크게 떨어진다(NN/g 실험에서 숨긴 탐색의 사용률은 27%로, 보이는 탐색 48%의 절반 수준). Apple HIG의 권고와 다르더라도 탐색을 숨기지 않고 '더보기' 시트로 노출하는 쪽을 택했다.
- 기각한 안:
  - 상단 햄버거 메뉴로 주 탐색 숨기기: 탐색 발견성과 사용률이 떨어진다.
  - 모든 업무 앱의 메뉴를 다섯 개 이하로 제한하기: 실제 업무 도구의 메뉴 구성을 담기 어렵다.

### 휴대폰 상세·작성·대화 화면에서는 하단 탭을 숨긴다

- 분류: `[고래밥]`
- 관련 규칙: [적응형](/app-shell/adaptive/)

휴대폰에서 상세 읽기, 양식 작성, 대화처럼 내용에 집중하거나 화면 키보드를 쓰는 화면으로 들어가면 하단 탭과 앱 도구를 치우고, 상단 `← 이름 + 자기 도구`와 바닥 동작 줄만 있는 전체 화면으로 연다.

- 이유: Apple HIG는 모달이 덮을 때를 제외하면 화면 이동 시에도 하단 탭 바를 숨기지 말라고 권한다(상세 화면에서 탭 바를 숨기라는 외부 공식 지침은 조사에서 확인하지 못했다). 하지만 휴대폰 웹 브라우저는 브라우저 자체 주소창·도구 줄에 더해 화면 키보드가 올라오면 네이티브 앱보다 세로 공간이 훨씬 좁아진다. 또한 작성·상세 화면 바닥에는 전역 탭이 아니라 저장·제출 같은 현재 화면의 주요 동작이 놓여야 하므로 관례와 다르게 하단 탭을 숨긴다.
- 기각한 안:
  - 상세·작성 화면에서도 하단 탭 바를 항상 남겨 두기(Apple HIG 방식): 키보드가 올라올 때 본문 영역이 좁아지고 바닥 제출 버튼과 하단 탭이 겹쳐 오작동을 유발한다.

### 주소 없는 바텀시트는 `CloseWatcher`로 닫고 쿼리에 상태를 두지 않는다

- 분류: `[고래밥]` (2026-11-07 결정)
- 관련 규칙: [적응형](/app-shell/adaptive/)

데스크톱 팝오버가 휴대폰에서 바텀시트로 바뀐 경우(값 고르기, 필터, 표시, 행 메뉴, 더보기)에는 주소를 부여하지 않고 브라우저의 닫기 요청 API(`CloseWatcher`)를 연결한다. 안드로이드 뒤로가기 제스처와 `Esc` 키를 누르면 방문 기록을 건드리지 않고 시트만 닫힌다.

- 이유: NN/g 바텀시트 지침은 뒤로가기로 시트를 닫을 수 있어야 한다고 안내한다. 이를 위해 시트 열림 상태를 주소 쿼리에 넣으면 필터나 메뉴를 잠깐 열 때마다 방문 기록이 쌓이고, 새로고침했을 때 시트가 다시 열리는 부작용이 생긴다. 의미 있는 화면 상태(페이지, 마스킹 대상, 탭, 필터 값, 미리보기 `?peek=`)만 주소에 두고, 일시적인 시트 열림은 `CloseWatcher`로 처리한다.
- 대가와 보완: 현재 `CloseWatcher`를 지원하지 않는 브라우저(iOS 사파리 등)에서는 시트가 열린 채 뒤로가기를 하면 이전 페이지로 이동할 수 있다. 이 제약을 받아들이는 대신, 모든 시트에 눈에 보이는 닫기 버튼을 반드시 두고, 잃으면 아까운 긴 입력은 시트에 담지 않는다(입력이 길면 주소가 있는 화면으로 연다).
- 기각한 안:
  - 바텀시트 열림 상태를 주소 쿼리에 기록하기: 짧은 조작마다 히스토리가 오염되고 새로고침 시 시트가 강제로 열린다.

## 상태, 피드백, 양식 저장

### 필수 값이 비어 있어도 제출 버튼을 비활성화하지 않는다

- 분류: `[관례]` (2026-11-07 결정, 기존 자체 동작 변경)
- 관련 규칙: [상태와 피드백](/app-shell/states-and-feedback/)

양식에서 필수 입력 칸이 비어 있어도 저장·제출 버튼은 활성 상태로 둔다. 사용자가 버튼을 누르면 비어 있는 필수 항목마다 그 곁에 필요한 값을 알리는 오류 문구를 표시하고, 첫 번째 빠진 항목으로 초점을 옮긴다. 필수 표시(`*`, 접근 가능한 이름 '필수')는 처음부터 보여 주고, 오류 표시는 첫 제출 시도 뒤부터 보이며 값을 채우면 즉시 사라진다. 버튼은 실제 저장 요청이 진행 중일 때만 처리 중 상태로 막는다.

- 이유: 이전에는 Linear의 작성 모달처럼 필수 항목이 채워지기 전까지 제출 버튼을 비활성화했다. 그러나 GitHub Primer의 Saving 지침이 지적하듯 비활성화한 버튼은 키보드 탐색으로 초점이 닿지 않고, 화면이 긴 양식에서 왜 버튼을 누를 수 없는지 이유를 알려 주지 않는다. 접근성과 명확한 오류 안내를 위해 Primer 지침을 따르기로 결정했다.
- 기각한 안:
  - 필수 값이 비었을 때 제출 버튼 비활성화 유지하기(Linear 방식): 키보드 사용자와 화면 낭독기 사용자가 막힌 이유를 알기 어렵다.

### 토스트는 화면에 결과가 보이지 않는 짧은 완료에만 쓴다

- 분류: `[고래밥]` (2026-11-07 결정)
- 관련 규칙: [상태와 피드백](/app-shell/states-and-feedback/)

자동으로 사라지는 토스트 알림은 화면 자체에 변화가 남지 않는 짧은 완료(링크 주소 복사, 항목 보관, 백그라운드로 넘긴 작업의 시작)에만 쓴다. 보관이나 삭제 취소처럼 되돌리기 동작 하나를 제공하는 완료 알림은 토스트에 둘 수 있으며, 이때는 사용자가 누를 수 있도록 충분히 오래 남긴다. 반면 결과가 화면에 바로 반영되는 동작에는 토스트를 띄우지 않고, 오류·경고·되돌릴 수 없는 결과·다음 행동이 필요한 안내에는 토스트를 절대 쓰지 않는다.

- 이유: GitHub Primer는 토스트가 작업 위치에서 멀고 자동으로 사라져 접근성과 인지 면에서 불리하므로 토스트 자체를 쓰지 말라고 권한다. Atlassian(flag 지침)은 자동으로 사라지는 알림에 중요한 내용을 넣지 말라고 안내한다. 오류와 경고를 원인 가까운 곳(입력 칸 곁, 양식 안, 머리 줄 아래 배너)에 두는 원칙은 Primer와 같지만, 주소 복사처럼 화면이 바뀌지 않는 동작에는 완료 피드백이 필요하므로 용도를 엄격히 제한해 허용했다.
- 기각한 안:
  - 토스트를 전면 금지하기(Primer 방식): 클립보드 복사나 백그라운드 작업 시작 뒤 성공 여부를 확인할 별도 UI를 매번 만들어야 한다.
  - 저장 실패나 오류까지 토스트로 띄우기: 사용자가 오류 원인을 읽거나 복사하기 전에 알림이 사라지고, 어느 입력 칸의 문제인지 알기 어렵다.

## 그 밖의 고래밥 세부 규칙

개별 화면 규칙 페이지에 포함된 나머지 `[고래밥]` 결정이다. 자세한 적용 방법은 각 문서에서 확인한다.

- 하위 공간의 메뉴 대체([셸과 사이드바](/app-shell/shell-and-sidebar/)): '내 계정'이나 '관리' 같은 하위 공간에 들어가면 기존 주 메뉴 위에 메뉴를 한 겹 더 쌓지 않고, 사이드바 주 메뉴 전체를 하위 공간 메뉴로 대체한 뒤 맨 위에 `← 공간 이름` 복귀 링크를 둔다.
- 도구 순서와 페이지 배너 자리([머리 줄과 툴바](/app-shell/header-and-toolbar/)): 도구 자리는 `검색 → 필터 → 표시` 순서로 좁은 간격으로 묶고, 주요 동작인 `만들기` 버튼은 그보다 넓은 간격을 띄워 머리 줄 맨 끝에 둔다. 페이지 전체의 상태·오류 배너는 머리 줄 아래·툴바 위에 두며, 알릴 내용이 없으면 자리도 차지하지 않는다.
- 창 폭이 아닌 영역 실제 폭 기준([콘텐츠 폭](/app-shell/content-width/)): 상세 화면의 오른쪽 속성 열을 옆에 둘지 제목 아래 알약 줄로 내릴지는 브라우저 창 전체 폭이 아니라 그 상세가 놓인 영역(페이지, 미리보기 패널, 대화상자)의 실제 폭으로 판단한다.
- 좁은 화면의 표 전환과 주소 상태 유지([컬렉션](/app-shell/collections/), [필터와 표시](/app-shell/filters-and-display/)): 휴대폰 폭에서 표는 가로 스크롤 대신 핵심 속성만 남긴 행 목록으로 바꾼다(외부 지침 문서가 아니라 실무 관행을 택한 결정이다). 사람 속성은 사진과 이름을 함께 표시하고 미지정 상태도 같은 자리를 유지한다. 검색어·필터·표시 조건은 모두 주소에 반영하되, 검색어 입력 중에는 방문 기록을 쌓지 않고(`replace`) 주소만 갱신한다.
- 대기 시 화면 유지([상태와 피드백](/app-shell/states-and-feedback/)): 데이터를 불러올 때 캐시가 있으면 즉시 그리고 뒤에서 갱신한다. 캐시가 없으면 이전 화면을 유지하다가 대기가 길어질 때만 로딩 표시를 덮어 짧은 대기에 화면이 깜빡이지 않게 한다.

## 확인하지 못한 외부 근거

비교 조사 시점(2026-11-07)에 원문을 직접 확인하지 못해 결정에 참고만 했거나 제외한 항목이다.

- Linear 웹 앱의 구체적인 픽셀 수치(사이드바 기본 폭, 목록 행 높이, 모달 크기)는 공개 문서에 나와 있지 않아 확인하지 못했다.
- Linear의 미리보기(peek) 및 모바일 관련 일부 문서는 페이지가 열리지 않아(404) 검색 요약으로만 확인했다.
- Material 3 웹 문서(`m3.material.io`) 본문은 스크립트 렌더링 제약으로 직접 읽지 못하고 Android 개발자 공식 문서(창 크기 구분, 적응형 탐색, 표준 레이아웃)로 대체했다.
- Refactoring UI는 단행본 원문 전체가 아니라 핵심 요약 자료만 확인했다.
- 휴대폰에서 표를 핵심 속성 중심의 행 목록으로 바꾸는 규칙과, 상세·작성 화면에서 하단 탭을 숨기는 규칙은 이를 직접 뒷받침하는 외부 디자인 시스템 문서를 찾지 못해 우리 자체 결정(`[고래밥]`)으로 분류했다.
