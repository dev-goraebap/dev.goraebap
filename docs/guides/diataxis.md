# Diátaxis 기반 문서 작성과 관리

이 저장소의 지침 문서는 [Diátaxis](https://diataxis.fr/) 프레임워크의 4개 분면과 용어집으로 관리합니다.

## 1. 분면 구분과 폴더 구조

| 분면 | 사이트 메뉴 | 폴더 | 독자의 질문 | 담는 내용 | 담지 않는 내용 |
| --- | --- | --- | --- | --- | --- |
| Tutorials | **튜토리얼** | `tutorials/` | "처음 어떻게 시작하지?" | 처음 따라 하는 단계별 입문 안내 (`/webapp` 홈 전용, 스킬 빌드 제외) | 세부 스펙 표(→ 레퍼런스), 긴 배경 논증(→ 아티클) |
| How-to guides | **플레이북** | `playbooks/` | "이 작업을 어떤 순서로 하지?" | 목표를 이루는 실행 절차, 레퍼런스 조합 순서, 확인 체크리스트 | 긴 배경 설명(→ 아티클), 모든 규칙 나열(→ 레퍼런스) |
| Explanation | **아티클** | `articles/` | "왜 이렇게 설계했지?" | 설계 의도, 대안 비교, 트레이드오프, 판단 기준 | 단계별 실행 지시(→ 플레이북), 건조한 스펙 표(→ 레퍼런스) |
| Reference | **레퍼런스** | `reference/` | "규칙·구조·스펙이 뭐지?" | 정확한 사실, 구조, 허용/금지 표, 계약, 매핑 | 1인칭 경험이나 긴 논증(→ 아티클), 작업 순서(→ 플레이북) |
| Glossary | **용어집** | `content/glossary/` | "이 용어가 무슨 뜻이지?" | 영역별(`frontend.md`, `backend.md`, `design-system.md` 등) 보편 아키텍처·설계 용어의 정의, 혼동 구분, 메타데이터 | 특정 프로젝트 전용 기능 분류명, 산문 메모 |

분면끼리 내용을 중복하지 않고 **상대 경로 링크**로 연결합니다.
- 플레이북 → 기준표가 필요하면 레퍼런스로, 경계 판단이 애매하면 조건부로 아티클로 링크
- 레퍼런스 → 설계 배경이 필요하면 아티클로 링크
- 아티클 → 구체적 규칙이 필요하면 레퍼런스로 링크

## 2. 톤앤매너

모든 문서는 담백한 **‘합니다’체**를 씁니다. 분면에 따라 글의 결을 분명히 나눕니다.

- **레퍼런스**: 건조하고 정확하게 사실·규칙·경계만 씁니다. 이유는 생략하거나 한 구절까지만 둡니다.
- **플레이북**: 번호가 매겨진 실행 단계와 바로 복사해 쓸 수 있는 설정·명령 위주로 씁니다. 마지막에 동작 확인 단계를 둡니다.
- **아티클**: **유연하고 겸손한 기술 블로그 톤**으로 씁니다.
  - 다른 선택지(예: 전통 레이어드, 멀티모듈, ORM 등)의 장점을 솔직히 인정합니다.
  - 어떤 전제와 트레이드오프를 거쳐 현재 기준을 택했는지 사고의 흐름을 풀어냅니다.
  - 확신에 찬 선언(“~해야 한다”, “~이 달라집니다”, “~가 자연스럽게 풀립니다”, “~가 답답해집니다”)을 피하고, 관찰과 경험에 기반한 어투(“~라고 느끼게 되었습니다”, “~쪽이 덜 불편했습니다”, “~에 가깝습니다”, “~으로 타협했습니다”)를 씁니다.
  - 일기체나 우유부단한 결론(“알아서 선택하세요”)으로 흐르지 않게 선택의 근거와 중심은 유지합니다.

### 공통 금지 표현

- AI 특유의 서론·결론 금지 (“이 문서에서는 ~에 대해 알아봅니다”, “이상으로 ~을 살펴보았습니다”).
- 근거 없는 평가 수식어 금지 (“강력한”, “손쉬운”, “효율적인”, “완벽한”).
- 문단마다 `**이름**: 설명` 패턴이나 형식적인 3항목 나열을 기계적으로 반복하지 않습니다.
- 특정 제품명·사내 업무명·프로젝트 전용 기능 분류명(예: `cowork`, `foundation`)을 일반 지침에 넣지 않습니다. 어떤 프로젝트에서나 통용되는 일반화된 개념과 예시만 씁니다.

## 3. 프레임워크 중립성과 스택 분리

프레임워크가 바뀌어도 기준이 무너지지 않도록 **공통 기준**과 **스택 구현**을 파일로 분리합니다.

```text
content/<space>/
  tutorials/
    <slug>.md           # 단일 공통 입문 안내 (/webapp 홈 전용)
  playbooks/
    <slug>/
      index.md          # 공통 절차 (프레임워크 이름 없음)
      <stack>.md        # 스택별 구현 절차 (예: springboot.md, react-tanstack.md, angular.md)
  articles/
    <slug>.md           # 단일 공통 글 (스택 탭 없음)
  reference/
    <slug>/
      index.md          # 공통 규칙·명세 (프레임워크 이름 없음)
      <stack>.md        # 스택별 매핑·예시
```

- **공통 문서(`index.md`)**: 모든 스택에서 참인 문장만 쓰고, 프레임워크 고유 용어 대신 일반 개념어(진입 계층, 트랜잭션 경계, 영속성 포트 등)를 씁니다.
- **스택 문서(`<stack>.md`)**: `<Slot>`/`<Fill>` 같은 전용 태그 없이 독립된 순수 마크다운으로 작성합니다.
- **단일 공통 문서(`<slug>.md`)**: 아티클·튜토리얼처럼 스택 구분이 필요 없는 글은 단일 파일로 둡니다.

### 머리말 (Frontmatter)

- 공통 문서(`index.md`, `<slug>.md`): `title`, `summary`, `order`, `icon`을 작성합니다. 본문에 H1(`# 제목`)을 중복해서 쓰지 않습니다.
- 스택 문서(`<stack>.md`): `title`, `summary`를 작성합니다. 본문에 H1(`# 제목`)을 중복해서 쓰지 않습니다.
- 아티클·블로그 글: 카드뷰에 노출할 `thumbnail: /thumbnails/<slug>.jpg`와 이미지 배경의 지배적 색상 `thumbnailColor: "#XXXXXX"`를 함께 둡니다(로딩 전 자리 표시 배경색으로 먼저 그린 뒤 이미지를 부드럽게 페이드인). 썸네일은 단색 배경 중앙에 주제를 추상적으로 표현하는 한 손 미니멀 잉크 스케치(16:9, 텍스트·테두리 없음)로 통일해 `web/apps/blog/public/thumbnails/`에 저장합니다.

## 4. 통합 용어집 (`content/glossary/*.md`) 스키마

용어집은 영역별 마크다운 파일(`content/glossary/<domain>.md`)로 한 폴더에서 관리합니다.

```markdown
---
domain: backend
label: 백엔드
order: 2
---

## <카테고리>

### <대표 용어> (<영문>)

- **id**: `<전역-고유-영문-슬러그>`
- **정의**: 팝오버에 단독으로 띄워도 완결되는 1~2문장입니다.
- **구분**: *(선택)* 혼동하기 쉬운 다른 용어와의 경계입니다.
- **스택 매핑**: *(선택)*
  - Spring Boot: 대응 표현
- **관련 컴포넌트**: *(선택)* `button`, `dialog`
- **자동 연결**: *(선택)* `없음` 또는 `별칭1, 별칭2` (생략 시 대표 용어로 본문 자동 연결)
```

## 5. 시각 표현용 코드 펜스 (순수 마크다운 유지)

문서 원본에는 JSX를 쓰지 않고 아래 3가지 코드 펜스로 폴더 구조·계층도·플로우차트를 표현합니다.

- **`tree` (폴더 구조)**: 들여쓰기(2칸) + `# 설명` 주석. 첫 줄 `# title: 제목`, 이름 앞 `!`로 강조.
- **`layers` (수직 계층도)**: `# title:`, `# direction: down|up|none`, `# caption:` 메타 줄과 `이름 | 배지 | 설명` 행. 배지에 `선택`·`optional` 포함 시 점선 테두리.
- **`mermaid` (플로우차트 · 시퀀스)**: 첫 줄 `%% caption: 설명`으로 하단 캡션 표시.

## 6. 성숙도(Maturity) 메타데이터와 기준 점검

지침과 아티클에 실무 검증 정도를 나타내는 성숙도 상태 코드와 근거를 기록합니다. 아직 분류하지 않은 문서에는 생략합니다.

```yaml
---
title: ...
summary: ...
maturity: stable
maturityNote: "여러 업무 앱에서 오래 써 보며 검증됨. 소규모 단순 CRUD는 예외 가능"
reviewedAt: 2026-11-27
---
```

| 코드 | 라벨 | 의미 | AI 스킬 적용 강도 |
| --- | --- | --- | --- |
| `stable` | **안정** | 여러 프로젝트에서 오래 써 보며 실무 검증을 거친 기준 | 기본 기준 (프로젝트 예외 규칙이 없으면 그대로 따름) |
| `refining` | **다듬는 중** | 실무에 적용하며 계속 다듬고 있는 기준 — 경험에 따라 변경 가능 | 참고 기준 (상황에 맞게 유연하게 판단·확인) |

- 점검 명령: 루트에서 `node scripts/maturity-audit.mjs` (`--unscored`, `--json`, `--stale=180`)

## 7. 외부 출처 인용과 문서 정합성 원칙

블로그 글·아티클·레퍼런스에 외부 자료를 인용할 때 아래 원칙을 지킵니다.

1. **무검증 외부 출처 금지**: 에이전트는 학습 기억만으로 외부 URL이나 참고 자료 목록을 채우지 않습니다. 외부 링크는 사용자가 직접 제공했거나, 에이전트가 실제 원문을 조회해 **원문 핵심 논조와 우리 글에서의 역할(지지 / 대조 / 공식 명세)**을 확인·보고한 것만 포함합니다.
2. **원문 논조 존중과 역할 명시**: 원문의 주된 논조가 우리 주장과 다를 때 유리한 단서 한 줄만 발췌해 지지 근거처럼 쓰지 않습니다. 일반 통념이나 반대 입장을 대조 참고로 인용할 때는 본문과 참고 자료 목록 모두에 **대조 참고임을 분명히 밝힙니다.**
3. **참고 자료 덤프 금지**: 하단 `## 참고 자료`에 제목과 URL만 나열하지 않고, 본문 논지나 언급된 스펙에 직접 쓰인 핵심 출처만 남기며 각 항목 옆에 인용 목적을 한 줄로 적습니다.
4. **내부 레퍼런스 정합성 유지**: `reference/`의 규칙이 바뀌면 그 문서를 링크하고 있는 `blog/`·`articles/` 글의 서술과 충돌이 생기지 않는지 함께 점검합니다.
